## 📌 Зафиксированные решения

> Владелец может поменять любой пункт. Если пункт изменён — следуй новой версии.

| Тема | Решение |
|---|---|
| Где работает controller | Linux VPS (основной сценарий). Запуск на Windows желателен, но не обязателен |
| Бинарник | `cmd/hyroute-server` в том же Go-модуле |
| БД | SQLite через `modernc.org/sqlite` (без CGO), миграции, repository interfaces |
| Web-admin | Svelte 5 в `web/admin`, встраивается через `go:embed`, визуальный язык существующего frontend |
| Язык UI | Русский — основной, строки вынесены так, чтобы позже можно было добавить i18n |
| Bind по умолчанию | `127.0.0.1:<port>`; доступ извне — через SSH-туннель или reverse proxy с TLS (документировать) |
| Master key | env `HYROUTE_MASTER_KEY` или файл с правами 0600; потеря ключа = потеря сохранённых credentials (документировать) |
| Шифрование секретов | AES-256-GCM, envelope encryption, версия ключа хранится рядом с шифротекстом |
| Хеширование паролей | argon2id |
| Live-логи | SSE (проще WebSocket для однонаправленного потока) |
| Тесты remote-операций | fake `RemoteExecutor` + in-process SSH-сервер на `golang.org/x/crypto/ssh`; Docker-тесты только за build tag `integration` |
| Версия Hysteria | Проверить актуальную официальную документацию. Если сеть недоступна — зафиксировать целевую версию и пометить допущения в ARCHITECTURE |
| Ветка | Не коммитить в `main`. Если текущая ветка — `main`, создай `feature/server-manager`. Маленькие коммиты, без force-push |

## Снимок сервера (необязательно)

Владелец может положить в `reference/server-snapshot/` снимок своего сервера: конфиги Hysteria, systemd unit, правила firewall, sysctl, версию, ОС, список слушающих портов. Секреты и IP в нём заменены заглушками. В `reference/server-snapshot/README.md` владелец описывает, что в этой установке сделано не так, как надо.

Как использовать снимок:
- как тестовую фикстуру для импорта (P1-11): импорт должен распознавать такую установку, ничего на ней не меняя;
- как источник предупреждений «Needs attention»: каждая проблема из README владельца должна находиться автоматически и сопровождаться понятным объяснением и предложением исправить;
- **не** как образец для генерации новых конфигов.

Если снимка нет, работай по официальной документации Hysteria 2 и пометь в PROGRESS, что импорт проверен только на синтетических фикстурах.

## Phase 3 — Cascades
> Разбита на задачи P3-XX. Порядок — по зависимостям: модель и связь Entry → Exit, проверки, интерфейс; затем загрузка через другой узел; затем маршрутизация (ACL, outbounds, базы geo) и шаблоны топологий.

### Решения Phase 3 (сверено с исходниками Hysteria v2.12.3)
- **Как устроена связь.** У сервера Hysteria нет outbound типа «hysteria» — только `direct`, `socks5`, `http`. Поэтому на entry работает второй процесс — **клиент Hysteria до exit** (своя служба `hyroute-link-<id>.service`, конфиг `/etc/hysteria/link-<id>.yaml`, 0600, пользователь `hysteria`), он слушает SOCKS5 на `127.0.0.1:<свободный порт>` с логином и паролем; в конфиге сервера entry — outbound `socks5` до этого порта. SOCKS5-outbound Hysteria умеет UDP ASSOCIATE, так что UDP тоже идёт через цепочку.
- **Маршрут по умолчанию.** Default — первый outbound списка (и с ACL, и без). Outbound каскада ставится первым под именем `cascade`: всё идёт через exit, кроме того, что ACL явно отправляет в `direct`/`reject`.
- **Учётные данные на exit.** Exit с `auth.type: userpass` — отдельный пользователь `link-<id>` со сгенерированным паролем. Exit с `password` — entry использует этот пароль; режим auth не меняется, иначе изменились бы ссылки всех клиентов (записать и показать в UI). Exit с `http` или `command` (у Hysteria четыре типа auth) каскад не принимает: учётные данные для связи HyRoute там создать не может — понятный отказ при проверке цепочки. Пароль локального SOCKS5 генерируется (клиенты entry могут попасть на `127.0.0.1` entry через `direct`). Все промежуточные секреты — в envelope, маскируются в журналах, diff и редакторе.
- **Служба связи без проверки обновлений.** Клиент Hysteria проверяет обновления через своё подключение (`api.hy2.io` через exit): unit связи запускается с `--disable-update-check`.
- **N-hop.** Модель — цепочка из N узлов и N−1 связей; связь `A → B` — общий кирпич (на B учётные данные, на A клиент и outbound). В Phase 3 в production — ровно 2 узла; ограничение в проверке, не в схеме, поэтому Phase 4 не требует миграции.
- **Без петель и скрытых каскадов.** Связи всех цепочек вместе образуют граф, и у entry outbound `cascade` — default: если A → B и B → A, трафик ходит по кругу и кладёт оба сервера; если A → B и B → C, цепочка A → B на деле выходит через C. Поэтому граф всех связей проверяется на циклы, а в Phase 3 сервер не может быть entry в одной цепочке и exit в другой (сервер-exit может обслуживать несколько entry).
- **Проверка связи без чужих сервисов.** SOCKS5 клиента Hysteria отвечает одним кодом (host unreachable) на любую ошибку, поэтому сигналов два. (1) Служба и её пароль: controller открывает SSH-туннель (direct-tcpip) к `127.0.0.1:<порт>` на entry и проходит приветствие SOCKS5 с логином и паролем из outbound entry — ровно то, что делает сам Hysteria; затем CONNECT к цели проверки. (2) Exit и путь за ним: `hysteria ping -c <конфиг связи> <цель>` на entry (секреты в файле, не в argv; логи в JSON через `HYSTERIA_LOG_FORMAT=json`): «connected to server» — exit отвечает, время TCP-подключения через exit — задержка. `ping` не сообщает время рукопожатия: оно считается по меткам времени в логе. Цель проверки — адрес и порт SSH exit из инвентаря, в параметрах связи её можно заменить: с exit до собственного адреса бывает не достучаться (NAT, частный адрес, allowlist SSH, правило ACL), и тогда это отдельная причина «exit не открывает цель», а не Offline.
- **Итоговый egress IP** — исходящий адрес exit из его проверок (P2-03), только если первый outbound exit — `direct`; иначе — «через outbound X», адрес не показывается.
- **DNS на entry.** С ACL Hysteria ставит перед правилами системный resolver и разрешает **каждый** домен на entry, даже уходящий в `cascade` (сам SOCKS5-outbound передаёт exit имя, не адрес). Для каскада с IP- или geoip-правилами это значит: provider entry видит все домены, а подменённый ответ на заблокированный домен (заглушка с адресом из той же страны) попадает под `geoip:ru` и уходит в `direct`. Поэтому у entry с каскадом и такими правилами — шифрованный `resolver` (DoH/DoT), lint предупреждает о его отсутствии, а шаблоны ставят доменные правила (`geosite:`) выше IP-правил.
- **Базы geo.** Без явного пути Hysteria при старте сама качает `geoip.dat`/`geosite.dat` с `cdn.jsdelivr.net`; если не скачалось и файла нет — сервер не стартует. С явным путём (`acl.geoip`/`acl.geosite`) Hysteria ничего не качает: HyRoute кладёт файлы сам (напрямую, через controller или через другой узел) и обновляет их заданием.
- **Где хранятся правила.** Источник правды — `acl.inline` в конфиге сервера (ревизии, diff, откат и импорт работают как есть). Hysteria отбрасывает всё после `#`, поэтому метаданные редактора — в служебных строках-комментариях: `# @group Имя`, выключенное правило `# @off direct(...)`, комментарий к правилу — строка `# текст` перед ним. Чужие комментарии и порядок строк сохраняются.
- **Семантика «Проверить правило»** — как у Hysteria: первое совпавшее правило; домен в нижнем регистре без точки в конце и в Unicode (`idna.ToUnicode`: `xn--…` и кириллица — одно имя); `suffix:example.com` совпадает с `example.com` и `*.example.com`; IP-правила — по адресам, в которые разрешился домен; без совпадения — `default`. Чтобы семантика совпадала точно, разбор и сопоставление — копия пакета `extras/outbounds/acl` (с `v2geo`) Hysteria v2.12.3 в `third_party/hysteria-acl` (MIT, с лицензией): модуль `extras/v2` как зависимость не подключается (`replace core/v2 => ../core`), а сам пакет зависит только от `idna` и `protobuf`.
