# HyRoute Server

HyRoute Server — панель для своих серверов Hysteria 2. Она подключается к VPS по SSH, ставит и настраивает Hysteria, показывает её состояние и журнал, меняет конфиг с откатом при ошибке и выдаёт ссылки и QR-коды для клиентов. Ходить на сервер по SSH руками не нужно.

Панель состоит из одной программы `hyroute-server` (controller) с веб-интерфейсом. Controller запускается где угодно — на своём компьютере, на домашнем сервере или на отдельном VPS — и управляет серверами Hysteria по SSH. На самих серверах ничего, кроме Hysteria, не ставится.

> Панель в разработке, готовых сборок пока нет: её собирают из исходников.

## Сборка

Нужен Go 1.27. Веб-интерфейс уже собран и лежит в репозитории, Node.js не нужен.

```sh
go build -o hyroute-server ./cmd/hyroute-server
```

Собирается под Linux и Windows. Управляемые серверы — Linux с systemd (Debian, Ubuntu и похожие).

## Запуск

```sh
./hyroute-server
```

По умолчанию панель слушает только `127.0.0.1:8480`: снаружи её не видно (как до неё добраться — ниже, в разделе «Доступ»). Данные лежат в `/var/lib/hyroute-server` (в Windows — `C:\ProgramData\HyRoute Server`):

| Файл | Что это |
|---|---|
| `hyroute-server.db` | база: серверы, задания, ревизии конфигов, пользователи |
| `master.key` | мастер-ключ, которым зашифрованы пароли и ключи SSH и конфиги Hysteria |
| `setup-token` | код первого запуска; исчезает, когда создан владелец |
| `backups/` | резервные копии базы (раздел «Резервные копии» ниже) |
| `lock` | пока панель работает, второй её экземпляр с этим каталогом не запустится («another hyroute-server process uses this data directory») |

Доступ к этим файлам должен быть только у пользователя, от которого работает панель. В Linux и других Unix панель проверяет это при запуске: каталог — не шире `0700`, база и ключ — не шире `0600`, владелец — сам этот пользователь. Иначе она не запустится и напишет команду, которая это исправит (`chmod 700 …`, `chmod 600 …` или `chown`). В Windows каталог и ключ получают права только для SYSTEM, «Администраторов» и пользователя панели.

Параметры задаются флагами или переменными окружения:

| Флаг | Переменная | По умолчанию |
|---|---|---|
| `-listen` | `HYROUTE_SERVER_LISTEN` | `127.0.0.1:8480` |
| `-data-dir` | `HYROUTE_SERVER_DATA_DIR` | `/var/lib/hyroute-server` |
| `-master-key-file` | `HYROUTE_SERVER_MASTER_KEY_FILE` | `<data-dir>/master.key` |
| `-tls-cert`, `-tls-key` | `HYROUTE_SERVER_TLS_CERT`, `HYROUTE_SERVER_TLS_KEY` | нет (HTTP) |
| `-insecure-http` | `HYROUTE_SERVER_INSECURE_HTTP` | выключено |
| `-trust-proxy` | `HYROUTE_SERVER_TRUST_PROXY` | выключено |
| `-allowed-host` | `HYROUTE_SERVER_ALLOWED_HOST` | нет (имена через запятую, например `panel.example.com`) |
| `-monitor-interval` | `HYROUTE_SERVER_MONITOR_INTERVAL` | `1m` (`0` — не собирать метрики) |
| `-geo-interval` | `HYROUTE_SERVER_GEO_INTERVAL` | `168h` (`0` — не обновлять базы geo; отрицательное значение — ошибка запуска) |
| `-alert-threshold` | `HYROUTE_SERVER_ALERT_THRESHOLD` | `3` — сколько проверок подряд нужно, чтобы событие сказало о смене статуса сервера или связи каскада (от 1 до 100) |
| `-backup-interval` | `HYROUTE_SERVER_BACKUP_INTERVAL` | `0` — копии только по кнопке и командой (например, `24h` — раз в сутки; не меньше `10m`) |
| `-backup-keep` | `HYROUTE_SERVER_BACKUP_KEEP` | `7` — сколько последних копий хранить |
| `-backup-passphrase-file` | `HYROUTE_SERVER_BACKUP_PASSPHRASE_FILE` | нет — копии не шифруются; парольную фразу можно передать и переменной `HYROUTE_SERVER_BACKUP_PASSPHRASE` |
| `-log-level` | `HYROUTE_SERVER_LOG_LEVEL` | `info` |

Мастер-ключ можно передать и переменной `HYROUTE_MASTER_KEY` — тогда файл не читается и не создаётся. Переменная из одних пробелов и переводов строки считается незаданной: ключ берётся из файла, с теми же проверками прав.

Пример службы systemd для Linux (`/etc/systemd/system/hyroute-server.service`):

```ini
[Unit]
Description=HyRoute Server
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/hyroute-server
Restart=on-failure
StateDirectory=hyroute-server
StateDirectoryMode=0700
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

```sh
sudo install -m 0755 hyroute-server /usr/local/bin/
sudo systemctl enable --now hyroute-server
```

## Первый запуск

При первом запуске панель пишет в журнал, где лежит код первого запуска (сам код в журнал не попадает):

```sh
sudo cat /var/lib/hyroute-server/setup-token
```

Откройте панель, введите код и задайте имя и пароль владельца. После этого код удаляется, а вход — по имени и паролю. Владелец и администраторы добавляют других пользователей в «Настройках»; роль «только чтение» видит серверы и журналы, но ничего не меняет и не видит ссылок с паролями.

## Пользователи и журнал аудита

**Роли.** Владелец и администратор управляют серверами и пользователями, оператор — серверами, каскадами и пресетами, но не пользователями, «только чтение» ничего не меняет. Владельцем управляет только владелец: администратор не может сменить ему роль или пароль, заблокировать или удалить его и не может сделать кого-то владельцем. Себя заблокировать или удалить нельзя.

**Пользователи.** «Настройки» → «Пользователи»: роль, состояние и последний вход каждого (для входов до этой версии — по журналу аудита, если он их сохранил). Владелец и администраторы добавляют пользователей, а в меню «Действия» у каждого:

- «Изменить роль» — новая роль действует сразу, входить заново не нужно;
- «Сбросить пароль» — панель создаёт случайный пароль и показывает его один раз (кнопка «Копировать»), или вы задаёте свой; все сессии пользователя сразу завершаются;
- «Заблокировать» — все сессии пользователя завершаются сразу, включая открытые журналы и ход заданий, а войти он не сможет, пока его не разблокируют; «Разблокировать» возвращает вход, но не старые сессии;
- «Передать роль владельца» (только у владельца) — пользователь становится владельцем, а вы — администратором;
- «Удалить» — пользователь и его сессии удаляются; его задания, версии конфигов и записи аудита остаются.

Блокировка, удаление и передача роли просят подтверждения. У панели всегда остаётся владелец, который может войти: последнего такого владельца нельзя понизить, заблокировать или удалить — сначала передайте роль другому. Владелец может сделать владельцем и ещё одного пользователя (роль «владелец» в «Изменить роль»).

**Свой пароль.** «Настройки» → «Учётная запись» → «Сменить пароль»: текущий пароль и новый дважды. Это доступно любой роли. Сессии на других устройствах завершаются, а в этом браузере вы остаётесь в панели. Неверный текущий пароль считается неудачной попыткой входа (те же ограничения на число попыток).

**Аудит.** «Журнал» → вкладка «Аудит» (владелец и администраторы): кто и когда входил и выходил, неудачные входы, действия с пользователями, серверами, каскадами и пресетами, показы ссылок и каждый запуск и повтор задания с его номером. Фильтры — пользователь, действие (одно или группа, например «Входы и сессии: все»), объект (сервер, каскад, пользователь или все объекты такого вида) и даты; «Показать ещё» загружает следующие записи. Задание в аудите записано под своим первым сервером, номер задания открывает его страницу. Паролей в журнале аудита нет: ни при создании пользователя, ни при сбросе и смене пароля, ни в заданиях.

## Доступ

Панель управляет вашими серверами и знает их пароли, поэтому открытой в интернет по HTTP её оставлять нельзя. На адресе, доступном из сети (например, `0.0.0.0:8480`), панель без TLS не запустится; обойти это можно только явным флагом `-insecure-http`, для сети, которой вы доверяете. Три способа:

**SSH-туннель** — ничего не нужно настраивать. Если controller работает на машине `admin.example.com`:

```sh
ssh -L 8480:127.0.0.1:8480 user@admin.example.com
```

и откройте `http://127.0.0.1:8480` у себя в браузере. Если controller работает на вашем компьютере, туннель не нужен. На адресе `127.0.0.1` панель открывается только как `127.0.0.1`, `localhost` или `[::1]`: под другим именем она отвечает ошибкой, чтобы чужой сайт не мог выдать себя за неё, перенаправив своё имя на `127.0.0.1`.

**Обратный прокси с TLS** — если панель нужна по адресу вида `https://panel.example.com`. Controller остаётся на `127.0.0.1:8480`, а прокси на той же машине принимает HTTPS. Пример для Caddy (сертификат он получит сам):

```
panel.example.com {
	reverse_proxy 127.0.0.1:8480
}
```

Для nginx:

```nginx
location / {
	proxy_pass http://127.0.0.1:8480;
	proxy_set_header Host $host;
	proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
	proxy_set_header X-Forwarded-Proto $scheme;
}
```

Прокси должен передавать панели адрес, который набран в браузере: заголовок `Host` (Caddy делает это сам, nginx — только с `proxy_set_header Host $host`) или `X-Forwarded-Host`. Иначе вход и любые изменения отклоняются с ошибкой защиты от подделки, а в журнале controller появляется предупреждение «write refused: Origin is not the host».

Запустите controller с `-trust-proxy`: тогда он верит заголовкам `X-Forwarded-For`, `X-Forwarded-Proto` и `X-Forwarded-Host` от прокси на этой машине (для журнала входов и защиты от перебора), и cookie сессии помечаются как только для HTTPS. Укажите и `-allowed-host` с публичным именем панели (`-allowed-host panel.example.com`): тогда она отвечает только на это имя и на `localhost`, `127.0.0.1`, `[::1]`. Без флага за прокси имя не проверяется, и если к панели ходят ещё и SSH-туннелем, чужой сайт может выдать себя за неё, перенаправив своё имя на `127.0.0.1`.

**Свой TLS** — без прокси: укажите сертификат и ключ в формате PEM, и панель будет отвечать по HTTPS на любом адресе.

```sh
hyroute-server -listen 0.0.0.0:8443 -tls-cert /etc/hyroute-server/fullchain.pem -tls-key /etc/hyroute-server/privkey.pem
```

Когда файлы сертификата меняются (например, после продления), панель подхватывает их сама, перезапуск не нужен.

## Мастер-ключ и резервная копия

Пароли и ключи SSH, пароли Hysteria и конфиги в базе зашифрованы мастер-ключом. **Без мастер-ключа база бесполезна:** зашифрованное из неё не восстановить.

- При первом запуске ключ создаётся в `master.key` (права 0600), и в журнале появляется напоминание сделать его копию.
- Новый ключ создаётся только для пустой базы. База запоминает свой ключ: если ключа нет или он не тот (потерялся файл, неверный `-master-key-file` или `HYROUTE_MASTER_KEY`), панель не запустится и напишет, что делать, — верните ключ из резервной копии или укажите путь к нему. Если данные базы не нужны, удалите её, и панель начнёт с чистого листа.
- Сохраните копию `master.key` отдельно от базы — например, в менеджере паролей. Копия базы и ключа в одном месте равна отсутствию шифрования.
- Резервная копия панели — копия базы (раздел «Резервные копии» ниже) плюс ключ.
- Вместо файла ключ можно передавать переменной `HYROUTE_MASTER_KEY` (например, из хранилища секретов). Формат тот же, что в файле: `1:<32 байта в base64>`.
- В файле ключа строка, которая начинается с `#`, — комментарий: она пропускается целиком, вместе с ключами в ней.
- Смена ключа: остановите службу и выполните `hyroute-server rekey -rotate`. Команда добавит в файл ключа строку с новой версией (старые строки остаются), перешифрует ею все данные базы и скажет, какие версии базе больше не нужны. Их строки можно удалить из файла, но копии базы, сделанные раньше, зашифрованы и ими: пока такие копии нужны, храните прежний файл ключа вместе с ними. После смены сохраните новую копию файла ключа. Если ключ передаётся переменной `HYROUTE_MASTER_KEY`, добавьте в неё строку новой версии (`2:<новый ключ>`) сами и выполните `hyroute-server rekey` без `-rotate`.
- Новую версию можно добавить и вручную, строкой `2:<новый ключ>` рядом со старой: тогда новые данные шифруются ею, а старые остаются на своей версии, пока их не перешифрует `rekey`. Без версии, которой зашифровано хоть что-то в базе, панель не запустится и назовёт строку, которую нужно вернуть.

### Резервные копии

Копия базы — это всё, что знает панель: серверы, их ревизии конфигов, каскады, пользователи, журнал заданий и аудита. Копии лежат в `<data-dir>/backups` с правами 0600, хранятся последние семь (`-backup-keep`).

- **По расписанию:** запустите панель с `-backup-interval 24h` — копия будет делаться раз в сутки, пока служба работает. По умолчанию расписание выключено.
- **По кнопке:** владелец в «Настройках» → «Резервные копии» нажимает «Сделать копию» и может скачать любую копию из списка. Скачивание записывается в аудит.
- **Командой:** `hyroute-server backup` кладёт копию в `<data-dir>/backups`, `hyroute-server backup -out /путь/к/файлу` — в указанный файл. Служба может работать: копия согласованная. Команду запускают от того же пользователя, что и службу (в примере выше — `root`), с теми же `-data-dir` и `-master-key-file`, если они заданы.

**Мастер-ключа в копии нет.** Без копии ключа копия базы не восстановится, поэтому храните ключ отдельно — например, в менеджере паролей. Проверить, что сохранённый ключ правильный, можно заранее: «Настройки» → «Проверить копию ключа» (владелец и администратор). Вставьте текст файла `master.key`, и панель скажет по каждой версии ключа, открывает ли она данные базы. Вставленный ключ нигде не сохраняется.

**Шифрование копий.** Положите парольную фразу в файл с правами 0600 и укажите его флагом `-backup-passphrase-file` (или передайте фразу переменной `HYROUTE_SERVER_BACKUP_PASSPHRASE`). Тогда копии шифруются (имя заканчивается на `.db.enc`), и без фразы их не открыть. Фразу, как и ключ, храните отдельно от копий.

**Восстановление** — только командой, при остановленной службе:

```sh
sudo systemctl stop hyroute-server
sudo hyroute-server restore /var/lib/hyroute-server/backups/hyroute-server-20261008-030000.db
sudo systemctl start hyroute-server
```

На новой машине сначала положите на место файл ключа (`<data-dir>/master.key`, права 0600) или задайте `HYROUTE_MASTER_KEY`. Для зашифрованной копии передайте парольную фразу так же, как при её создании. До того как что-то заменить, команда проверяет копию: что она не повреждена, что её сделала не более новая версия `hyroute-server` и что ключ открывает её данные. Если в каталоге уже есть база с пользователями или серверами, команда откажет; с флагом `-force` прежняя база не удаляется, а переносится рядом, в `hyroute-server.db.before-restore-<время>`. Копия — состояние на момент её создания. Задания, которые шли в тот момент, панель при запуске проверит, как после сбоя: посмотрит фактическое состояние серверов и продолжит или завершит их. Если после копии конфиг сервера меняли, панель увидит это как правку вне HyRoute и откажется его перезаписывать — такой сервер импортируйте заново.

### Команды обслуживания

Команды работают с каталогом данных на машине, где стоит панель. Запускайте их от того же пользователя, что и службу, с теми же `-data-dir` и `-master-key-file` (или переменными), если они заданы. Список команд — `hyroute-server help`.

| Команда | Что делает | Служба |
|---|---|---|
| `hyroute-server backup [-out файл]` | копия базы (раздел выше) | может работать |
| `hyroute-server restore [-force] файл` | восстановление из копии | остановите |
| `hyroute-server reset-password имя` | новый пароль пользователя: панель создаёт его и показывает один раз; с `-password-stdin` пароль берётся из первой строки ввода. Все сессии пользователя завершаются, сброс пишется в аудит | может работать |
| `hyroute-server rekey [-rotate]` | перешифровывает все данные базы текущей версией мастер-ключа (с `-rotate` — сначала добавляет новую версию) и говорит, какие версии больше не нужны. Если команду прервать, её можно просто повторить: перешифрованное останется | остановите |
| `hyroute-server doctor` | проверяет права каталога данных, базы, ключа и копий, подходит ли ключ, целостность базы, версию схемы, свободное место и когда сделана последняя копия; при проблемах завершается с ошибкой | может работать |
| `hyroute-server diag [-out файл] [-jobs N]` | диагностический пакет (раздел «Диагностический пакет» ниже) в `hyroute-diag-<время>.zip` текущего каталога или в указанный файл; только читает базу, журнала панели в нём нет | может работать |
| `hyroute-server version` | версия программы и схемы базы | — |

Забыли пароль единственного владельца — выполните на машине панели `sudo hyroute-server reset-password <имя>` и войдите с паролем, который она покажет.

## Работа с серверами

**Добавить сервер.** «Серверы» → «Добавить сервер»: название, адрес, пользователь SSH (root или пользователь с sudo без пароля) и пароль или закрытый ключ. Кнопка «Добавить и развернуть» сразу переходит к развёртыванию.

**Ключ сервера.** При первом подключении панель показывает отпечаток ключа SSH сервера. Сверьте его с тем, что показывает сам сервер (в консоли хостинга: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), и подтвердите. До подтверждения пароль на сервер не отправляется. Если ключ позже изменится, подключение блокируется, пока вы не подтвердите новый. Если у сервера есть сертификат хоста от вашего CA, панель показывает отпечаток самого ключа (тот же, что у `ssh-keygen -lf` для файла ключа), а перевыпуск сертификата с тем же ключом сменой не считается.

**Проверить готовность.** Меню «Ещё» → «Проверить готовность»: система, архитектура, память и диск, брандмауэр, доступ к GitHub, занятость порта, есть ли уже Hysteria. Сервер при этом не меняется. Если порт держит другая Hysteria (своя служба с другим именем или контейнер Docker), развернуть не получится: новая служба не займёт порт. Панель предложит импортировать сервер или сначала остановить ту Hysteria.

**Развернуть.** Выберите сертификат (самоподписанный — домен не нужен, клиенты проверяют его по отпечатку; или Let's Encrypt — нужен домен, указывающий на сервер; домен в зоне вроде `.рф` можно ввести кириллицей, панель запишет его в punycode), порт, смену портов (port hopping), сайт-маскировку и обфускацию Salamander. Панель скачивает Hysteria с GitHub и сверяет контрольную сумму (если с сервера GitHub недоступен — скачивает сама и заливает по SFTP), ставит её туда же, куда официальный скрипт установки, открывает порты в ufw или firewalld и проверяет, что Hysteria приняла соединения. Если что-то пошло не так, изменения откатываются, в том числе закрываются порты, открытые этим развёртыванием; правила брандмауэра, которые были до него, не трогаются. Панель помнит, какие порты открыла сама: при смене порта (развёртыванием или правкой конфига) новые открываются до перезапуска, а свои старые закрываются после успешной проверки. Повторное развёртывание сохраняет сертификат и пароли клиентов при любом способе входа (общий пароль, пользователи userpass с их паролями, внешняя проверка): ссылки у клиентов продолжают работать. Конфиг развёртывание собирает из параметров формы, а форма открывается с настройками текущего конфига и с установленной версией Hysteria: после «Обновить версию» повторное развёртывание её не понижает (через API без `version` — тоже). Если после развёртывания конфиг меняли в редакторе, возвращали из истории или он импортирован, панель предупредит, что всё, чего в форме нет (ACL, resolver, несколько выходов и другое), пропадёт, и развернёт только после подтверждения. Если конфиг после развёртывания меняли только смена паролей, базы geo или каскад (или его вернули к такой версии), форма заполняется параметрами того развёртывания целиком; иначе из конфига переносятся основные поля, скорость и UDP, а QUIC, определение сайтов и выход нужно задать заново. «Не открывать порты в ufw / firewalld» форма помнит всегда.

**Настройки развёртывания.** Кроме основных параметров, форма задаёт:

- вход клиентов: один пароль на всех или пользователи, у каждого свой пароль и своя ссылка. При повторном развёртывании оставшиеся пользователи сохраняют пароли, удалённые теряют доступ, а смена способа входа даёт всем новые пароли; форма об этом предупреждает;
- сайт-маскировку: чужой сайт (прокси), папку на сервере (развёртывание её не создаёт, а проверяет, что она есть) или свою страницу с кодом ответа; по желанию сайт отвечает и по TCP 80/443, как обычный сайт;
- проверку домена для Let's Encrypt через DNS: порты не нужны, нужен ключ API провайдера (Cloudflare, DuckDNS, Gandi, GoDaddy, Namecheap, Njalla, Porkbun, Vultr);
- в разделе «Дополнительно»: скорость сервера на клиента или отказ от скорости клиентов (BBR), окна и тайм-аут QUIC, пересылку и тайм-аут UDP, определение сайтов (sniff), выход в интернет (напрямую с выбором IPv4/IPv6 и интерфейса или через SOCKS5/HTTP-прокси).

У каждой настройки есть пояснение, что она меняет. Пустое поле оставляет значение Hysteria по умолчанию. Неверные сочетания (например, скорость сервера вместе с отказом от скорости клиентов или маскировка по TCP вместе с проверкой Let's Encrypt через HTTP) панель отклоняет до начала развёртывания и объясняет почему. Ключи DNS-провайдера и пароль прокси хранятся зашифрованными вместе с заданием и в его параметры не попадают; при повторном развёртывании пустое поле оставляет текущее значение.

**Импортировать.** Если Hysteria на сервере уже стоит, «Импортировать» найдёт службу и конфиг и возьмёт их под управление как есть — на сервере при этом ничего не меняется. Отчёт импорта перечислит, что стоит поправить: конфиг, который читают все, работу от root, короткие пароли, сертификат на исходе и другое. Программу Hysteria панель запускает (чтобы узнать версию или проверить связь каскада) только если её и каталоги над ней может изменить лишь root; иначе версия не показывается, а отчёт импорта об этом предупредит. Вместо импорта можно развернуть свою Hysteria с заменой («Заменить Hysteria, установленную не HyRoute»): прежние бинарник, конфиг, сертификат и служба сохранятся рядом с суффиксом `.hyroute-orig`, и HyRoute их потом не меняет и не удаляет — из них можно вернуть прежних клиентов.

**Страница сервера** (щёлкните по названию): состояние службы, версия, порты, память, перезапуски; «Запустить», «Перезапустить», «Остановить»; нагрузка, память и диск сервера; живой журнал Hysteria. Живой журнал одного сервера можно держать открытым в двух вкладках, а всего страницы панели держат к одному серверу до 8 подключений по SSH: сверх этого панель просит повторить через несколько секунд.

**Обновить или переустановить Hysteria.** На странице сервера в блоке службы — «Обновить или переустановить». «Обновить версию» ставит указанную версию Hysteria, в том числе более старую: бинарник скачивается и сверяется с хешем релиза, прежний сохраняется рядом с суффиксом `.hyroute-prev`, служба перезапускается, и панель проверяет, что новая версия работает и принимает соединения; если нет — возвращает прежний бинарник и перезапускает службу с ним. Обновить можно и импортированную Hysteria: бинарник заменяется на месте — если служба запускает программу с именем `hysteria*`; службу, которая запускает Hysteria через docker, `env` или оболочку, панель не обновляет, чтобы не заменить чужую программу. «Переустановить» (только для Hysteria, которую поставил HyRoute) заново ставит всё, кроме конфига: бинарник установленной версии, пользователя `hysteria`, службу systemd и права файлов в `/etc/hysteria`; конфиг, сертификаты и ссылки клиентов не меняются. Если ничего не изменилось, служба не перезапускается.

**Сменить пароли и сертификат.** Кнопка «Сменить пароли» в блоке конфига: новый случайный пароль клиентов (или пароли отмеченных пользователей userpass), новый пароль обфускации Salamander и новый самоподписанный сертификат (с тем же именем, но другим pinSHA256). Остальной конфиг не меняется. Перед запуском панель предупреждает, у кого перестанут работать старые ссылки: пароль обфускации и сертификат общие для всех клиентов. Смена применяется как правка конфига: копия, перезапуск, проверка, а если Hysteria не заработает, возвращаются прежние пароли и сертификат. Новые ссылки и QR-коды — в карточке «Подключение клиентов». Копии старого ключа на сервере не остаются. Сертификат Let's Encrypt или от удостоверяющего центра панель не меняет, пароли внешней проверки (`auth: http`/`command`) — тоже.

**Конфиг.** «Изменить конфиг» открывает редактор: основные настройки формой или весь YAML. Вкладка переключается, когда панель проверит последнюю правку, поэтому другая вкладка всегда показывает её; если правка не прошла проверку (например, YAML не разобрать), вкладка остаётся, пока ошибку не исправят. Пароли в редакторе скрыты (`[REDACTED]`) и остаются прежними, пока вы не впишете новые; скрываются и пароли, подставленные через YAML-ссылку (`&` / `*`), и пароли внутри адресов вида `https://user:pass@…`. Редактор открывают только роли, которым можно менять серверы. Перед применением видны ошибки проверки и изменения. Применение: копия прежнего конфига → запись нового → новые порты в ufw или firewalld → перезапуск Hysteria → проверка. Если Hysteria не заработала, возвращается прежний конфиг. Если ошибка случилась до перезапуска (например, не удалось открыть порт), прежний конфиг возвращается без перезапуска, и клиенты не отключаются. Если конфиг на сервере правили вручную по SSH, панель откажется его перезаписывать и предложит импортировать сервер заново.

**Статистика трафика.** Флажок «Статистика трафика» в редакторе включает API статистики Hysteria: через него панель видит, кто из клиентов в сети и сколько у кого трафика. API слушает только `127.0.0.1` на сервере, и панель обращается к нему изнутри по SSH, а секрет к нему панель создаёт сама и нигде не показывает. Адрес не на localhost или API без секрета панель применить не даст: через этот API видно всех клиентов и их можно отключать.

На странице сервера появляется карточка «Трафик клиентов»: кто сейчас в сети, сколько клиенты скачали (приём) и отправили (отдача) по часам за сутки, неделю, 30 или 90 дней и таблица по пользователям. Трафик считается раз в минуту и хранится 90 дней; при одном общем пароле все клиенты считаются одним пользователем `user`. Владелец, администраторы и операторы могут открыть «Показать соединения» — куда клиенты ходят прямо сейчас; список обновляется каждые 5 секунд, пока открыт. Панель эти адреса не сохраняет. Для чтения статистики на сервере нужен `curl`.

**Нагрузка сервера.** Панель раз в минуту заходит на серверы по SSH (только чтение, без sudo) и записывает загрузку процессора, память, диск, load и скорость сети. На странице сервера — графики за час, 6, 24 и 48 часов (каждая минута) и за 7 и 30 дней (средние по 15 минут); наведите мышь или нажмите стрелки на графике, чтобы увидеть значения, или переключитесь на таблицу. На «Обзоре» у каждого сервера видны текущие процессор и память. Если сервер перестал отвечать по SSH, он помечается «Не в сети» и возвращается в «Работает», когда снова отвечает. Частоту меняет `-monitor-interval` (`0` — не собирать).

**Здоровье.** У серверов с установленной Hysteria панель раз в минуту проверяет: заходит ли SSH, работает ли служба, слушает ли Hysteria свой UDP-порт и — главное — отвечает ли этот порт снаружи, со стороны панели. Для последнего панель шлёт на порт служебный пакет QUIC, на который сервер отвечает, не принимая подключения; пароли клиентов при этом не используются (с обфускацией Salamander пакет шифруется её паролем). По результату сервер получает статус «Работает», «С проблемами» (с причиной: служба упала, порт закрыт брандмауэром и т. п.) или «Недоступен», а в блоке «Здоровье» видна последняя проверка и смены статуса за неделю. Пока на сервере идёт задание, проверка его пропускает. Служба, остановленная кнопкой «Остановить», — тоже «С проблемами»; когда она снова работает (в том числе запущенная на сервере вручную), статус возвращается в «Работает» сам.

**Требует внимания.** На «Обзоре» сверху — список того, что стоит посмотреть сейчас, худшее первым: серверы не в «Работает» с причиной, последнее задание сервера, если оно упало, связи каскадов устаревшие, не развёрнутые или не работающие по последней проверке, предупреждения правил маршрутизации, устаревшая Hysteria и базы geo, мониторинг на паузе (сервер отклонил вход по SSH) или выключенный, сменившийся ключ SSH сервера, диск заполнен больше чем на 90 %. Название ведёт на страницу сервера, каскада или задания; список обновляется сам раз в 30 секунд, пока вкладка открыта. В нём нет ни паролей, ни адресов серверов — только их названия.

**События.** Всё это панель записывает и как события: событие открыто, пока проблема есть, и закрывается, когда она прошла (например, «Сервер «Alpha» снова работает»). Повторы открытого события не создают нового, а прибавляются к нему. Статус сервера и связи каскада меняется в событии только после нескольких проверок подряд с одинаковым итогом (`-alert-threshold`, по умолчанию 3), поэтому один пропущенный ответ не поднимает тревогу. События — об упавшем задании и сервере, который после него «Требует внимания», о сменившемся ключе SSH или отказе во входе, о диске (открывается выше 90 %, закрывается ниже 85 %), о базах geo, которые controller не смог обновить. Последние события видны под списком «Требует внимания» («События за 30 дней»); закрытые хранятся 30 дней.

**Если сеть пропала у самой панели.** Когда в круге мониторинга не ответил ни один сервер (их два и больше), панель сначала проверяет свою сеть — пробует подключиться к общедоступным адресам Cloudflare, Google и Quad9. Сети нет — состояния серверов не меняются и проверки не записываются, на «Обзоре» висит красная плашка «У controller нет сети», а событие одно на всё время, пока сети нет. Когда сеть вернулась, проверки снова идут как обычно.

**Порты.** Кнопка «Порты» в блоке конфига меняет порты сервера: один порт или несколько портов и диапазонов для port hopping (до 16 строк, без пересечений), адреса (все IPv4 и IPv6 или только IPv4) и интервал, с которым клиент переходит на другой порт. Hysteria слушает наименьший порт и сама перенаправляет на него остальные. Перед перезапуском панель проверяет, что эти UDP-порты не заняты другими программами (например, WireGuard или локальным DNS) и что на сервере есть nftables, либо iptables и ip6tables для IPv6; новые порты открываются в брандмауэре, а старые порты HyRoute закрываются после проверки. Интервал — настройка клиента: он сохраняется сразу, без перезапуска Hysteria, и попадает в ссылки (`mportHopInt`) и конфиг клиента. После смены портов раздайте клиентам новые ссылки.

**Пресеты.** Страница «Пресеты» хранит части конфига по разделам: порты, обфускация, маскировка, скорость, QUIC, UDP, DNS, определение сайтов, ACL, выходы. «Создать из сервера» берёт их из текущего конфига без паролей, ключей, адресов серверов и outbound каскада `cascade` (что не вошло, пресет перечислит; на входе каскада раздел «выходы» пресета outbound `cascade` не трогает), поэтому пресет можно экспортировать в файл и передать; импорт снова очищает файл. Пресет можно скопировать, переименовать и удалить. «Применить к серверу» (или кнопка «Пресет» на странице сервера) показывает, что изменится в выбранных разделах, и применяет их как обычную правку конфига — с копией, перезапуском, проверкой и откатом; остальной конфиг не меняется. Пароли в предпросмотре скрыты, в том числе новый пароль обфускации: его создаёт само применение, а новые ссылки клиентов после него — в карточке «Подключение клиентов». При развёртывании пресет выбирается в форме: отмеченные разделы (кроме портов и обфускации, их задаёт форма) берутся из пресета вместо полей формы. Если пресет, из которого прошлое развёртывание брало разделы, с тех пор удалён, форма предупредит, что эти разделы пропадут из конфига, и развернёт только после подтверждения.

**Загрузка Hysteria через другой сервер.** Если ни сервер, ни controller не достают до GitHub, в развёртывании и в «Обновить или переустановить» выберите «Через другой сервер» и сервер, у которого доступ есть. Он отдаст свою Hysteria, если это та же сборка, или скачает релиз сам; controller перенесёт файл, а хеш релиза сверяется и на нём, и на целевом сервере. Хеш всегда берётся у controller, поэтому подменённый сервер-источник не установит чужой файл. Ключ SSH сервера-источника должен быть подтверждён («Подключение»), иначе панель не начнёт задание; root или sudo на нём не нужны. Если Hysteria не скачал controller, ошибка задания скажет, что делать: загрузить самим сервером (когда GitHub с него доступен) или через другой сервер.

**Каскады.** Страница «Каскады»: вход → выход, при желании через один или два промежуточных сервера. Клиенты подключаются ко входу, а их трафик уходит в интернет с выхода. «Создать каскад»: название, сервер входа и сервер выхода (на них Hysteria уже развёрнута или импортирована), по желанию — скорость связи, без UDP и адрес для проверки связи. Кнопка «+» на стрелке между серверами ставит туда промежуточный сервер, «×» убирает его; в каскаде до четырёх серверов. Промежуточный сервер принимает трафик сервера перед ним и передаёт следующему, а его собственные клиенты тоже выходят через выход каскада. Каждый промежуточный сервер — ещё один участок со своей связью и своей задержкой. Сервер может быть промежуточным только в одном каскаде и не может быть в нём ещё и входом или выходом другого каскада: иначе трафик того каскада ушёл бы дальше незаметно или пошёл бы по кругу; панель объяснит, что мешает. Можно начать с шаблона: «Всё через exit» или «RU напрямую» — или загрузить свой файл шаблона. «Развернуть» ставит на вход клиент Hysteria, который подключается к следующему серверу (служба `hyroute-link-…`, SOCKS5 только на `127.0.0.1` входа с паролем), и делает его первым outbound входа — `cascade`; на следующий сервер с пользователями userpass добавляется отдельный пользователь связи (`link-…`). Промежуточный сервер получает и то и другое: пользователя связи от сервера перед ним, клиент и outbound `cascade` до следующего. Все связи каскада разворачиваются одним заданием от выхода ко входу: сервер получает outbound `cascade`, только когда связь после него уже работает. Он не клиент: в «Подключении клиентов» его нет и ссылку на него панель не выдаёт, «Сменить пароли» его пароль не меняет, а повторное развёртывание сохраняет его, пока вход остаётся по пользователям (при переходе на общий пароль форма предупреждает, что связь перестанет работать). Перед перезапуском панель проверяет связь, а если что-то не заработало на любом участке, откатывает все серверы каскада. Если откат не удался (например, оборвалось подключение), каскад помечается «устарел»: на серверах могли остаться его части, и «Удалить каскад» сначала снимет их. На странице каскада видны службы на каждом сервере, каждый участок со своим состоянием и задержкой (рукопожатие), задержка всех участков вместе и история проверок по участкам; каскад в целом — по худшему участку, выходной IP — адрес последнего сервера. Панель проверяет каждую связь раз в минуту с сервера, на котором она начинается, а «Проверить сейчас» — сразу. Если конфиг сервера каскада потом поменяли так, что связь надо пересобрать, она помечается «устарел»: нажмите «Обновить» — панель развернёт заново только устаревшие связи. «Снять связь» убирает всё, что поставил каскад, от входа к выходу, а остальной конфиг серверов не трогает. Если сервер каскада пропал насовсем (VPS удалён или заблокирован), «Удалить каскад» не сможет к нему подключиться и ничего не изменит, а страница каскада скажет, какой сервер не ответил. Тогда владелец или администратор может нажать «Удалить, не дожидаясь недоступного сервера»: с серверов, которые отвечают, панель снимет всё, что поставил каскад, как при обычном удалении (со входа и промежуточных серверов — outbound `cascade` и службу связи с её конфигом, иначе их клиенты остались бы без интернета; с промежуточных и выхода — пользователя связи), а сервер, который не отвечает, пропустит, пометит «Требует внимания» и допишет в его заметки, что на нём осталось: на входе — служба `hyroute-link-…`, конфиг клиента связи и outbound `cascade`, на выходе — пользователь `link-…`, на промежуточном — и то и другое (сервер с общим паролем пользователя связи не хранит). Подтверждение заранее перечисляет, что останется. Так можно удалить каскад без любого его сервера. Затем каскад и пароли связи удаляются, и его серверы можно ставить в другие каскады или удалить. Такое удаление записывается в журнал аудита. «Сохранить как шаблон» сохраняет параметры связи и правила входа в файл — без серверов и паролей. Заметки каскада в файл не попадают (можно дать ему описание), как и адрес проверки и DNS входа, если они указывают на серверы этого каскада или в локальную сеть. После создания каскада из шаблона с правилами для входа его страница предложит применить их с проверкой и diff, до или после развёртывания связи. «Проверить правило по каскаду» на странице каскада показывает, куда уйдёт домен или IP: какое правило сработает на входе, а если оно отправляет соединение в каскад (`cascade`) — какое на следующем сервере, и так до сервера, с которого соединение уйдёт в интернет («Уйдёт в интернет с «Выход» через «direct»») или который его отклонит. Это полезно и для каскада из двух серверов: то, что вход отправил в каскад, выход может отправить своими правилами в другой outbound или отклонить.

**Маршрутизация.** Кнопка «Маршрутизация» в блоке конфига сервера. Правила Hysteria показаны таблицей: куда идёт соединение (outbound) в зависимости от адреса — домен, домен и поддомены, шаблон, категория сайтов geosite, IP, подсеть, страна geoip — протокола и порта, а при желании с подменой адреса. Правила срабатывают сверху вниз: первое подошедшее решает, а что не подошло ни одному, уходит в первый outbound. Порядок меняется перетаскиванием или стрелками, группа целиком — стрелками у её заголовка; правила можно выключать, объединять в сворачиваемые группы, искать и фильтровать; выделенным — включить, выключить, дублировать, перенести в группу, сменить outbound или удалить. Каждую правку панель проверяет так же, как Hysteria: ошибки и подсказки видны у правила — например, правило не сработает, потому что выше есть более общее, или домен записан в punycode. Над таблицей — проблемы всего набора; если клиентам открыты адреса самого сервера и его локальных сетей, кнопка «Добавить в начало» закрывает их правилами `reject`. Рядом — outbounds (напрямую, SOCKS5, HTTP; пароли скрыты, outbound каскада заблокирован) и DNS сервера. На входе каскада с правилами нужен DNS over HTTPS или TLS: иначе провайдер входа видит, какие сайты открывают клиенты. «Проверить правило» показывает, какое правило сработает для домена или IP (на входе и промежуточном сервере каскада, если правило отправляет соединение в каскад, — и что с ним сделают следующие серверы); перед применением видно, у каких адресов меняется маршрут (переименование outbound маршрут не меняет, а новый outbound со старым именем — меняет), и diff конфига. «Из шаблона» и «Импорт» добавляют набор правил в начало, в конец или вместо; DNS из шаблона или файла заменяет DNS сервера, только если отмечено «Заменить DNS сервера» (для импортированного файла по умолчанию не отмечено). «Экспорт» сохраняет правила сервера (JSON без паролей или текстом; системный DNS в файл не пишется); правила из `acl.file` панель для этого читает с сервера. Если правила сервера лежат в файле (`acl.file`), их можно посмотреть и перенести в конфиг; сравнить маршруты адресов с правилами файла панель не может, эта проверка появится, когда правила будут в конфиге; предупреждение о DNS без шифрования на входе каскада видно и для таких правил.

**По сервисам.** Вкладка «По сервисам» в маршрутизации — популярные сервисы (видео и музыка, мессенджеры, соцсети, нейросети, игры, российские сервисы, банки и госуслуги, работа) с переключателем «не трогать / напрямую / через выход / блок». «Через выход» — outbound `cascade`, трафик уходит в интернет с выхода каскада; он есть только на входе развёрнутого каскада. На обычном сервере вместо него можно выбрать свой outbound сервера (например, SOCKS5-прокси). Сервис — это категории баз geo (geosite, а у Telegram, Netflix и X ещё и geoip), поэтому вкладка показывает только сервисы, чьи категории есть в базах geo панели: без баз она пуста, скрытые сервисы перечислены внизу. Если сервер читает свои базы, а не те, что ставит панель, вкладка предупредит: таких категорий в них может не оказаться. Каждое переключение собирает правила в одну группу «По сервисам»: сначала правила по доменам, потом по адресам (geoip), чтобы домен одного сервиса не забрало правило по адресам другого; сервис, чьи домены входят и в категорию другого (Кинопоиск — в Яндекс, ВКонтакте — в Mail.ru), стоит раньше него. Новая группа встаёт после блока локальных сетей (или первой, если его нет); её можно перенести стрелками у заголовка группы на вкладке «Правила», и конструктор оставит её там. Остальные правила он не трогает. На вкладке «Правила» группа видна как любая другая; если поменять там outbound всех правил сервиса, конструктор прочтёт это как выбор. Если группу изменили иначе (своё правило внутри, правило выключено, переставлено или с другим комментарием), вкладка скажет, что изменилось, и перед первой сборкой спросит, перезаписать ли группу. Перед применением — та же проверка, «у каких адресов меняется маршрут» (для сервисов панель сама пробует их домены, например youtube.com) и diff, что после любой правки. С правилами в файле (`acl.file`) конструктор не работает: сначала перенесите их в конфиг.

**Правила.** Страница «Правила» — наборы правил: встроенные «Блок локальных сетей», «Блок рекламы», «RU напрямую» и пресеты с разделом ACL. Набор можно поставить на сервер (в начало, в конец или вместо его правил — с проверкой и diff), сохранить в файл и загрузить из файла: экспорта HyRoute или текста ACL Hysteria.

**Базы geo.** Правила `geoip:` и `geosite:` берут списки из баз `geoip.dat` и `geosite.dat` (Loyalsoldier). Без настройки Hysteria качает их при старте с cdn.jsdelivr.net и не запустится, если CDN недоступен — панель предупредит об этом в маршрутизации. Скачайте базы в панель (они нужны и для подсказок категорий и проверки правил; если в конфиге сервера указаны свои базы не из `/etc/hysteria/geo`, имена категорий в его правилах не проверяются), затем поставьте их на сервер: панель кладёт файлы в `/etc/hysteria/geo`, прописывает их в конфиг, перезапускает Hysteria и проверяет; если она не заработала, возвращает прежние файлы. Сервер скачивает базы сам, а если не может — их заливает controller; можно и через другой сервер. Раз в неделю панель ищет новый релиз и обновляет базы на серверах, где их ставила она (`-geo-interval`, `0` — не обновлять); неудачное обновление на сервере не повторяется до перезапуска controller.

**Система.** Карточка «Система» на странице сервера по кнопке «Проверить» читает настройки ядра: буферы UDP для QUIC и алгоритм TCP (BBR с очередью fq). Отмеченное записывается в `/etc/sysctl.d/90-hyroute.conf` и применяется сразу, без перезапуска Hysteria; если ядро не примет значения, вернутся прежний файл и прежние значения. Повторное применение ничего не меняет, а то, чего ядро не умеет (например, BBR без модуля `tcp_bbr`), не предлагается. Карточка разделяет три разных механизма: BBR ядра — для TCP самого сервера; алгоритм QUIC в Hysteria (`congestion` в конфиге) — между клиентом и сервером; Brutal — скорость, которую указал клиент, в пределах `bandwidth` сервера. Последние два меняются в конфиге.

**История конфига.** Кнопка «История» на странице сервера показывает все версии конфига: откуда каждая взялась (развёртывание, импорт, правка, возврат), кто и когда её сделал. Нажмите на версию, чтобы увидеть её конфиг и что изменится, если к ней вернуться (пароли не показываются, только какие из них другие). «Вернуть эту версию» применяет её так же, как правку: копия, перезапуск, проверка, а если Hysteria не заработает — остаётся текущий конфиг. Возврат не стирает историю, а добавляет в неё новую версию. Роль «только чтение» видит список версий, но не их содержимое.

**Ссылки для клиентов.** Карточка «Подключение клиентов» → «Показать ссылку и QR». Две формы ссылки: официальная (все порты в адресе — HyRoute, Hysteria, HApp, Incy) и для клиентов, которые разбирают ссылку как обычный URL (первый порт и `mport` — v2rayN и похожие). Есть QR-код и `config.yaml` для клиента Hysteria. При нескольких пользователях над ссылкой указано, чья она, а выбор другого пользователя в списке показывает уже его ссылку. В HyRoute ссылка вставляется на вкладке «Серверы» в поле «Сервер». Если на сервере включён mimic, карточка предупредит: ссылка и QR-код его не передают, такому клиенту нужен `config.yaml` (HyRoute mimic не поддерживает). Каждый показ ссылки записывается в журнал аудита.

**Журнал.** Страница «Журнал»: записи controller, журналы заданий всех серверов и журнал Hysteria выбранного сервера, с фильтрами по серверу, уровню и тексту; у владельца и администраторов — ещё вкладка «Аудит» (см. «Пользователи и журнал аудита»). Из записей controller хранятся последние 2000 того же уровня, что `-log-level`, и выше; с `-log-level debug` в них видны и запросы к API. Ошибки самого HTTP-сервера (например, TLS-рукопожатия сканеров интернета) пишутся только в stderr (journald), чтобы не вытеснять записи controller.

**Развёртывания.** Каждое действие с сервером — задание с шагами и журналом. Одновременно на сервере выполняется одно задание. Пока оно идёт, сервер нельзя удалить, а его адрес, пользователя SSH и пароль или ключ — изменить: заданию и его откату нужно подключение (название и заметки менять можно). Если controller перезапустился посреди задания, после запуска оно сверяет состояние сервера и продолжает или откатывается. Упавшее задание можно повторить.

## Диагностический пакет

Если что-то не работает и нужно спросить мейнтейнера, соберите диагностический пакет: ZIP, который можно приложить к issue. В нём:

- версии программы и схемы базы, система, на которой работает панель;
- настройки панели без путей и секретов, версии мастер-ключа, релиз баз geo, число копий базы;
- серверы: состояние, установка Hysteria (версия, служба, брандмауэр), ОС и проверки из последней проверки готовности, последние 20 проверок здоровья и последний замер нагрузки;
- сводки текущих конфигов (способ входа, обфускация, маскировка, TLS, скорость, outbounds, число правил и пользователей) и проверки правил маршрутизации;
- каскады: узлы, связи, их состояние и последние проверки;
- последние задания (по умолчанию 20) с шагами, ошибками и параметрами и журнал каждого из них;
- последние записи журнала панели — только в пакете из панели.

**Как пакет обезличен.** Пароли, ключи SSH и API, токены, ссылки для клиентов, сертификаты, отпечатки и pinSHA256 в пакет не попадают: на их месте `[REDACTED]`, а сводки конфигов собраны из конфигов со скрытыми секретами. Названия серверов и каскадов, адреса (IPv4, IPv6, имена хостов), домены, SNI, адреса почты и имена пользователей (панели, SSH и клиентов Hysteria) заменены на `server-1`, `chain-1`, `host-1`, `domain-1`, `email-1`, `user-1` и так далее — одно и то же значение одинаково во всех файлах пакета. Таблицы замен в пакете нет. Номер `server-N` идёт по порядку добавления серверов, а поле `id` — номер сервера в панели (тот, что в адресе его страницы): по нему вы сами поймёте, о каком сервере речь. Общие имена (`root`, `localhost`), адреса локальных сетей, публичные DNS и адреса GitHub остаются как есть.

**Из панели:** «Настройки» → «Диагностический пакет» (владелец и администратор). Выберите, журналы скольких последних заданий взять, и нажмите «Собрать пакет»: панель покажет список файлов пакета с размерами, а «Скачать ZIP» соберёт пакет заново и скачает его. Скачивание записывается в аудит.

**Командой:** `hyroute-server diag` на машине панели (от того же пользователя, что и служба) пишет пакет в `hyroute-diag-<время>.zip` текущего каталога, `-out файл` — в указанный файл, `-jobs N` — журналы N последних заданий (до 200). Команда только читает базу и работает при запущенной службе. Журнала панели в таком пакете нет: он хранится в памяти работающей службы.

Перед отправкой пакет можно распаковать и проверить: это текстовые файлы JSON и журналы.

## Безопасность

- Пароли и ключи SSH, пароли Hysteria, сертификаты и конфиги хранятся в базе в зашифрованном виде (AES-256-GCM, мастер-ключ).
- Пароли не попадают ни в журналы, ни в ответы API: журналы Hysteria и заданий проходят через редакцию, которая знает пароли конфигов.
- На серверах панель выполняет только заранее описанные операции, а не произвольные команды. Импорт, статус и журнал работают через исполнитель, который физически не может ничего изменить на сервере.
- Ключ сервера SSH всегда сверяется; незнакомые ключи без подтверждения не принимаются.
- Входы, выходы, действия с пользователями, подтверждения ключей, показы ссылок, запуски заданий, удаления каскада без недоступного сервера, резервные копии и скачивания диагностического пакета записываются в журнал аудита; владелец и администраторы читают его на вкладке «Журнал» → «Аудит».
- Смена или сброс пароля и блокировка пользователя сразу завершают все его сессии, в том числе открытые потоки журналов и заданий.
