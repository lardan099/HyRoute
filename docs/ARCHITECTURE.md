# HyRoute — архитектура

Рабочее имя: **HyRoute**. Настройки лежат в `%APPDATA%\HyRoute\`.
Сверено с документацией Hysteria 2 (Full Client Config, URI Scheme), исходниками `apernet/hysteria` app/v2.12.3 и `basil00/WinDivert` v2.2.2.

## Изменения после ревью (ред. 2)

| Пункт | Решение |
|---|---|
| Tunnel при живом приложении и недоступной Hysteria | **Не Direct.** TCP получает RST, UDP-датаграммы дропаются. Direct работает как обычно. В UI: «Туннель недоступен, N соединений отклонено». Fail-open остаётся только на случай крэша или выхода приложения (§8) |
| Правило брандмауэра | Узнаваемое имя `HyRoute relay (TCP)`, проверка и исправление при **каждом** Connect, удаление деинсталлятором и кнопкой в настройках (§5) |
| Резолв сервера | Системный резолвер (трафик Dnscache никогда не маршрутизируется), при каждом (пере)запуске Hysteria, исключаются **все** A/AAAA-записи (§3) |
| zapret / GoodbyeDPI | Конкретные приоритеты, порядок прохождения пакета и поведение при чужом драйвере WinDivert (§1.1) |
| Бинарники | В репозиторий не коммитятся. `scripts/fetch-deps.ps1` скачивает их в `bin\` и сверяет SHA256, версии и хэши лежат в `deps.json` (§12) |
| Тестовый сервер | Прод не используется. Ссылка на тестовый сервер хранится только локально в `.dev\hy2.uri`, каталог в `.gitignore` |

## 0. Ключевые решения

| Вопрос | Решение |
|---|---|
| Перехват | **WinDivert 2.2.2** (DLL + подписанный `WinDivert64.sys` рядом с exe, драйвер грузится при первом `WinDivertOpen`, отдельный инсталлятор не нужен) |
| Биндинги | Свои, на `windows.NewLazyDLL` (без cgo). Open/RecvEx/SendEx/Shutdown/Close/SetParam/GetParam + `WINDIVERT_ADDRESS`. Только x64: `UINT64`-аргументы передаются одним регистром, сборка под 386 намеренно не компилируется |
| Ядро | `hysteria-windows-amd64.exe` app/v2.12.3, режим `socks5`, дочерний процесс в Job Object |
| Как трафик попадает в SOCKS5 | TCP: «отражение» пакетов (reflect, как в примере WinDivert `streamdump`) в локальный relay-listener. UDP: на уровне пакетов, без listener'а. Датаграммы уходят через SOCKS5 UDP ASSOCIATE, ответы собираются в пакеты и инжектятся обратно |
| Что перехватывается | **Только outbound** (+ снифф DNS-ответов). Входящий трафик Direct-соединений в user space не попадает, поэтому скачивание не просаживается |
| Туннель недоступен | Tunnel-соединения отклоняются (RST/drop), напрямую не уходят. Direct и Block работают как обычно |
| UI | Wails v2 + Svelte + TS, трей через `energye/systray`, single-instance lock |

### Почему WinDivert, а не Windows Packet Filter (ndisapi)
1. **Атрибуция процесса из ядра.** У WinDivert есть слои `SOCKET` и `FLOW` поверх WFP ALE: событие приходит с `ProcessId`, 5-tuple и `EndpointId`. Событие `SOCKET_CONNECT` генерируется на ALE_AUTH_CONNECT, *до* отправки SYN. ndisapi работает на уровне NDIS, PID там нет. ProxiFyre для этого опрашивает таблицы IP Helper, и там неизбежна гонка.
2. **Reinject с разворотом направления.** Outbound-пакет можно переписать и инжектить как inbound. На этом держится прозрачный relay для TCP.
3. **Фильтр в ядре.** Loopback, приватные сети и IP сервера Hysteria отсекаются до user space.
4. **Не нужен инсталлятор драйвера.** ndisapi ставит драйвер через MSI.

Минусы WinDivert: выше накладные расходы на пакет, чем у ndisapi. Их гасят батчинг `RecvEx`/`SendEx` и перехват только outbound. Последний релиз вышел в 2022 году, но версия стабильная. Лицензия LGPLv3, динамическая загрузка DLL допустима.
Общий риск для обоих драйверов: часть античитов (Vanguard, FACEIT, иногда EAC) и AV ругаются на загруженный пакетный драйвер. Описываем это в README.

## 1. Хэндлы WinDivert

Приоритет в WinDivert 2.x: **большее значение видит пакет раньше** (диапазон −30000…30000, 0 — «средний», по умолчанию). Пакет, инжектнутый хэндлом с приоритетом P, дальше видят только хэндлы с приоритетом < P, сам хэндл его повторно не получает.

| # | Слой | Приоритет | Флаги | Фильтр (упрощённо) | Назначение |
|---|---|---|---|---|---|
| H1 | NETWORK | **1000** (1001 при горячей замене; при каждой замене все прежние H1 сразу перестают принимать пакеты и закрываются через 3 с) | — (inline) | `outbound and !loopback and (tcp or udp) and not <exclusions>`<br>`or (inbound and tcp.DstPort == RELAY_PORT)` | Основной: решения, NAT, reflect. Второе условие ловит внешние попытки подключиться к relay, такие пакеты дропаются |
| H2 | NETWORK | 1010 | SNIFF, RECV_ONLY | `!loopback and ((outbound and (udp.DstPort == 53 or (tcp.DstPort == 53 and tcp.PayloadLength > 0))) or (inbound and (udp.SrcPort == 53 or (tcp.SrcPort == 53 and tcp.PayloadLength > 0))))` | Пассивный разбор DNS: исходящие запросы запоминаются, ответ принимается только на увиденный запрос |
| H3 | SOCKET | 1020 | SNIFF, RECV_ONLY | `!loopback and (event == CONNECT or event == BIND or event == CLOSE)` | Атрибуция PID, запись раньше первого пакета |
| H4 | FLOW | 1030 | SNIFF, RECV_ONLY | `!loopback` | ESTABLISHED/DELETED: чистка, длительность соединения |

`<exclusions>` в H1 задаются диапазонами прямо в фильтре: `0/8, 10/8, 127/8, 169.254/16, 172.16/12, 192.168/16, 224/4, 240/4` (включая 255.255.255.255), для IPv6 `::/127, fe80::/10, fc00::/7, ff00::/8`, плюс **все IP сервера Hysteria**. Опционально добавляется `100.64/10` (CGNAT/Tailscale), по умолчанию выключено. IP серверов нормализуются (без zone, без дублей, без адресов из фиксированных диапазонов), их не больше 100 (компилятор фильтров WinDivert вмещает 107), иначе Connect или запуск профиля получает ошибку. Применённый список меняется только после успешного открытия хэндла; `tunnels.Manager` при ошибке откатывает список профиля.
Каждое исключение записывается как `(ipv6 or ip.DstAddr < A or ip.DstAddr > B)` / `(ipv6 or ip.DstAddr != X)` (и симметрично для IPv6). Причины: в языке фильтров WinDivert `not`/`!` применяется только к одиночной проверке, `not (…)` — ошибка разбора (`WinDivertOpen` → 87); а проверка поля, которого у пакета нет (`ip.*` у IPv6-пакета), ложна, поэтому другое семейство пропускается явно. Фильтры проверяются настоящим компилятором и вычислителем WinDivert 2.2.2, собранным под Linux (`tools/wdfilter`, тест `internal/divert/filter_wdfilter_test.go`).

**DNS-политики** (§6.1). Пока включена хоть одна настройка DNS, в H1 диапазоны исключений сгруппированы отдельно и к ним добавлено «или»: `((<диапазоны>) or udp.DstPort == 53 or fragment or tcp.DstPort == 53 or tcp.SrcPort == RELAY)`. Так перехватывается DNS к частным и link-local адресам (роутер), все фрагменты к ним (WinDivert читает порты только в первом фрагменте, решение принимает `Core.dnsHold`) и ответы relay частному адресу, отражённому в него. IP серверов Hysteria и loopback по-прежнему не попадают. Это 4 теста фильтра: 45 постоянных плюс 2 на адрес сервера, со 100 адресами 245 из 256. Без политики фильтр байт в байт прежний; включение и выключение меняют H1 горячей заменой (`Engine.SetDNSCapture`).

Параметры H1: `QUEUE_LENGTH=8192`, `QUEUE_TIME=2000ms`, `QUEUE_SIZE=8MB`. Один читатель `RecvEx` (batch 64) раскладывает пакеты по N воркерам по хэшу 5-tuple, чтобы внутри одного соединения не было переупорядочивания. Каждый воркер сам вызывает `SendEx`. (В PoC один цикл, воркеры появятся на шаге 3.)

### 1.1 Сосуществование с zapret, GoodbyeDPI и другими программами на WinDivert

Проверено по исходникам: `winws` из zapret (`nfq/darkmagic.c`) и GoodbyeDPI (`src/goodbyedpi.c`) открывают свои NETWORK-хэндлы с **приоритетом 0**.

**Порядок прохождения пакета.** H1 стоит выше (1000), поэтому новый outbound-пакет сначала попадает к нам:
- **Direct**: реинжектим без изменений через H1. Дальше пакет идёт к хэндлам с приоритетом < 1000, то есть к zapret/GoodbyeDPI, и обход DPI работает как без нас.
- **Tunnel**: пакет превращается в inbound к локальному relay. Фильтры DPI-обходчиков ловят outbound на 80/443, так что до них он не доходит. Ответы relay (`tcp.SrcPort == RELAY`) мы тоже ловим первыми и разворачиваем в inbound.
- **Трафик Hysteria к серверу** исключён фильтром H1 и идёт мимо нас сразу к zapret. Если в zapret включены фейки для UDP (например, `--wf-udp=443` с fake QUIC) и порт сервера под них попадает, zapret может подмешивать мусорные датаграммы. Hysteria с obfs их отбрасывает, но при проблемах сервер нужно добавить в исключения zapret. Это есть в README.

**Почему не ниже zapret.** Тогда zapret первым видел бы Tunnel-соединения: резал бы ClientHello на сегменты и инжектил фейковые пакеты с намеренно битой контрольной суммой или малым TTL. Эти пакеты шли бы к нам, мы отражали бы их в relay и **пересчитывали контрольную сумму**, превращая фейк в «валидные» данные. Поток в relay был бы испорчен.

**Один движок на машину.** Блокировка единственного экземпляра Wails действует в пределах сеанса Windows, а две копии HyRoute (быстрая смена пользователя, RDP) перехватывали бы трафик друг друга. Поэтому `session.Start` захватывает Global-мьютекс `Global\HyRoute-engine-3f9b2c71` (`engine.LockMachine`), `Stop` его отпускает. Занят другим сеансом → `ErrOtherEngine` («HyRoute уже подключён в другом сеансе Windows…»). Мьютекс создаётся с владельцем BUILTIN\Administrators и DACL только для SYSTEM и администраторов. Объект с этим именем, которым владеет кто-то другой (его может создать любой процесс без прав администратора), не считается чужим HyRoute: подключение идёт без межсеансовой блокировки. Внутри процесса перед мьютексом стоит семафор с ожиданием до 15 с: Connect сразу после отключения ждёт остановки прежнего движка, иначе `ErrStillStopping`.

**Уникальные уровни.** В документации WinDivert: «A packet is only diverted once per priority level». Если два хэндла на одном уровне ловят один и тот же пакет, кто его получит, не определено, и второй может его вообще не увидеть. Поэтому ни один наш хэндл не стоит на 0, и у каждого свой уровень.

**Чужой драйвер WinDivert.** Все программы на WinDivert 2.x используют одну и ту же службу ядра `WinDivert` и устройство `\\.\WinDivert`. Как работает `WinDivertOpen` (dll/windivert.c):
1. Если устройство уже есть (драйвер загружен другой программой), DLL открывает его и **не** грузит наш `.sys`. Проверка версии пропускает любой драйвер с major ≥ 2.
2. Если устройства нет, но служба `WinDivert` уже зарегистрирована, DLL запускает **тот `.sys`, на который указывает служба** (например, `C:\zapret\...\WinDivert64.sys`), а не наш.
3. Иначе регистрирует службу на наш `.sys`, запускает её и сразу помечает на удаление. Драйвер выгружается, когда закроется последний хэндл у всех программ.

Что делает HyRoute:
- Перед открытием читает службу `WinDivert` через SCM: существует ли, запущена ли, её `ImagePath`. Если путь не наш, в лог и UI идёт «Драйвер WinDivert предоставлен другой программой: `<путь>`».
- После открытия читает `WINDIVERT_PARAM_VERSION_MAJOR/MINOR`. Нужна 2.2 или новее. Если загружен 2.0/2.1 (старые сборки GoodbyeDPI/zapret), хэндлы закрываются, а в UI понятная ошибка: какая версия загружена, откуда, и что делать (закрыть ту программу или перезагрузиться). Молча работать на непроверенном драйвере не будем.
- Драйверы WinDivert 1.x (службы `WinDivert1.0`…`WinDivert1.4`, очень старый GoodbyeDPI) — это другое устройство, наши приоритеты на них не действуют, и порядок не определён. Если такая служба запущена, выводим предупреждение.
- Ошибка загрузки `WinDivert.dll` не кэшируется: следующий Connect пробует снова. DLL без нужных экспортов выгружается.
- Коды ошибок `WinDivertOpen` переводятся в сообщения (`internal/divert/errors.go`):

| Код | Причина | Сообщение в UI |
|---|---|---|
| 2 / 3 | нет `.sys` или служба указывает на удалённый файл | нет файла рядом с exe → «переустановите». Служба указывает на чужой отсутствующий файл → «остаток удалённой программы» + кнопка «Удалить устаревшую службу WinDivert» (удаляет только **остановленную** службу) |
| 5 | нет прав | запустить от администратора |
| 87 | фильтр или параметры отклонены | внутренняя ошибка + путь драйвера другой программы, если служба `WinDivert` указывает на него |
| 577 | подпись драйвера не принята | файлы повреждены или политика запрещает сторонние драйверы |
| 654 | несовместимый загруженный драйвер | закрыть программы на WinDivert или перезагрузиться, с указанием пути |
| 1072 | драйвер выгружается | повторить через пару секунд (1 автоповтор через 2 с, только для первого хэндла в `Engine.Start`) |
| 1275 | драйвер заблокирован | антивирус, античит или ВМ без поддержки драйверов |
| 1753 | отключена служба BFE | включить Base Filtering Engine |

## 2. Атрибуция процесса

```
H3 SOCKET_CONNECT/BIND  ─┐
H4 FLOW_ESTABLISHED      ├─► ConnTable
                         │     key5: (proto, localIP, localPort, remoteIP, remotePort) → {pid, endpointId, ts}
                         │     port: (proto, localPort, remote)                        → {pid, endpointId}   (local IP не указан в событии)
                         │     bind: (proto, localPort)                                 → {pid, endpointId}
                         │     byEndpoint: endpointId → set(key)
H3 SOCKET_CLOSE ─────────┤  удаление всех ключей endpoint'а (только если ключ ещё принадлежит ему)
H4 FLOW_DELETED ─────────┘  финал статистики в «Соединениях» и закрытие NAT-записи (ConnTable не трогается)
```

Каждая запись истекает отдельно, через 30 мин без обновления; `bind` живёт, пока его сокет даёт события. Таблица ограничена 32768 записями, при переполнении вытесняются дольше всех не обновлявшиеся. После промаха поиск идёт дальше: `bind`, pending queue, IP Helper.

Поиск PID для нового пакета, по убыванию точности:
1. точный `key5`;
2. `(proto, localPort, remote)`, затем `bind` по (proto, localPort). Для UDP-сокетов без connect это основной путь;
3. **pending queue**: пакет паркуется максимум на **100 мс**, ожидая события H3/H4 (таблица будит ожидающих при каждой вставке, без поллинга). Через **20 мс** делается синхронный `GetExtendedTcpTable/GetExtendedUdpTable (OWNER_PID)`;
4. таймаут: процесс `Unknown`. Правила только по приложению не сработают, доменные и default сработают.

Pending queue ограничена: 512 пакетов и 128 flow (в PoC: 128 flow). При переполнении владелец сразу синхронно запрашивается у IP Helper (attrib `iphelper`); только если его там нет, пакет решается как `Unknown` (attrib `pending-full`), трафик не блокируется. Повторные SYN одного flow в очереди сливаются.

**Снимок таблицы TCP.** Кроме точечного `LookupTCPOwner` есть снимок `attrib.ReadTCPTable` / `TCPSnapshot`: `GetExtendedTcpTable` обеих семей адресов, строки LISTEN включены, 4in6-строки из IPv6-таблицы нормализуются так же, как ключи поиска. По нему движок определяет владельца соединений без состояния и серверную сторону входящих соединений (§4, «Смена правил»).

**PID → процесс.** `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, затем `QueryFullProcessImageNameW` и `GetProcessTimes`. Запись кэша ключуется парой `(pid, creationTime)`: при каждом обращении время создания процесса под этим PID сверяется заново (`OpenProcess` + `GetProcessTimes`), и если PID занял другой процесс, запись запрашивается заново вместе с цепочкой предков. Запись завершившегося процесса отдаётся, пока PID никто не занял; раз в 5 с такие записи удаляются.

**Дерево процессов** для правил с наследованием. Раз в 1 с снимается `NtQuerySystemInformation(SystemProcessInformation)`: в отличие от `CreateToolhelp32Snapshot` он отдаёт `CreateTime` каждого процесса, и PID, переиспользованный процессом с тем же родителем, не выглядит прежним процессом. Toolhelp остаётся запасным вариантом, если запрос не удался (без ctime). Есть и on-demand запрос при промахе. Для каждого `(pid, ctime)` запоминается цепочка предков: (родительский PID, ctime родителя < ctime ребёнка) + путь. Цепочка переживает смерть лаунчера: лаунчер запустил игру и закрылся, а правило лаунчера с «наследовать» продолжает действовать на игру. Глубина до 8.

**Dnscache.** PID службы берётся через `QueryServiceStatusEx("Dnscache")`. Его трафик на 53 порт и TCP на 443/853 (DoH/DoT) к DNS-серверам сетевых адаптеров (`GetAdaptersAddresses` в `internal/sysdns`, тот же список берёт kill switch, §8.1; список перечитывается не чаще раза в 5 с при промахе) считается системным: Direct, в правила не идёт. Остальной TCP 443 этого PID решают правила: Dnscache может делить svchost с другими службами. DNS-трафик остальных процессов (например, встроенный резолвер Chrome) маршрутизируется как обычный, и в cache он попадает в любом случае.

## 3. Обязательные исключения

Приоритет у них выше любых правил.

| Что | Как |
|---|---|
| Loopback, RFC1918, link-local, multicast, broadcast | В фильтре H1, в user space не попадает |
| IP сервера Hysteria (все порты, что покрывает port hopping) | В фильтре H1 исключается **весь IP**, а не порты. Список — все A/AAAA-записи хоста |
| Процесс Hysteria | `hysteria.exe`, чей родитель — HyRoute: его flow решаются как Direct («exclusion: hysteria»). Remote IP его сокетов в исключения фильтра не добавляются |
| Наш процесс | SOCKS5 к Hysteria идёт через loopback и уже исключён. Любой flow с PID HyRoute решается как Direct («exclusion: self»). Direct-upstream relay'я (SNIFF → Direct) исключается так же, по PID: событие `SOCKET_CONNECT` приходит раньше SYN. Идея с `selfPorts` через `bind` в `net.Dialer.Control` отброшена: на Windows Go сам делает `bind` перед `ConnectEx`, и повторный `bind` падает с WSAEINVAL |
| Служебный трафик relay | Пакеты с `tcp.SrcPort == RELAY_PORT` обрабатываются только NAT'ом (обратное отражение), правила к ним не применяются |
| DNS HyRoute и его Hysteria; имена серверов Hysteria, проверки Windows, хост своего прямого DNS-сервера, хосты, к которым HyRoute обращается сам (2 мин) | DNS-политики (§6.1) такие запросы не трогают: свой трафик по PID (`Core.own`), имена — по имени, кто бы ни спрашивал (служба DNS-клиента спрашивает за всех). DNS к IP серверов не перехватывается вовсе: адреса серверов исключены из H1 |

**Резолв сервера.** Режим «pin IP» включён по умолчанию.
- Резолв идёт через системный резолвер (Go на Windows → `GetAddrInfoW` → служба Dnscache). DNS-трафик Dnscache — обязательное исключение, в туннель он не попадает никогда, поэтому курицы и яйца нет: резолв сервера работает и когда туннель недоступен.
- Резолвим при **каждом** запуске и перезапуске Hysteria. Порядок: резолв → обновление исключения в фильтре (синхронно) → запись YAML → запуск процесса. Первый пакет Hysteria уходит, когда исключение уже действует.
- Исключаются **все** полученные адреса (A и AAAA). Hysteria получает один из них: `server: <IP>:<ports>`, предпочтительно IPv4, а `tls.sni` равен домену, если SNI не задан явно. Если запуск с закреплённым адресом завершился, не подключившись (кроме занятого локального порта и ошибки конфигурации), следующий запуск закрепляет следующий адрес набора: сначала остальные IPv4, потом IPv6, затем снова по кругу. После успешного подключения выбор начинается с первого IPv4.
- Раз в 5 минут, пока Hysteria работает, хост резолвится заново. Если набор адресов изменился, сначала фильтр получает объединение старого и нового наборов, потом, если закреплённого IP в новом наборе нет, Hysteria перезапускается. При перезапуске исключение сужается до нового набора. Без «Резолвить адрес в HyRoute» исключение за время жизни процесса только растёт (объединение всех адресов, увиденных при перерезолвах) и сужается до нового набора только при перезапуске Hysteria.

Фильтр обновляется без разрыва: открывается новый H1 на другом уровне (1000 ↔ 1001), старый получает `WinDivertShutdown(RECV)`, дренирует очередь и закрывается. При замене на уровень ниже принимающего инжект приостанавливается (`swapMu`) от открытия нового хэндла до переключения `e.send`, дальше инжектит только новейший хэндл. NAT-состояние живёт в памяти движка, а не в хэндле, поэтому соединения не рвутся.

## 4. Где принимается решение

```
новый flow (TCP SYN без NAT-записи / первый UDP-пакет 5-tuple)
 │
 ├─ исключение? ───────────────────────────────► pass (Direct, «system»)
 ├─ атрибуция (pending ≤100 мс)
 ├─ EvaluateSites(rules, proc, proto, dstIP, dstPort, dnsSites(dstIP))
 │     └─ результат: Final(action, rule, domainSrc)  |  NeedsDomain
 │
 ├─ Final:
 │    Direct ─► reinject как есть. Relay не участвует, в NAT только запись для UI
 │    Block  ─► RST (TCP), чтобы приложение быстро упало; UDP молча отбрасывается
 │              (ICMP unreachable не шлём: Windows отдаёт его как WSAECONNRESET всему
 │              UDP-сокету, и блок одного адреса ломал бы программе остальные направления)
 │    Tunnel ─► туннель недоступен (Hysteria не Connected или relay не работает)
 │                 → RST (TCP) / drop (UDP), счётчик «отклонено» (общий и профиля), напрямую НЕ идёт;
 │                   UDP-поток виден в «Соединениях» как «dropped: tunnel unavailable»,
 │                   а когда туннель поднимется, его исход станет «tunneled»
 │              IPv6 и «блокировать IPv6 в туннеле» → RST (приложение уйдёт на v4)
 │              TCP → relay в режиме NO-SNIFF (SOCKS5 CONNECT на IP сразу)
 │              UDP → UDP-сессия SOCKS5 ASSOCIATE (на пакетах, без listener'а)
 │                    сервер запретил UDP (udpEnabled=false) → drop
 │
 └─ NeedsDomain:
      TCP → IPv6, «блокировать IPv6 в туннеле» и хотя бы при одном домене соединение
            ушло бы в туннель → RST сразу, на SYN, без sniff: после рукопожатия RST уже
            не переводит приложение на IPv4 («IPv6 blocked for tunnel (domain unknown)»);
            если DNS-кэш знает для адреса только сайты, которые идут мимо туннеля, или у машины
            нет IPv4-маршрута в интернет (IPv6-only сеть, NAT64 без CLAT; `GetBestInterfaceEx`,
            не чаще раза в 5 с), SYN не сбрасывается
            иначе relay в режиме SNIFF (§5); relay не работает → решение по DNS cache/default,
            и если оно Tunnel, то RST
      UDP → dst port 443 и «блокировать QUIC» → drop (браузер уйдёт на TCP, там будет SNI)
            иначе → решение без домена (доменные правила считаются несовпавшими)
```

**Evaluate с трёхзначной логикой домена.** Правила обходятся по порядку, первое совпадение выигрывает. Приложение и протокол известны точно. Условие по домену даёт `Yes/No/Unknown`:
- в DNS cache для IP ровно один набор имён, и **все** имена дают одинаковый итог → `Final` (domainSrc = DNS). Исключение — настройка «Точное определение домена для веба» (`exactWebDomains`, по умолчанию включена): для TCP на 80/443/8080/8443 и для QUIC (UDP/443 при включённой блокировке QUIC) DNS cache на уровне пакетов не используется;
- имена дают разные итоги (CDN) или IP в cache нет → считаются обе ветви доменного условия. Если все ветви сходятся к одному действию, получаем `Final`, иначе `NeedsDomain`.

Отсюда следует гарантия из ТЗ: в relay попадают только соединения, итог которых зависит от ещё неизвестного домена, и Tunnel. Tunnel в relay неизбежен, потому что SOCKS5 требует терминировать TCP. Direct и Block не трогают relay никогда, и падение relay их не задевает.

**Смена правил.** Скомпилированный набор правил подменяется атомарно (`atomic.Pointer`). Решение фиксируется в flow-записи при первом пакете. Соединения со своей записью после смены правил остаются на прежнем маршруте, а новые получают новые правила. Hysteria при этом не перезапускается. Исключения: UDP-поток, профиль которого больше не может его нести (остановлен или недоступен), заново решается по текущим правилам (включая fallback), не чаще раза в секунду; чистый SYN на 4-tuple закрытого reflect-соединения получает новое решение.

Не-SYN пакет TCP-соединения, о котором у движка нет состояния (открыто до старта, в том числе через туннель прежнего движка до крэша или отказа), решается по правилам как новое. Direct-поток, чья запись в `tcp` истекла (через минуту после FIN или RST приложения, после 2 ч простоя), сюда не попадает: `Maintain` переносит его ключ в `untracked` с прежним решением, так что хвост потока или долго молчавшая SSH-сессия не решаются заново без домена или владельца. Владелец берётся из SOCKET/FLOW-событий или из снимка таблицы TCP IP Helper (§2): `GetExtendedTcpTable` для обеих семей адресов, не чаще раза в секунду, один снимок на все такие соединения. Соединение, которого нет в снимке (SYN ушёл до старта, а в таблице оно появилось после чтения), ищется в новом снимке, если текущему больше 100 мс; только потом владелец считается неизвестным. Сначала обязательные исключения (HyRoute, его hysteria, системный DNS). Домен берётся только из DNS cache: посреди потока снифать нечего, а при «Точном определении домена для веба» веб-порты решаются без домена. DNS cache каждой сессии начинается пустым. Если итог зависит от домена, решение принимается без него. С `Options.ResetUnknownDomain` Direct без домена заменяется сбросом (правило «… (domain unknown, reset)»): контроллер ставит опцию при автоматическом переподключении после отказа движка, при переподключении пользователя после такого отказа (пока не было «Отключить») и при подключении поверх блокировки kill switch (после крэша, обновления, `Reconnect`), когда соединение могло идти через туннель и сброс прежнего движка мог не дойти. Серверная сторона входящего соединения (исходящий SYN-ACK или сокет LISTEN на этом порту, на том же адресе или wildcard любой семьи, принадлежащий владельцу соединения) не маршрутизируется и проходит. Слушатель другого процесса не в счёт: `[::]` с IPV6_V6ONLY (по умолчанию в Windows) не занимает IPv4-порт, и клиент может получить его как эфемерный. Direct проходит как есть. Tunnel и Block: приложению инжектится RST от имени удалённой стороны (seq = ACK пакета), пакет дропается, дальнейшие сегменты получают RST без нового решения (`gone`), собственный RST приложения глушится. Решения запоминаются по 4-tuple: Direct в `untracked` (2 ч с последнего пакета, до 16384, при переполнении вытесняется произвольная запись), Tunnel/Block в `gone` (2 ч, до 16384). FLOW_DELETED и новый SYN на том же 4-tuple их снимают. Входящие пакеты неизвестных соединений не трогаются. Поэтому при подключении уже открытые соединения, которые правила отправляют в туннель или блокируют, один раз сбрасываются и открываются заново через движок, а Direct по правилам для программ и адресов продолжают работать. Direct по доменному правилу при туннеле по умолчанию решается без домена и тоже один раз сбрасывается. В журнал пишутся первые 20 сбросов сессии, дальше каждый сотый (поле `count` — счётчик `UntrackedReset`).

## 5. NAT и relay

### TCP reflect
```
Приложение:  L:lp → R:rp   (outbound, пойман H1)
  переписано: R:lp → L:RELAY  и инжектится как INBOUND на том же IfIdx
Relay accept видит peer = R:lp → по NAT[(R, lp)] получает оригинал {L:lp → R:rp, pid, решение}
Relay отвечает: L:RELAY → R:lp  (outbound, пойман H1 по tcp.SrcPort == RELAY)
  переписано: R:rp → L:lp  и инжектится как INBOUND
```
- NAT хранит два индекса: `app flow → entry` для прямого направления и `(R, lp) → entry` для accept и обратного направления. Запись закрывается по RST, по FIN в обе стороны, по закрытию relay-соединения и по FLOW_DELETED, и удаляется после грейса 30 с (хвостовые ACK/FIN). Записи без пакетов дольше 2 ч удаляются как потерянные.
- **Коллизия ключа** `(R, lp)`: одинаковые R и lp при разных rp. Windows умеет делить локальный порт между разными удалёнными endpoint'ами. Такой второй flow в relay не отражается и решается на уровне пакетов: NeedsDomain → DNS/default, Tunnel → RST (не Direct). Случай крайне редкий, пишется в лог.
- Checksum пересчитывается всегда (свой код в `internal/packet`), в адресе выставляются флаги «checksum valid», чтобы драйвер не считал их offload'ом.
- Relay слушает на `0.0.0.0:RELAY` и `[::]:RELAY` (IPV6_V6ONLY). Порт случайный из 49152–65535, свободный на обоих семействах. Внешние подключения отсекаются дважды: фильтр H1 дропает inbound на RELAY, который не был инжектнут нами (свои инжекты тот же хэндл не видит), а при accept проверяется наличие NAT-записи (нет записи → RST).
- **Windows Firewall:** инжектнутый inbound SYN проходит ALE_AUTH_RECV_ACCEPT, и без правила брандмауэр покажет запрос или заблокирует. Правило:
  - имя `HyRoute relay (TCP)`, входящее, разрешить, программа = наш exe, TCP, локальные порты 49152–65535, все профили;
  - проверяется при **каждом** Connect: `netsh advfirewall firewall show rule name=…`. Нет правила — `add rule`. Есть — `set rule … new <параметры>`, что чинит правило, если exe переехал или пользователь его выключил или отредактировал. Вывод `netsh` локализован, поэтому смотрим только на коды возврата;
  - удаляется деинсталлятором и кнопкой «Удалить правило брандмауэра» в настройках (в PoC: `hyroute-poc.exe -remove-firewall-rule`);
  - если служба брандмауэра отключена, `netsh` вернёт ошибку. Это предупреждение, а не отказ: без брандмауэра правило не нужно.

### Relay: режимы
- **NO-SNIFF** (Tunnel решён по пакетам): если туннель недоступен → RST. Иначе `SOCKS5 CONNECT <IP>:rp`, затем двунаправленный copy с half-close. Ошибка CONNECT → RST. Ошибка (не EOF) в любом направлении сбрасывает обе стороны RST. Сторона приложения закрывается (FIN) только после того, как приложение подтвердило все отправленные ему байты и открыло окно (`SIO_TCP_INFO`). Пока этого нет, соединение остаётся в relay, и Abort (Disconnect, переподключение, отказ движка) сбрасывает его RST: FIN, поставленный через shutdown, Windows отправит и после `SO_LINGER 0`, уже к реальному R:lp. Приложение, которое остановило чтение (пейджер, пауза загрузки), ждём, пока соединение живо, как и простаивающее: после паузы оно получит хвост и конец потока. Ожидание прекращается, если приложение закрыло или сбросило сокет. Через 10 с без изменений оно прекращается, только когда счётчики несогласованы (окно открыто, в полёте ничего нет, а байты не подтверждены): тогда в журнал пишется предупреждение и ставится обычный FIN.
- **SNIFF**: соединение принимается, upstream не открыт. Первые данные читаются с дедлайном `sniffTimeout` (по умолчанию 800 мс, настраивается):
  - TLS: сборка записей handshake (ClientHello часто больше MSS, в Chrome с Kyber около 1.8 КБ) до полного ClientHello или 16 КБ, затем извлечение SNI (ext 0). SNI берётся и при расширении ECH (0xfe0d): Chrome и Firefox шлют GREASE ECH каждому сайту без ECH-конфига, и внешний SNI — это сам сайт. Исключение — известное публичное имя ECH (cloudflare-ech.com и `public_name` из ECH-конфигов HTTPS/SVCB-ответов, увиденных в DNS, не дольше 1 ч), если кэш DNS не держит это же имя как сайт для этого IP. Тогда сайт скрыт: решают имена из кэша DNS для этого IP, а если они не дают однозначного маршрута, домен неизвестен (правила по IP, приложению или «Всё остальное»). Правило на само публичное имя не срабатывает, туннель подключается по IP. Если SNI нет, имя неизвестно;
  - HTTP: строка запроса и `Host:` до `\r\n\r\n`, максимум 8 КБ;
  - по имени (источник SNI/Host) вызывается `Evaluate(domain=exact)`. Если имени нет, решение по DNS cache (если имена сходятся), иначе «без домена»: доменные правила считаются несовпавшими, и срабатывает первое подходящее правило без домена или default;
  - Tunnel → SOCKS5 CONNECT (туннель недоступен → RST). `ATYP=DOMAIN` только если имя пришло из SNI/Host и включён «Prefer remote DNS», иначе исходный IP. Запросы к forward-прокси (CONNECT или absolute-form) идут на IP прокси: Host там только выбирает маршрут. Direct → dial `R:rp` с исходного IP приложения (bind на `Flow.Src`, порт 0); адреса больше нет — RST. Block → RST (`SetLinger(0)`);
  - буфер пишется в upstream без изменений, дальше идёт splice.
  - Для server-first протоколов (SSH 22, SMTP 25/587, FTP 21, POP/IMAP 110/143, MySQL 3306…) по списку портов ожидание сокращается до 150 мс: там клиент молчит до баннера.

### UDP
- Сессия ключуется по `(L, lp)` (сокет приложения). В ней одна ассоциация SOCKS5 UDP ASSOCIATE. Hysteria привязывает ассоциацию к первому отправителю, а разные назначения мультиплексирует. Решение принимается по каждому 5-tuple: Tunnel-назначения идут в ассоциацию, остальные по своему решению.
- Ответ от Hysteria приходит с адресом `from`. Из него собирается пакет IPv4/IPv6+UDP `from → L:lp` и инжектится inbound на IfIdx исходного пакета.
- Таймаут простоя 60 с (DNS 10 с), затем ассоциация закрывается.
- Предел размера. Hysteria несёт датаграмму, только если она помещается в два буфера по 4096 байт: буфер SOCKS5 UDP (`app/internal/socks5` `udpBufferSize`, с заголовком SOCKS5) и сообщение QUIC (`core/internal/protocol` `MaxUDPSize`: 8 байт + varint + «host:port» + данные) — на клиенте и на сервере. Больше второго — молча теряется внутри Hysteria. Больше первого — хуже: `ReadFromUDP` в `udpServer` падает (WSAEMSGSIZE), и Hysteria закрывает всю ассоциацию сокета. Поэтому предел жёсткий: `socks5.MaxUDPPayload` считает его по тем же байтам адреса, что уходят в Hysteria (IPv4-mapped разворачивается, зона отбрасывается), и никогда не завышает: 4040–4078 байт (IPv4 не меньше 4066). Больше — отбрасывается в `udpSend` (`UDPTooBig`, у потока `tooBig`; если через поток не прошло ничего, «Соединения» показывают исход `dropped: larger than Hysteria carries`). Это не ошибка сервера: отказы профиля не считаются. Настройкой не меняется, другие режимы клиента (`udpForwarding`, `tun`) упираются в тот же буфер. Любой, кто шлёт SOCKS5 UDP в Hysteria, обязан проверять этот предел.
- Ответы собираются в один пакет и инжектятся inbound, даже если он больше MTU (так было и в 1.0.0: ответы до ~4,1 КБ): так WinDivert сам реинжектит собранные входящие пакеты (inbound-классификатор пропускает фрагменты и ловит собранный пакет), путь приёма MTU не проверяет. Разбиение входящих ответов на фрагменты, о котором просил владелец, поэтому не включено: `packet.FragmentIP` написан и покрыт тестами, но не вызывается, и включается в `udpSession.read`, только если ручная проверка перед выпуском (`tools/udpprobe`) покажет, что Windows не принимает такие пакеты.

### IP-фрагменты и нераспознанные пакеты
- Фильтр H1 ловит `(tcp or udp or fragment)`: фрагменты без транспортного заголовка не подходят ни под `tcp`, ни под `udp`, и раньше уходили мимо движка напрямую (проверено вычислителем фильтров WinDivert 2.2.2, `tools/wdfilter`). Фрагменты других протоколов (ICMP, ESP, GRE, AH) проходят без изменений.
- UDP-фрагменты IPv4 (с опциями тоже) и IPv6 с заголовком фрагмента сразу после основного собираются (`packet.Assembly`, ключ — адреса, протокол, ID). Фрагмент со смещением 0 всегда начинает новую датаграмму и заменяет прежнее решение по ключу (ID IPv4 16-битный и повторяется). Он смотрит на существующий поток: Direct — фрагменты проходят как есть (байты считаются по длине из UDP-заголовка, поток не истекает), решение живёт 2 с; Block — отбрасываются; Tunnel — датаграмма собирается, а если по длине из UDP-заголовка она больше предела Hysteria и туннель потока доступен, отбрасывается сразу (туннель недоступен — собирается и проходит `udpOut`, как целая: перевыбор сервера, затем проверки `udpSend`). Нового потока нет — датаграмма собирается целиком и решается обычным путём, как несфрагментированная (владелец, ожидание SOCKET-события, правила); если итог Direct, уходят исходные фрагменты с исходными адресами, без изменений (`Packet.Orig`, `injectDirect`; в очереди ожидания владельца — тоже, с лимитом 8 МБ). Фрагменты до первого ждут его до 5 с, после чего датаграмма собирается целиком и только потом маршрутизируется. Неполные через 5 с, перекрывающиеся, с длиной UDP не по размеру и ошибочные датаграммы отбрасываются целиком (`FragIncomplete`); память ограничена: 256 собираемых датаграмм, 4 МБ, 128 фрагментов на датаграмму; решения (до 16384) вытесняются от старых к новым, новые фрагменты из-за них не отбрасываются. Состояние меняется в одной функции под `Core.mu` с `defer`-разблокировкой: паника в сборке отбрасывает датаграмму, но не блокирует движок; счётчики занятой памяти меняются только после успешного шага и пересчитываются при каждой очистке. Ни один фрагмент Tunnel- или Block-датаграммы не уходит напрямую.
- DNS-запросы (UDP на порт 53) никогда не идут по быстрому пути: датаграмма собирается и проходит `udpOut` целиком, поэтому решение видит весь запрос; собранный запрос, ушедший напрямую, записывается в кэш DNS (иначе ответ отбросился бы как ответ без запроса). Без DNS-политики фрагменты запросов к частным адресам (домашний роутер) не перехватываются, как и в 1.0.0.
- TCP-фрагменты и фрагменты IPv6 с заголовками расширения перед заголовком фрагмента решаются по первому фрагменту, как раньше (существующий поток, иначе правила по владельцу; нет SOCKET-события — IP Helper; неизвестный домен — как у целой UDP-датаграммы): Direct проходит, Tunnel и Block отбрасываются (`FragLegacy`). Решение хранится 2 с. Первый фрагмент без портов (заголовок расширения после заголовка фрагмента) отбрасывается вместе с остальными.
- Исходящий TCP/UDP, который не разбирается парсером, отбрасывается (`Malformed`), а не отправляется без маршрутизации. Паника при обработке одного пакета или DNS-ответа отбрасывает этот пакет (`Panics`) и не снимает фильтры.

## 6. Доменная атрибуция

**DNS cache** (`internal/dnscache`) наполняется от H2: UDP целиком, TCP 53 только если сообщение уместилось в сегмент (MVP). Ответ из H2 принимается, только если он отвечает на исходящий запрос, увиденный H2 (тот же транспорт, локальный IP:порт, IP:порт сервера, txid и вопрос), не позже 30 с и один раз; посторонние пакеты с порта 53 игнорируются. Ответы, пришедшие через туннель (`udp.go`), принимаются по тому же правилу: запрос регистрируется при отправке в туннель (`udpSend`), ответ сверяется в `udpSession.read` до доставки приложению. Размер ограничен строго, 200 000 пар: при переполнении вытесняется пара, истекающая раньше других из 8 случайных. Один ответ добавляет не больше 256 пар. Хранит:
- `name → {(сайт, ip) → expiry}` и `ip → {(сайт, name) → expiry}`; TTL берётся из ответа, но не меньше 60 с и не больше 24 ч: служба DNS-клиента Windows отвечает программам из своего кэша весь TTL записи (MaxCacheTtl по умолчанию — сутки), не спрашивая сеть;
- CNAME-цепочки разворачиваются: `ip` привязывается к запрошенному имени и ко всем именам цепочки, и все они — один сайт (сайт назван по запрошенному имени). Доменное правило срабатывает для сайта, если подходит любое его имя (`rules.Set.EvaluateSites`); расходиться могут только разные сайты на одном IP (соседи по CDN);
- публичные имена ECH из HTTPS/SVCB-ответов хранятся отдельно (`Cache.PublicName`, не больше 4096 имён и не дольше 1 ч: любая зона может объявить публичным любое имя);
- `Sweep` раз в 5 с просматривает не больше 4096 пар, чтобы не держать блокировку; истёкшие пары, ещё не удалённые, при поиске не видны. Поэтому счётчик «пар в DNS-кэше» в статистике (`Stats.DNSPairs` = `Cache.Len`) приблизительный: в него входят истёкшие, ещё не удалённые пары, а CDN-имя, общее для двух запрошенных имён, считается дважды;
- при смене IP у домена старые пары живут до своего TTL, это не ошибка;
- при старте опционально подгружается кэш ОС через `DnsGetCacheDataTable`. Функция недокументированная и даёт только имена; имена резолвятся заново через `DnsQuery` с флагом `NO_WIRE_QUERY`, то есть только из кэша ОС.

Нормализация имени: lower-case, без trailing dot, IDN в punycode (`golang.org/x/net/idna`, профиль Lookup). Нормализация одинаковая для правил, DNS, SNI и Host.

**Приоритет источников:** SNI (в том числе внешний SNI ECH-hello, если это не известное публичное имя ECH) > HTTP Host > DNS cache (по сайтам: имена одной CNAME-цепочки — один сайт) > Unknown. SNI всегда перекрывает неоднозначное DNS-сопоставление. DoH/DoT браузеров мы не видим. Поэтому общий IP CDN может лежать в cache под именем соседнего сайта, и решение по DNS для веба было бы неверным (заблокированный сайт ушёл бы Direct по имени разрешённого соседа). При `exactWebDomains` веб-соединения, итог которых зависит от домена, всегда идут через SNIFF: DNS cache остаётся запасным источником, если SNI/Host не найден. QUIC с неизвестным доменом режется, и браузер уходит на TCP. Цена — такие Direct-соединения проходят через relay. Решения, которые от домена не зависят (правило по приложению, нет доменных правил), по-прежнему принимаются на пакетах. Настройка применяется при перечитывании правил.

### 6.1 DNS-политики

«Настройки» → «DNS» (`dns.json`, по умолчанию всё выключено). Настройки общие, не по профилям правил. Без них движок видит DNS только пассивно (H2), путь пакетов байт в байт прежний: указатель `Core.DNSPol` пуст, фильтр H1 не меняется.

**Что перехватывается** (`Core.dnsTarget`). Windows (SMHNR) и встроенный резолвер Chrome шлют один запрос DNS-серверам всех адаптеров и берут первый положительный ответ, поэтому сервер назначения классифицируется сначала по принадлежности адаптеру (фоновый снимок `SysDNSView`, `sysdns.Snapshot`: DNS-серверы адаптеров со шлюзом по умолчанию и без, суффиксы DNS и пространства NRPT), потом по диапазону:
- основной: DNS-сервер адаптера со шлюзом или публичный адрес, ничей (программа сама спрашивает `8.8.8.8`);
- другой адаптер: DNS-сервер любого другого адаптера, любого диапазона (корпоративный VPN, Tailscale `100.100.100.100`, виртуальные адаптеры): прямые имена ему не меняются, а отрицательный ответ туннеля на имя «через VPN» уходит этому серверу (`dnspolicy.ForSecondary`);
- прочие частные, CGNAT и link-local адреса, loopback, TCP к IPv6 link-local — как раньше. Промах просит новый снимок в фоне (не чаще раза в 5 с), пакетная петля никогда не ждёт ОС.

**Порядок решения** (`dnspolicy.Policy.Classify`, до него движок пропускает не стандартные рекурсивные запросы и свой трафик — PID HyRoute и его Hysteria):
1. имена серверов Hysteria (постоянно), проверки Windows и хост своего прямого сервера (постоянно), хосты, к которым HyRoute обращается сам (2 минуты: `app.OwnDial` перед каждым прямым соединением HyRoute записывает хост в набор контроллера `dnspolicy.OwnNames` — есть сессия или нет, — а движок каждой сессии читает этот набор через `Core.OwnName`, так что загрузка, начатая до или во время подключения, покрыта с первого пакета) — как раньше, кто бы ни спрашивал;
2. локальные имена (одна метка, `.local`, `.lan`, `.home.arpa`, `.arpa` и др., суффиксы адаптеров, кроме публичных суффиксов (`com`, `co.uk`, `com.ru`; `rules.Registrable`) — их задаёт сеть через DHCP, и `com` сделал бы локальным весь домен верхнего уровня; остаток: сеть может назвать суффиксом обычный домен, и его имена уйдут её серверу, NRPT, имена входа роутеров) — как раньше;
3. «Не давать браузерам обходить DNS»: канарейка Firefox — NXDOMAIN; с «Отключать ECH» HTTPS/SVCB — NODATA;
4. «DNS по правилам»: `rules.Set.EvaluateName` по одному имени. Протокол, порты и адрес неизвестны, программа известна только у собственного резолвера программы. Правило с неизвестной частью и совпавшим сайтом — «кандидат»: VPN у победителя или любого кандидата выше — через VPN (первое такое правило), «блок» — только если блок у всех, иначе напрямую. Правила без сайтов с неизвестной частью не считаются. С «Сверяться с правилами по IP и geoip» правило «Напрямую» по адресу выше решающего (кроме только локальных диапазонов) оставляет имя как раньше. Туннель: AAAA при «Не пускать IPv6 в VPN» — NODATA, иначе разрешается через сервер правила (с запасными; член группы выбирает `Core.pick` с `Hint.Stable`: поиск без побочных эффектов, один сайт — один член); блок — NXDOMAIN;
5. напрямую: со «Шифровать прямые DNS-запросы» разрешается своим DoH/DoT; сбой, отмеченный недоступным сервер, NXDOMAIN или NODATA для A — запрос уходит как раньше.

**UDP** (`udpOut` → `dnsUDP` перед `udpRoute`): владелец из таблицы атрибуции; неизвестный владелец (свежий сокет программы) ждётся вне петли, как у нового соединения (до 100 мс). Ответ собирается и инжектится входящим от сервера, которому шёл запрос; сам запрос никуда не уходит. Разрешение идёт в горутине (не больше 256 одновременно; нет места — туннельное имя SERVFAIL, прямое как раньше). Ответ передаётся через `dnscache.AddAnswerFor` (только пара «наш запрос — его ответ»).

**TCP**: SYN к перехватываемому серверу отражается в relay в режиме `nat.DNS` (`Entry.DNSDest` фиксирует вид сервера на соединение), `Core.ServeDNS` отвечает на сообщения (не больше 32, 60 с, 10 с простоя). То, что политика не берёт, передаётся одному соединению к исходному серверу по маршруту, который соединение получило бы сегодня (служба DNS и частный сервер — напрямую, иначе по правилам на адрес; туннель без запасного пути, блок — RST). Ответы с чужим ID (остаток многосоставного ответа) пропускаются. Передача зоны (AXFR/IXFR) отдаёт остаток соединения серверу целиком: копирование в обе стороны, как у обычного соединения relay. Разрешение идёт в контексте relay: `Abort` его прерывает.

**Строки «Соединений»**: запросы, на которые ответил HyRoute, собираются в строку на (PID, имя, правило, маршрут, сервер, исход) со счётчиком, закрываются через 30 с тишины или 5 минут и хранятся в своём кольце (1000), не вытесняя соединения. Статистика их не считает.

**Резолвер** (`dnsproxy.Resolver`): кэш по (путь, профиль, имя, тип, DO, CD) с TTL ≤ 300 с (негативы ≤ 60 с), singleflight, клиенты DoH (HTTP/2, без прокси окружения, без User-Agent), DoT и TCP (только через туннель). Через туннель клиент звонит через SOCKS5 Hysteria (`Endpoint.Dial` на каждый дозвон), у пресетов — на их bootstrap-адреса. Здоровье на клиент: 3 ошибки подряд — «не отвечает» на 30 с, потом 60, 120 с, после паузы один пробный запрос. Ответы через туннель ограничиваются 300 с, негативы 60 с (`Reply`).

**Отказ** — всегда в сторону «не отправлять напрямую»: туннель недоступен, резолвер туннеля не отвечает или отмечен, нет места, паника — SERVFAIL (§8). Единственное исключение — пауза портала на 5 минут («Разрешить имена напрямую на 5 минут»): имя через VPN при **недоступном** туннеле уходит как раньше.

**Браузеры и DoH**: с «Не давать браузерам обходить DNS» соединения браузера (имя exe из списка) на 443/853 к известным адресам и именам DoH (`dnspolicy.IsDoHAddr`/`IsDoHHost`, имена из DNS-кэша, SNI в relay) блокируются в `decide`, `untrackedRoute` и `RelayDecide`; включение сбрасывает уже открытые (`Core.DropDoH` + `relay.AbortWhere`).

**Переключения в сессии** (`Session.SetDNS`): включение — сначала фильтр (`SetDNSCapture`), потом политика; выключение — сначала политика, потом RST DNS-соединениям (`Core.AbortDNS`, `relay.AbortWhere`) пока фильтр их ещё отражает, потом фильтр. `applyRoutingLocked` вызывает `SetDNS` раньше `SetRules`: новый сервер запускает Hysteria с уже известным именем.

**Кэш DNS Windows** (`DnsFlushResolverCache`, не чаще раза в 2 с): при запуске HyRoute с включённой политикой, при подключении, при изменении настроек DNS, при сохранении правил (и переключении профиля) с «DNS по правилам», когда туннель поднялся после SERVFAIL или паузы, при начале паузы и после отключения; при выходе (`Shutdown`) ожидающая очистка выполняется сразу, до возврата, без ограничения частоты (не дольше 3 с).

## 7. Правила: модель и матчинг

```jsonc
{
  "id": "uuid", "name": "Discord", "enabled": true,
  "apps":    [{ "pattern": "discord.exe", "kind": "name|path|glob", "inheritChildren": true }],   // любая из программ; пусто = любая
  "domains": [".discord.com", "*.discord.gg", "discord.media"],   // любой из сайтов; exact | *.x (только поддомены) | .x (x и поддомены)
  // старая форма "app": {...} / "domain": {"pattern": ...} по-прежнему читается
  "profile": "<id сервера>",                   // для tunnel; пусто = основной
  "protocol": "any|tcp|udp",
  "ports":    "443,8000-8100",                // порты назначения: порт или диапазон; нет поля = любые (ports)
  "action":   "tunnel|direct|block",
  "failMode": "open"                          // зарезервировано (kill switch теперь глобальный, §8.1)
}
```
- Путь нормализуется: `\\?\`, `\Device\HarddiskVolumeN\` через `QueryDosDevice` в `C:\`, сравнение без учёта регистра. `name` сравнивается с basename, `glob` проверяется по полному пути: `*` — любая последовательность символов, включая `\` (как в Proxifier: `C:\Games\*` покрывает все вложенные папки), `?` — один символ. Тип определяется автоматически, если не задан: есть `*`/`?` → glob, есть `\` или `/` → path, иначе name.
- Приложение без атрибуции (`Unknown`) не совпадает ни с одним правилом по приложению. Наследование (`inheritChildren`) проверяет цепочку предков из дерева процессов (§2).
- Режим задаёт `defaultAction`: «только выбранные через туннель» даёт Direct, «все, кроме выбранных» даёт Tunnel.
- Порядок применения: исключения (§3), затем пользовательские правила сверху вниз (first match), затем default.
- **Порты** (`internal/rules/ports.go`). `ports` — список портов назначения: `"443"` или `"8000-8100"`, между элементами «ИЛИ», с остальными условиями (программы, сайты, протокол) — «И». Порт назначения движок знает всегда (`Subject.Dst` у всех мест решения, у фрагментов — из первого), поэтому условие решается на уровне пакета: `base` проверяет его вместе с протоколом, и поток на порт, которого нет в правиле, не ждёт имени сайта (не `NeedsDomain`). При компиляции элементы проверяются (1..65535, `lo <= hi`; не больше 256 на правило — только при вводе: редактор, текст правил, `ParsePortList`; сохранённый список не ограничен, как в v1.2.0), сортируются и сливаются в диапазоны (`80, 81-90` → `80-90`), совпадение — бинарный поиск; порт 0 (неизвестен) не совпадает никогда. Порты проверяются и у выключенных правил: иначе испорченный вручную порт расширил бы правило при экспорте или включении. Правило может состоять только из портов («TCP 22 → напрямую» для всех программ и сайтов); правило только с протоколом по-прежнему ошибка. Безымянное правило только из портов называется по ним («TCP 22», «порт 443») — одинаково в Go (`ruleName`, снаружи пакета `RuleLabel` — им подписаны и предупреждения о серверах правил) и в UI (`ruleTitle`, элементы канонизируются так же: `"0443"` → «порт 443»). В JSON поле пишется, только если порты есть (`omitempty`), строкой в форме v1.2.0 (`"80,443,27000-27200"`, `PortList.MarshalJSON`), чтобы после отката на 1.2 файл читался; читается и эта строка, и массив (`["443", 8000]`). Строку из одних разделителей (`","`) ввод отклоняет (редактор, текст правил), а не делает «любым портом»; в файле (так сохранял редактор v1.2.0) она читается, как читал v1.2.0: портов нет, правило на любой порт, при записи поле пропадает. У правил без портов settings.json остаётся в формате 1.0.0, а 1.0.0/1.1 с портами файл не прочтут (`DisallowUnknownFields`) — это отказ, а не расширение правил. QUIC (UDP 443) при «Точное определение сайта» и «Блокировать QUIC…» решается без имени (`rules.NamelessUDP`, общий для `packetSites`, Explain и Lint): правило «сайт + UDP 443» там не срабатывает, об этом предупреждают lint и редактор. Lint (`LintWith` с настройками движка) ещё подсказывает («info»), что UDP-порт 49152–65535 без программы ловит и ответы локальных UDP-серверов.
- **Правила текстом** (`internal/app/rulestext.go`). Весь список можно выгрузить текстом, поправить и загрузить обратно, или добавить много правил пачкой. Формат: одна строка — одно правило `что -> куда [| опции]`. Блок `[chrome.exe]` ограничивает строки под ним одной программой (в них пишутся только сайты: программа в такой строке — ошибка, правило для неё пишется после `[*]`), `[*]` (а также `[все]`, `[всё]`, `[all]`, `[]`) снимает ограничение и означает все программы, `* -> …` задаёт «всё остальное» и допускается один раз, вне блока программы и без опций. Опции `tcp` и `udp` вместе — ошибка (это любой протокол). Сервер указывается именем, его уникальной частью или `id:`; неоднозначное имя — ошибка. При любой ошибке ничего не сохраняется, в ответе номера строк. Экспорт и импорт дают те же правила (тест round-trip). `=game.exe` — программа без дочерних процессов, маски `*`/`?` (кроме `*.x`) — программы по полному пути; элемент или название с пробелами, `|`, `->` или начальным `#` пишется в кавычках, название без кавычек с `.`, `\`, `/` или `*` — ошибка (просим кавычки); путь с пробелами без кавычек (абсолютный путь не к `.exe`, за которым идёт относительный путь, а для пути без расширения — программа или голое слово) отклоняется, элемент в кавычках всегда цельный, и экспорт берёт в кавычки абсолютный путь не к `.exe`; элемент-сайт с невозможными символами (`«youtube.com»`, `(a.com)`, `a.com!`) или пустыми частями (`..a.com`, `a..com`, `domain:.a.com`) — ошибка (`rules.SiteProblem`); ссылка на `www.сайт` даёт сайт без `www.`; строки с `выкл` тоже компилируются и проверяются (без предупреждений); сервер с зарезервированным именем выгружается как `id:`. В `[ ]` допустимы только программы (имя с точкой без `.exe` принимается с предупреждением). Программу, которую строка прочла бы иначе (`vmmem` как `vmmem.exe`, `my.app` как сайт, одинокое `*` как «всё остальное»), экспорт пишет с префиксом `app:` (`app:vmmem`, `=app:my.app`); кавычка внутри элемента в кавычках удваивается. Опции портов (`ports`): `tcp 443`, `udp/27000-27100`, `tcp:22`, `порт 443`, `порты 80, 443` (элементы через запятую, точку с запятой или пробел, диапазон через `-`, `–`, `—`, в том числе с пробелами); несколько опций с портами (текст v1.2.0: `| порт 443 | порт 8443`) сливаются в один список, разные протоколы в одной строке — ошибка, опция из одних разделителей (`порт ,`) — ошибка. `* -> X | tcp 22` — правило только по порту (с именем: `SSH: * -> …`, под `[chrome.exe]` — для этой программы), `* -> X` без порта — по-прежнему «всё остальное». Экспорт пишет опцию канонически (`ruleOptionText`, общий с конвертером ACL), программу-маску `*` с портами — как `app:*`, а неверные сохранённые порты — обезвреженными (`rawPortItem`), чтобы импорт показал ошибку в этой строке, а не расширил правило.
- Внутри списка `apps` условия объединяются через «ИЛИ», внутри `domains` тоже. Между списками — «И»: если заданы и программы, и сайты, правило ловит только соединения этих программ к этим сайтам. UI объясняет это и предлагает два правила, если нужна вся программа целиком.

### 7.1 Адреса и базы правил (geosite / geoip)

- В `domains` кроме сайтов можно писать: `geosite:youtube` (категория geosite.dat, `geosite:google@cn` — только записи с атрибутом, `geosite:google@cn@ads` — записи со всеми атрибутами, как в Xray; если ни у одной записи категории таких атрибутов нет, это предупреждение, а не пустой элемент), `geoip:ru` (категория geoip.dat), IP (`1.2.3.4`), сеть (`10.0.0.0/8`, `2001:db8::/32`), `keyword:слово`, `regexp:RE2`, `full:x` (= `x`), `domain:x` (= `.x`). Поле в JSON то же, `domains`: адресные элементы (`IsAddressItem`) компилируются в отдельный список `ips`.
- Назначение правила = «сайты ИЛИ адреса»: правило совпадает, если IP назначения входит в любой адресный элемент или имя подходит под любой доменный. IP известен всегда, поэтому трёхзначная оценка: адресное совпадение сразу терминально; правило только с адресами, которые не совпали, не влияет на исход и не требует sniff.
- Формат баз — protobuf v2ray (`GeoSiteList`/`GeoIPList`), читается без зависимостей (`internal/geodata`). Файл 70+ МБ целиком не грузится: при первом обращении строится индекс «категория → смещение» (≈15 мс на 74 МБ), категория декодируется, только когда её использует правило, и кешируется до смены файла; категории, которых нет во включённых правилах (например, проверенные в редакторе), выбрасываются из памяти планировщиком (раз в 10 минут и после сохранения правил). Домены: отсортированные `full` и `suffix` с бинарным поиском по суффиксам имени, `keyword`, `regexp` (шаблон в нижний регистр не переводится, а компилируется с `(?i)`, без учёта регистра). IP: слитые отсортированные диапазоны v4/v6, бинарный поиск; `reverse_match` поддерживается. `geoip:private` встроен и работает без баз.
- Нет базы или категории — это предупреждение (`Set.Warnings`, lint, текстовый импорт), а не ошибка: правило компилируется и такой элемент ничего не ловит. Иначе обновление базы, где убрали категорию, при старте сбросило бы все правила пользователя на значения по умолчанию.
- Источник — пресет (по умолчанию runetfreedom/russia-v2ray-rules-dat: всё из v2fly плюс `ru-blocked`, `ru-available-only-inside`; Loyalsoldier; v2fly) или свои ссылки. Обновление: `.sha256sum` рядом с файлом → если совпадает с установленным, ничего не качается; иначе новая версия ставится. Установленным считается файл на диске: его SHA-256 сверяется при каждой проверке, поэтому испорченный файл (сбой питания, ошибка диска) ставится заново даже той же версией. Скачивание — во временный файл со случайным именем (`os.CreateTemp`, CREATE_NEW) с fsync, затем проверка SHA-256 и формата (индекс строится, есть категории), старый файл → `.prev`, новый на место. geo.json и `.prev.json` пишутся так же (временный файл + rename), а читаются без прохода по ссылкам (FILE_FLAG_OPEN_REPARSE_POINT, отказ при NumberOfLinks ≠ 1): папка доступна на запись программам пользователя, а HyRoute работает с правами администратора. Редирект с https на http не выполняется. Адрес суммы — путь файла + `.sha256sum`, query сохраняется. Ответы 401/403/404/410 и ответ не вида `<sha256> имя` значат «сумма не опубликована»: файл ставится без пометки «проверена». Сетевая ошибка, 5xx и 429 — файл не ставится. Откат меняет файл и `.prev` местами, «всё или ничего». Восстановленный откатом файл закреплён (`heldFor`/`rolledBackFrom` в geo.json): для того же источника он не считается недостающим, а плановое обновление не ставит версию, от которой откатились (более новую ставит). Ручное «Проверить обновления»/«Скачать заново» и смена источника закрепление снимают. `.prev.json` описывает только файл в `.prev`; если описание не совпадает с файлом, при откате состояние строится по самому файлу. После обновления правила перекомпилируются и уходят в сессию; новые соединения идут по новой базе.
- Принадлежность файла источнику определяется по URL в `geo.json` (`FileState.url`). Свои ссылки — только `https://`; сохранённые раньше `http://` не скачиваются, причина видна в «Базы правил». Неудачная смена источника или своих ссылок оставляет базу «недостающей», повтор идёт с паузой.
- Базы качаются, только если их используют включённые правила (кроме `geoip:private`), и решается это по каждой базе отдельно: при правилах только с `geoip:` `geosite.dat` не качается и не обновляется по расписанию, если не остался файл от прежнего источника (его заменяют один раз). Ручное обновление работает с обеими базами. Проверка — при сохранении правил, при старте и каждые N часов (по умолчанию 12, настраивается). Недостающая база качается даже при выключенном автообновлении. Прямая загрузка не удалась (GitHub часто режется) — повтор через туннель основного профиля, если он подключён. После ошибок, в том числе при автообновлении, — пауза с ростом до 6 ч, а не повтор через N часов.
- «Проверить адрес» для сайта при наличии адресных правил резолвит его IPv4 и показывает, по какому адресу проверялись geoip/IP.
- Инспектор списков (`internal/geodata/inspect.go`, `internal/app/inspect.go`, страница «Списки»): обратный поиск — какие категории содержат имя или IP. Индекса нет: все категории файла сканируются параллельно по индексу смещений, без построения множеств (≈170 мс на 74 МБ geosite, ≈40 мс на geoip). include: в .dat уже раскрыты, поэтому родительские категории находятся сами. Для имени ещё резолвятся A/AAAA и проверяется geoip. Результаты сортируются по приоритету (явные значения для anthropic/telegram/openai/…, сервисы 700, category-* 100, geoip 80, агрегаты — реестры, регионы, страны — 40), при равенстве — меньший список выше. Просмотр категории держит в памяти только последнюю открытую. Конвертер ACL (как и в Hysteria, срабатывает первое совпадение: строка `all`/`*` без протокола задаёт «Всё остальное», а строки ниже неё пропускаются с предупреждением): строки `action(resource[, proto/port])` → корневые домены `*.x suffix` (geosite раскрывается по базе, keyword/regexp пропускаются с подсчётом) или правила HyRoute (direct → напрямую, reject → блок, остальные выходы → vpn; подряд идущие с одним действием склеиваются, порядок сохраняется; `reject(all, udp/443)` указывает на настройку «Блокировать QUIC»). Протокол и порт переносятся (`aclProtoPort` повторяет `parseProtoPort` Hysteria: строку, которую Hysteria не примет, конвертер пропускает с предупреждением; начальный порт 0 значит «любой порт»): `proxy(x.com, tcp/443)` → `| tcp 443`, `*/80` → `| порт 80`; строки склеиваются, только если совпадают действие, протокол и порты. `action(all, tcp/22)` → правило только по порту `* -> … | tcp 22`, `all` с протоколом без порта → `| udp 1-65535`; `reject(all, …)` и `direct(all, …)` добавляются выключенными: на сервере первое блокировало только трафик через него, а второе означало выход сервера напрямую (трафик клиента всё равно шёл через VPN), правило же HyRoute заблокировало бы и прямой трафик или пустило бы трафик всех программ мимо VPN. Исключение прежнее: `reject(all, udp/443)` — указание на «Блокировать QUIC». Строки с перенаправлением (третий аргумент) пропускаются; такая строка `all`/`*` без протокола и порта всё равно завершает список, как в Hysteria. Строка «Сейчас HyRoute» на странице «Списки» спрашивает о TCP к веб-порту сайта (порт из запроса, для `http://` — 80, иначе 443) и, если в правилах есть порты, называет его.

### 7.2 Профили правил

- **Что общее, что своё.** Профиль правил — это `rules.Config` (`defaultAction`, `defaultProfile`, `defaultFallback`, `rules`). Всё, что в `settings.Settings` вне `Config` (опции движка), общее, как и основной сервер, прокси, группы и DNS. Поле, которое должно быть своим у каждого профиля, добавляется в `rules.Config`.
- **Файлы.** `settings.json` всегда хранит правила включённого профиля и главный для них: v1.0.0 и все пути записи работают как раньше. `rulesets.json` (`internal/store/rulesets.go`) появляется только со вторым профилем: версия формата, `active`, список `{id, name, config}` и — только между двумя записями пары — `pending {was, to}`: хэши правил в `settings.json` до и после (`ConfigHash`, sha256 JSON правил, разобранных из записываемых байтов). Копия включённого профиля в `rulesets.json` обновляется при каждой записи этого файла; `configOfLocked` для включённого профиля всегда отдаёт живые правила.
- **Чтение.** `LoadRulesets` читает через `readRegular` (ссылка, точка соединения, папка — «не обычный файл»), не больше 16 МиБ. Оболочка разбирается строго (`DisallowUnknownFields`; `version` больше известной — «создан более новой версией HyRoute»), каждый `config` тоже строго, но профиль, в правилах которого есть только неизвестные поля, загружается как «новее» (`Newer`): его байты сохраняются при каждой записи файла, включить, открыть или скопировать его нельзя, переименовать, переместить и удалить можно. ID `^[0-9a-f]{8,32}$`, не больше 50 профилей, имя 1–40 символов без управляющих и форматных (bidi, zero-width), уникально без учёта регистра.
- **Три вида записи**, все под `saveMu`:
  - S — только `settings.json` (правка правил включённого профиля): `rulesets.json` не трогается, его копия просто стареет;
  - R — только `rulesets.json` (создание без включения, переименование, порядок, удаление, правка неактивного): `rulesetsOnlyState` освежает копию включённого профиля живыми правилами;
  - P — пара, `Store.WriteRulesPair`: 1) сырые байты `rulesets.json` (`ReadRaw`, даже битые); 2) `rulesets.json` с `pending`; 3) `settings.json` — при ошибке байты шага 1 возвращаются (`WriteRaw`; файла не было — он удаляется); 4) `rulesets.json` без `pending` (ошибка не страшна: следующая запись снова будет парой). P — переключение, создание с включением и любая запись `settings.json`, пока на диске есть отметка или `settings.json` отстаёт от работающих правил (`rulesetsForCommit`). Если не удалось и вернуть байты, отметка в памяти заставит следующую запись переписать `rulesets.json`, а перезапуск до неё завершит прерванную операцию (в журнале). Если файла не было (первое создание с включением), вместо отметки следующая запись одного `settings.json` сначала удаляет оставшийся `rulesets.json` (`rsLeftover`, строка в диагностике); перезапуск до неё так же завершит прерванную операцию. Установка пары — всегда `installPairLocked` (он же снимает «`settings.json` отстаёт»), а не один `installRulesetsLocked`.
- **Загрузка** (`reconcileRulesets`, без блокировок; её же вызывает откат резервной копии): нет `rulesets.json` — функции нет; битый — `rulesetsBroken`: текущие правила работают, переключение, создание, правка неактивных и удаление серверов запрещены, файл не перезаписывается; нет `settings.json` — правила включённого профиля из копии (опции движка по умолчанию), следующая запись — пара; если при этом копия не загрузилась (`rulesets.json` битый, включённый профиль «новее» или не компилируется), в памяти правила по умолчанию вместо неизвестных — `rsLoad.RulesUnknown`, и `Load` ставит его в `settingsBroken`, как для битого `settings.json`: подключение и запись правил отклоняются (иначе трафик шёл бы напрямую, а записанные правила по умолчанию после починки `rulesets.json` заменили бы включённый профиль); есть `pending` и хэш `settings.json` равен `was` — прерванная запись: правила берутся из `rulesets.json`, следующая запись — пара; иначе главный `settings.json`, и отличие от копии принимается в профиль (правка v1.0.0 или руками, включая возврат к прежним правилам). Единственная неоднозначность: HyRoute упал во время записи пары (или не смог снять отметку), а до следующего запуска `settings.json` отредактировали снаружи ровно в прежние правила — тогда запись пары завершится (в журнале имя профиля). Во время загрузки файлы не пишутся.
- **Неактивные профили** проверяются `rules.Check` (синтаксис без баз правил, матчеры geosite/geoip не строятся) при загрузке и после каждой записи (`prepRulesets`: только новые, изменённые и бывший включённый); ошибка хранится в `rsErrors`, такой профиль нельзя включить, но можно открыть без включения и исправить (его правка компилируется полностью, с базами). Компиляция и ввод-вывод никогда не идут под `c.mu`: между двумя короткими секциями под `saveMu`. `rulesets`, `rsErrors` и `rsAt` при изменении заменяются целиком, а не правятся на месте.
- **Токены и ревизии.** Страница шлёт `EditGuard{Ruleset, Rev, EditRev}`. `Ruleset` — ID включённого профиля (`"implicit"` до создания файла; принимается и после, пока включён первый профиль) или `"edit:<id>"` для правки неактивного без переключения. Он проверяется первым: копия другого профиля отклоняется своим текстом («Профиль правил сменился на «X»…», в режиме правки «…включили или удалили…»; `errors.Is(err, errRulesetChanged)`). Затем ревизия (§7.3): для включённого — `Rev < rulesAt`; для неактивного — `EditRev < rsAt[id]`, где `rsRev` растёт при каждой установке списка, а `rsAt[id]` — `rsRev` последней установки, изменившей правила именно этого профиля. Поэтому переименование, порядок, создание, удаление, правки и переключения других профилей правку X не отклоняют. `Status.ruleset.rev` = `rsRev`: страница в режиме правки перезагружается при `rev > editRev`, в обычном — при смене `Status.ruleset.token` или росте `settingsRev`.
- **Переключение** (`SwitchRuleset(id, src, opts)`; `ActivateRuleset` для «Сетей»). Сначала `switchPrecheck` (файлы загружены, профиль есть и загружается): отказ приходит до `netManual`, и отклонённое переключение не считается ручным выбором. Для окна, трея и CLI затем `netManual()` (до `saveMu`); с `SourceNetwork` вызывающий уже держит блокировку «Сетей». Порядок блокировок `netActMu → saveMu → mu`, `lifeMu` не берётся; «Переподключить» (`SwitchOptions.Reconnect`) — публичный `Reconnect` после снятия всех блокировок. Переключение — это коммит настроек (растут `settingsRev` и `rulesAt`, вызывается `OnSettings`), затем `Session.SetRules` и `tunnels.Manager.Sync`: новые соединения идут по новому профилю, открытые — по прежнему, кроме идущих через серверы, которые новому профилю не нужны: `Sync` их останавливает, и эти соединения закрываются (`SwitchResult.Stopped` — имена серверов). Редкий отказ уже после `netManual` (компиляция с текущими базами, запись файла, гонка с другой записью) всё равно считается ручным выбором.
- **Ссылки.** `eachRulesConfigLocked` — единственный обход правил всех профилей: `explicitRefsLocked` (ссылка из неактивного помечается « (профиль правил «X»)», `DeleteProfile` подсказывает «Открыть без включения»), `geoDue` (базы, нужные неактивному профилю, тоже скачиваются и обновляются). Пока `rulesets.json` битый, каждый сервер считается используемым. Что запущено, решает только включённый профиль (`routingLocked`).
- **Трей** — §11.

### 7.3 Сохранение правил и ревизии

Правила меняются с нескольких страниц сразу («Правила», «Главная», «Списки», «Правила текстом», а дальше и из «Соединений», трея, CLI), и каждая держит свою копию. Без проверки страница с устаревшей копией молча вернула бы чужое изменение, а «Настройки» со своей копией — старые правила вместе с переключателем.

- **Один путь записи** (`internal/app/settings.go`). `commitSettingsLocked(st, next)` вызывается под `saveMu`: проверка и запись `settings.json` (`next` — запись `rulesets.json` вместе с ним; какой из видов S/R/P, решается внутри, §7.2), затем под `c.mu` установка правил и `applyRoutingLocked`. Хвост (журнал, базы правил, kill switch, `OnChange`, `OnSettings`) выполняется после снятия `saveMu`, без блокировок. Ошибка записи не меняет ни правил в памяти, ни ревизии. Порядок блокировок прежний: `saveMu` → `c.mu`.
- **Писатели:**
  - `SaveRulesIn(EditGuard, cfg)` — только правила (`rules.Config`); опции движка остаются текущими, что бы ни было в копии страницы. Страницы «Правила», «Главная», «Списки» (привязка `SaveSettings(SettingsView)`).
  - `SaveEngineOptions(EngineOptions)` — только опции движка (`settings.EngineOptions`: те же ключи JSON, что у `Settings` вне правил), правила остаются текущими. Страница «Настройки»; без проверки ревизии: изменению правил она помешать не может. Синхронизация задачи проверки kill switch — в этой привязке.
  - `editRulesIn(EditGuard, fn)` — правка свежей копии правил под `saveMu`, так что между чтением и записью никто не вклинится. Порядок: сначала часть проверки, не зависящая от правил (`guardTargetLocked`: какие правила адресованы, дальше токен профиля правил), и копия — в одной секции `c.mu`, так что отказ приходит раньше `fn` и его не скроет ни `false`, ни ошибка `fn`; затем `fn`; затем правило ревизии (`guardRevLocked`) на изменённых правилах. «Правила текстом» (`ApplyRulesText(text, replace, guard)`), дальше правило из соединения и CLI.
  - `SaveSettingsIn(EditGuard, st)` — всё сразу; для внутренних вызовов и тестов. `SaveSettings(st)` = `SaveSettingsIn(EditGuard{}, st)`.
  - Новая опция движка добавляется и в `Settings`, и в `EngineOptions` (`TestEngineOptionsCoverSettings`).
- **Ревизия.** `settingsRev` (atomic): +1 за каждую успешную запись, при установке под `c.mu`; 1 после `Load`. `rulesAt` (под `c.mu`) — ревизия последней записи, изменившей правила (сравнение как в `settings.json`, через JSON). Запись одних опций движка `rulesAt` не двигает. Ревизию несут `SettingsView.rev` (читается в той же секции `c.mu`, что и копия), `RulesTextView.rev`, `SaveResult.rev`, `Status.settingsRev` и событие Wails `settings` (payload — новая ревизия, `ctl.OnSettings`).
- **Отказ.** Запись с `EditGuard{Rev}` отклоняется, если `Rev != 0 && Rev < rulesAt` и присланные правила отличаются от текущих: «Правила изменились в другом месте (например, из «Соединений»): изменение не сохранено, список обновлён — повторите.» Копия, устаревшая только из-за записи опций, и копия с теми же правилами проходят. `Rev = 0` — без проверки (внутренние вызовы, CLI). Добавление пачкой в «Правилах текстом» ревизию не шлёт: правила добавляются после текущих.
- **Страницы.** `ui.settingsRev` — наибольшая увиденная ревизия (статус раз в секунду и событие `settings`). «Правила» и «Главная» перезагружают копию при `ui.settingsRev > rev`, но только в простое: не во время своей записи, не при открытом редакторе правила, тексте или перетаскивании. Записи «Правил» идут цепочкой в порядке кликов, и каждая шлёт ревизию, полученную предыдущей. Если за время перезагрузки пришла новая ревизия, после неё страница перезагружается ещё раз; неудачная перезагрузка не повторяется, пока ревизия не вырастет снова. После отказа «Правила» и «Главная» показывают ошибку и перезагружаются. «Правила текстом» после отказа замены текст пользователя не трогают: обновляется только ревизия, так что повторное «Сохранить список» заменит им новые правила сознательно, а кнопка «Показать текущие правила» / «Вернуть мой текст» меняет текст в редакторе, не теряя ни один из двух.
- `EditGuard.Ruleset` и `EditRev` (и `SettingsView.editRev`, `warnings`) — для профилей правил: токен набора правил и ревизия неактивного профиля при его правке.

## 8. Отказоустойчивость

Два разных сценария, и поведение в них разное:
- **Приложение живо, туннель недоступен** (Hysteria ещё не подключилась, упала, переподключается, relay не работает): Tunnel-трафик **отклоняется** (RST/drop). Отправлять его напрямую — худший вариант для обхода блокировок: будет утечка, а соединение, скорее всего, всё равно не пройдёт. Direct и Block работают как обычно, так что интернет в целом не ломается. Это мягкий kill switch, отдельный WFP для него не нужен.
- **Приложения нет** (выход, крэш, зависание, убито watchdog'ом): фильтры снимаются, весь трафик идёт напрямую (**fail-open**). С включённым kill switch (§8.1) после сбоя интернет закрывается.
- **DNS-политики** (§6.1): имя сайта через VPN при недоступном туннеле или неработающем DNS-сервере для VPN получает SERVFAIL и напрямую не спрашивается никогда (исключение — пауза портала, которую включает пользователь, только для недоступного туннеля). Сбой прямого DoH/DoT (в том числе его ответ SERVFAIL, REFUSED и другие коды ошибки, кроме NXDOMAIN; через VPN такой ответ даёт SERVFAIL этому запросу; в кэш он не попадает и к отказам сервера, после трёх подряд помечающим его неработающим, не засчитывается — SERVFAIL обычно касается одного имени, а Windows спрашивает A, AAAA и HTTPS одновременно), его NXDOMAIN или NODATA для A — запрос уходит DNS-серверу сети, как без настройки. При крэше и отказе движка фильтры снимаются, DNS идёт как без HyRoute; ответы через VPN Windows помнит не дольше 300 с, отказы — не дольше 60 с, а следующий запуск с включённой политикой чистит кэш.

### 8.1 Kill switch (WFP)

Выключен по умолчанию (`settings.json`: `"killSwitch": true`). Пакет `internal/killswitch`, WFP через `github.com/tailscale/wf`. Все объекты в своём подслое (вес 0xFFFF) с фиксированными GUID, поэтому следующий запуск находит и снимает их без перечисления чужих фильтров. Слои: `ALE_AUTH_CONNECT_V4/V6` и `ALE_AUTH_RECV_ACCEPT_V4/V6`.

| Фильтр | Вес | Сессия | Смысл |
|---|---|---|---|
| block | 1 | обычная (не dynamic, без PERSISTENT) | всё закрыто; живёт после смерти процесса, до `Release` или перезапуска BFE (перезагрузки) |
| исключения | 10 | обычная | loopback; LAN (10/8, 172.16/12, 192.168/16, 169.254/16, 224/4, 255.255.255.255, fe80::/10, fc00::/7, ff00::/8); DHCP — только `svchost.exe` (AppID), UDP с порта клиента на порт сервера (68→67, 546→547); DNS — только `svchost.exe` и только к DNS-серверам адаптеров своего семейства (`internal/sysdns`, список обновляется при каждом `Arm` и `RefreshApps`): UDP и TCP на порт 53, TCP на 443 и 853 (UDP на 443/853 — нет), так что BITS/WebDAV из svchost не выходят через порт 53 к другим хостам, а входящие с порта 53 не проходят; 443 и 853 нужны, чтобы при DoH/DoT-only Windows мог резолвить сервер Hysteria. Если DNS-серверы неизвестны (ни один адаптер ещё не поднят) — svchost.exe получает UDP и TCP на порт 53 любого хоста, но только исходящие (на слоях RECV_ACCEPT правила нет), DHCP остаётся узким. Если неизвестен AppID svchost — как раньше: удалённые порты 53, 67, 68, 546, 547 для всех программ; блок старой версии с портами для всех заменяется; AppID `HyRoute.exe` и `hysteria.exe` (выбранное, встроенное и предыдущее ядро; после установки или отката ядра список обновляется сразу, без нового `Arm`) |
| порт relay | 15 | обычная | block: `HyRoute.exe` (`Switch.Self`) с локального порта relay к не-loopback адресам. Выше исключения для HyRoute, ниже pass. Порт — текущей сессии, передаётся в `Arm(relayPort)`. После сбоя или крэша FIN, повторы и keepalive сокетов relay не уходят к реальным R:lp (M40) |
| pass | 20 | dynamic | разрешить всё: пока движок работает, маршрутизирует он |

Жизненный цикл (`app/killswitch.go`):
- движок поднялся → `Arm`: pass, затем block и исключения (идемпотентно, список программ обновляется);
- движок упал (panic, ошибка `Recv`, watchdog) → `Engine.fail` сначала инжектит RST в каждое отражённое соединение приложения, как `Engine.Stop`, пока pass ещё действует (блок мог бы отбросить входящие RST), затем вызывает `OnFail` (сбросить relay, закрыть pass) и только потом снимает хэндлы, так что между fail-open и блоком нет окна. Сброс ждёт не дольше 0,5 с: зависший packet loop может держать блокировку NAT или `swapMu`, и тогда фильтры снимаются без сброса, с записью в журнал; все шаги (`resetReflected` → `OnFail` → `closeMains`) делает только первый вызов `fail`, одновременный второй ничего не делает, так что окна между fail-open и блоком нет. Закрытый `divert.Handle` больше никогда не передаёт своё значение в WinDivert: зависший loop, проснувшись позже, не прочитает хэндл нового движка;
- через 5 с контроллер сам делает `Reconnect` (не больше 3 раз за 10 минут; попытка, которая не запустилась, тоже считается, и следующая планируется так же): pass уже закрыт, block держится всё время переподключения, новый `Arm` снова ставит pass. Когда попытки кончились, `OnGiveUp` (в отдельной горутине) показывает окно;
- крэш или kill процесса → Windows закрывает dynamic-сессию, pass исчезает, block остаётся;
- `Disconnect`, выключение настройки → `Release`;
- выход из приложения (`Shutdown`) block не снимает: Windows закрывает окно одинаково и по крестику, и по «Снять задачу» в диспетчере задач (WM_CLOSE), отличить их нельзя;
- завершение сеанса Windows (выключение, перезагрузка, выход; трей получает `WM_ENDSESSION`) → `Release`: при «Завершении работы» с быстрым запуском состояние WFP переживает выключение, и после включения интернета не было бы. Работает только у запущенного HyRoute, у которого systray создал своё окно (без него `WM_ENDSESSION` не приходит); block, оставшийся после закрытого HyRoute, при быстром запуске переживает выключение, его показывает проверка при входе (ниже). `WM_ENDSESSION` приходит и при отменённом завершении: `EndSession` до `SessionResumed` запрещает `Arm`, а трей через 30 с, если процесс жив и `SM_SHUTTINGDOWN` снят, вызывает `SessionResumed` и kill switch снова следует настройке. Если маршрутизация при этом не работает (движок отказал, сессии нет, блок остался от сбоя), `SessionResumed` снова ставит снятый блок без pass, если пользователь тем временем не нажал «Отключить» или «Открыть интернет» и не выключил настройку. systray сообщает `WM_ENDSESSION` один раз за запуск, поэтому после отменённого завершения трей сразу перезапускается (`renewTray`), до того как `SessionResumed` вернёт блокировку;
- GUID фильтров общие для всех HyRoute на машине: владеет ими копия, которая их поставила (`Arm`) или нашла блок при запуске (`Engaged`), пока фильтры стоят; `Release` отдаёт владение. Просто запущенная копия с выключенным kill switch владельцем не становится. Копия в другом сеансе Windows фильтры владельца не трогает. Владельца отмечает Global-мьютекс; объект с этим именем, чей владелец не Administrators/SYSTEM (его создала обычная программа), или объект другого типа не считается чужим HyRoute и не мешает kill switch.
- `Reconnect` и выход → сначала `Session.ResetConnections` (relay и отражённые соединения сбрасываются, пока pass пропускает RST к приложениям), затем pass закрывается до остановки движка, block остаётся до нового `Arm`;
- установка обновления и перенос в Program Files → `HoldKillSwitch`: block переживает выход, новая копия с `--reconnect` снова ставит pass;
- запуск → `InitKillSwitch` видит подслой от прошлого запуска: статус `blocking`, на главной «Подключиться» и «Открыть интернет». Он сразу обновляет исключение программ (`RefreshApps`): блок мог остаться от копии по другому пути (перенос в Program Files, обновление). Если состояние неизвестно (например, блоком владеет HyRoute другого пользователя), при включённом kill switch ошибка показывается в статусе. При старте с `--autostart` окно с оставшейся блокировкой открывается видимым (не в трее и не свёрнутым), как при `--killswitch-check`;
- «Открыть интернет» после того, как автопереподключение уже снова взвело kill switch, ничего не снимает: интернет открыт, защита подключения остаётся.
- проверка при входе: пока kill switch включён, HyRoute в Program Files (`protectedLocation`, §11) и нет задачи автозапуска, существует задача пользователя «HyRoute kill switch (<SID>)» (`autostart.EnableCheck`, та же XML-схема и COM `RegisterTask`, HighestAvailable, Priority 4, задержка 3 с). Она запускает `HyRoute.exe --killswitch-check`. Сразу после проверки прав, до `--wait-pid`, single-instance, восстановления обновления и прочего, `main` вызывает `killswitch.Leftover`: подслой установлен и нет Global-мьютекса владельца, созданного повышенным процессом, то есть ни один HyRoute его не ведёт. Без захвата владения, в отличие от `Engaged`. Если блокировки нет, процесс тихо выходит (код 0). Если есть или результат неизвестен, HyRoute стартует обычно с видимым окном. Синхронизация задачи (`GUI.syncKillSwitchCheck`, решение `planCheck`): при старте, при смене настройки kill switch, при `SetAutostart`. Пока `settings.json` не загружен, задача не меняется. Копия не в защищённой папке задачу не создаёт, а в настройках показывает предупреждение. Если права папки открыли уже после создания задачи, копия удаляет свою задачу при любых настройках: задача запускает exe с HighestAvailable, а его может подменить любая программа пользователя. Задачу другой копии она не трогает. Задачу автозапуска, которая запускает программу из папки, открытой на запись программам без прав администратора (`protectedLocationOf`), `syncKillSwitchCheck` удаляет при любых настройках и пишет об этом в журнал.

Блокируется весь трафик, а не только туннельный: без движка правила по программам и доменам применить нечем. DNS разрешён, потому что Hysteria резолвит сервер через службу DNS-клиента (svchost), а не от своего процесса. Флаг PERSISTENT не ставится намеренно: блок, переживший перезагрузку, оставил бы без интернета пользователя, который не запускает HyRoute.

| Сценарий | Что происходит | Почему трафик не ломается |
|---|---|---|
| Штатный выход / Disconnect | `Session.Stop` сначала сбрасывает соединения relay RST, пока фильтры ещё стоят; движок инжектит RST (как от удалённой стороны) в каждое отражённое соединение приложения, ожидая этот сброс не дольше 0,5 с; затем `WinDivertShutdown(BOTH)` и `Close` у всех main-хэндлов (в том числе у второго, если шла горячая замена), H2–H4; Job убивает Hysteria. `Engine.Stop` ждёт горутины не дольше 5 с. Close relay отменяет ожидающие dial, а не ждёт `DialTimeout`. `Session.Stop` и `ResetConnections` ждут обработчики relay не дольше 0,5 с (`relayWait`): обработчик может ждать блокировку NAT, которую держит зависший packet loop. Если время вышло, в журнал пишется «relay: connection handlers still running after close», и остановка продолжается | Фильтров нет, новые соединения идут напрямую. Соединения, которые шли через relay или туннель, рвутся, приложения переподключатся, а не продолжают их напрямую |
| Panic в горутине | `recover` в каждой горутине. Ошибка в соединении закрывает только его. Паника или неожиданная ошибка `Recv` в packet loop закрывают все main-хэндлы и дают статус «Engine failed». Через 5 с — автоматическое переподключение с тем же лимитом (3 за 10 минут), см. «Зависание packet loop» | Хэндлы закрыты явно |
| Крэш процесса (fatal error, kill) | Ядро закрывает хэндлы процесса, WinDivert сразу снимает фильтры; `KILL_ON_JOB_CLOSE` убивает Hysteria | Фильтры в ядре живут только пока открыт хэндл |
| Зависание packet loop | **Опасно:** WinDivert дропает пакеты, пролежавшие в очереди дольше `QUEUE_TIME`, то есть получается чёрная дыра. **Watchdog в процессе:** зависание считается по тикам: 4 тика по 500 мс без завершения той же пачки (у каждого packet loop своё состояние), а не по настенным часам. Тогда все main-хэндлы закрываются принудительно (fail-open), отражённые соединения приложений сбрасываются RST, как при Stop, ещё до `OnFail` (пока pass действует), соединения relay — в `OnFail` (ожидание не дольше 0,5 с: зависший loop может держать блокировку NAT или `swapMu`, тогда фильтры снимаются без сброса, с записью в журнал). Перед закрытием хэндлов в журнал движка пишутся стеки всех горутин (до 64 КБ). Остановка ждёт обработчики relay не дольше 0,5 с (`relayWait`), как при Disconnect. Движок остаётся в failed до Stop, `SetServerIPs` больше не открывает H1. Контроллер через 5 с сам делает переподключение (новая сессия, новый движок; зависшая горутина старого не мешает). Не больше 3 автоматических переподключений за 10 минут, дальше статус «Движок перехвата снова отказал: 3 автоматических переподключения за 10 минут не помогли…», окно показывается (`OnGiveUp`), и HyRoute ждёт пользователя. Неудачный запуск при автоматическом переподключении тоже считается попыткой, в статусе к ошибке запуска добавляется, будет ли ещё попытка. Connect, Disconnect, Reconnect и выход отменяют ждущую попытку | Закрытие H1 снимает перехват |
| Зависание всего процесса | **Внешний watchdog** `HyRoute.exe --watchdog <pid>`: тот же exe, крошечный режим без UI, пинг через named pipe раз в 500 мс. Нет ответа 5 с → `TerminateProcess` главного процесса, дальше как при крэше | То же |
| NAT-запись отражённого соединения истекла | Внутри сессии не-SYN сегменты такого соединения получают RST, а не уходят напрямую | Приложение переподключится через движок |
| Соединения, открытые до старта (в том числе после крэша HyRoute) | Не-SYN пакеты без состояния решаются по правилам (владелец из IP Helper, домен только из DNS cache, §4): Direct проходит, Tunnel и Block — RST приложению, пакет в сеть не уходит | Приложение переподключится через движок. Ограничение: DNS cache каждой сессии начинается пустым (при любом Connect, после крэша и после автопереподключения), а при «Точном определении домена для веба» веб-порты решаются без домена вообще. Соединение, которое шло в туннель только по доменному правилу, решается без домена (обычно по «Всё остальное») и при обычном подключении может продолжиться напрямую. После отказа движка (автоматическое переподключение и переподключение пользователя до «Отключить») и поверх блокировки kill switch такое соединение сбрасывается (`ResetUnknownDomain`) |
| Relay-listener упал | Флаг `relayHealthy=false`: Tunnel → RST на уровне пакетов, NeedsDomain решается по DNS/default на пакетах (итог Tunnel → RST). Listener перезапускается | Direct/Block relay не используют |
| Hysteria упала или ещё не подключена | Tunnel → RST/drop, в UI «Туннель недоступен, N соединений отклонено». Автоперезапуск с backoff 1 → 2 → 4 … 60 с (сброс после 30 с стабильной работы); при ошибке авторизации или конфига сразу 60 с и красный статус | Direct не затронут |
| Сервер пропал после подключения | Hysteria сама переподключается при запросах и пишет warn «SOCKS5 TCP/UDP error» с `connect error` / `authentication error` / `invalid config`. Supervisor видит это как потерю сервера: перезапускает `hysteria.exe`, профиль уходит в Failed, новые соединения идут через запасной (§15.2). Возврат сервера — с обычным backoff (до 60 с) | Fallback работает, как при недоступности на старте |
| SOCKS CONNECT вернул ошибку | RST приложению, в логе причина | Обычная семантика прокси |

## 9. Hysteria: профиль, конфиг, процесс

Поля профиля берутся только из официального конфига: `server` (host, ports: `443` или `443,20000-50000`), `auth`, `tls.{sni, insecure, pinSHA256, ca}`, `obfs.type = salamander|gecko` + `password` (для gecko `minPacketSize`/`maxPacketSize`), `transport.udp.{hopInterval | minHopInterval+maxHopInterval}`, `bandwidth.{up, down}`, `congestion.{type, bbrProfile}`, `quic.{initStreamReceiveWindow, maxStreamReceiveWindow, initConnReceiveWindow, maxConnReceiveWindow, maxIdleTimeout, keepAlivePeriod, disablePathMTUDiscovery, disableChromeParrot}`, `fastOpen`, `tls.ech` (продвинутое).

Сгенерированный YAML (golden-файлы в `internal/hysteria/testdata`):
```yaml
server: 203.0.113.10:443,20000-50000   # pin IP (§3) или host как есть
auth: <secret>
tls: { sni: example.com, insecure: false, pinSHA256: "..." }
obfs: { type: salamander, salamander: { password: <secret> } }
transport: { udp: { hopInterval: 30s } }
bandwidth: { up: 50 mbps, down: 200 mbps }
socks5:
  listen: 127.0.0.1:<свободный порт>
  username: <random 16>      # чтобы чужие локальные процессы не пользовались туннелем
  password: <random 32>
  disableUDP: false
```
- Файл пишется в `%APPDATA%\HyRoute\run\hy-<n>.yaml` с защищённым DACL: SYSTEM и Administrators; текущий пользователь — только если HyRoute запущен без повышения (тогда и Hysteria работает с его правами). HyRoute держит файл открытым с разрешением только на чтение для других, пока Hysteria не сообщит «connected to server» или не завершится: программы пользователя без прав администратора не могут переписать, удалить или переименовать конфиг, пока его читает Hysteria с правами администратора (папку `run` от подмены защищает `store.Guard`). Затем файл закрывается и удаляется.
- Запуск: `hysteria.exe client -c <file>`, env `HYSTERIA_LOG_FORMAT=json`, `HYSTERIA_LOG_LEVEL=info`, `HYSTERIA_DISABLE_UPDATE_CHECK=1`. Процесс создаётся `CREATE_SUSPENDED | CREATE_NO_WINDOW`, добавляется в Job `KILL_ON_JOB_CLOSE`, затем потоки возобновляются (`os/exec` не отдаёт хэндл главного потока, поэтому через Toolhelp-снимок потоков).
- Порт SOCKS5 выдаётся `reservePort`: он закреплён за своим процессом до его выхода, поэтому несколько одновременно стартующих профилей не получают один и тот же порт. Hysteria сначала подключается к серверу и только потом открывает SOCKS5, а порт до этого момента может занять чужое исходящее соединение (особенно если динамический диапазон Windows начинается с низких портов). Поэтому: bind-ошибка — отдельный вид `ErrPortBusy` с перезапуском через 200 мс на новом порту; Connected выставляется только после того, как порт принимает TCP (ожидание до 15 с, иначе перезапуск); если соединение с SOCKS5 работающего профиля отклонено (connection refused) и порт три раза подряд не отвечает, процесс перезапускается.
- Статусы берутся из JSON-лога (stderr, ключи `level`/`time`/`msg`): `connected to server` (плюс открытый порт SOCKS5, см. выше) даёт Connected (с полем `udpEnabled`: если сервер запретил UDP, UDP-Tunnel отклоняется с предупреждением). Ошибки `authentication error` / `x509` / `certificate` / `CRYPTO_ERROR` / `timeout` превращаются в понятные сообщения («Неверный пароль», «Сертификат не прошёл проверку: используйте pinSHA256 или insecure», «Сервер не отвечает: проверьте порт или obfs-пароль»). `fatal` и выход процесса переводят в Error с backoff.
- URI: `hysteria2://` и `hy2://`, auth в userinfo с percent-decode (`user:pass` → `auth: user:pass`, как в Hysteria), мульти-порт, `obfs`, `obfs-password`, `sni`, `insecure=1|0`, `pinSHA256`, `ech`, `#name`. Authority разбирается вручную: `net/url` отвергает хосты вида `host:443,20000-50000`. Экспорт делается обратно тем же форматом, без bandwidth и режимов (так требует спецификация).
- Нестандартные ссылки из панелей (Xray, v2rayN, Throne) тоже принимаются:
  - `allowInsecure` → `insecure`;
  - `peer` → `sni`, если `sni` нет;
  - `mport` добавляется к портам;
  - `pcs` (pinnedPeerCertSha256 из Xray) → `pinSHA256`;
  - `fm` (Xray finalmask, JSON `{"udp":[{"type":"salamander","settings":{"password":…}}]}`) → obfs salamander;
  - `obfs-password` без `obfs` → **предполагается salamander**. Сама Hysteria такой пароль молча игнорирует, поэтому это догадка, и она попадает в предупреждения импорта.

  Косметические параметры других протоколов (`security`, `alpn`, `fp`, `type`) пропускаются молча, про неизвестные выводится предупреждение.
- `pinSHA256` задаёт проверку **только по пину**: в YAML добавляется `insecure: true`. Иначе Hysteria проверяет ещё и цепочку CA, и самоподписанный сертификат с правильным пином отвергается.
- Ссылки в тексте и в подписке разделяются по строкам: ссылка идёт до конца строки или до следующей `scheme://`. Поэтому имена с пробелами и emoji (`#🇳🇱 Нидерланды напрямую`) не обрезаются. Имя не служит идентификатором: правила ссылаются на постоянный `id`.
- Маскирование: единый `Redactor` знает текущие auth, obfs-password и SOCKS-креды (в сыром и URL-escaped виде) и заменяет их на `***` во всех логах, включая вывод Hysteria.

## 10. «Соединения» и логи

Flow-запись: `id, pid, process path, dst ip:port, domain, domainSrc (SNI|Host|DNS|Unknown), proto, rule (id/name или «default»/«exclusion»), route, outcome (reflected|passed|relayed|rst: tunnel unavailable|dropped: QUIC blocked…), attrib (как найден процесс: packet|pending|iphelper|pending-timeout|pending-full), stage (где принято решение: packet|sniff|sniff-timeout), sent, recv, start, end`.
- Для relay и UDP-туннеля байты считаются точно. Для Direct на уровне пакетов точно считается только Sent: inbound не перехватывается ради производительности. Recv показывается как «—». Опция «Точная статистика Direct» подключит SNIFF-хэндл на inbound, по умолчанию выключена.
- В UI пушится дельта раз в 500 мс через Wails events. Закрытые соединения хранятся в кольцевом буфере на 5000 записей.
- Счётчик «отклонено» (Tunnel при недоступном туннеле) показывается рядом со статусом.
- «Создать правило» из соединения (`RuleFromFlow.svelte`) собирает правило из полей записи: программа (имя exe), сайт, его домен второго уровня, geosite-списки с этим сайтом (`SiteLists`: `FindSite` без DNS-запросов, узкие списки), IP, порт с протоколом; сайт/IP/порт можно сузить программой. Правило открывается в обычном редакторе и вставляется первым (сохранение с `rev` свежей копии). Для обязательных исключений кнопки нет.
- **Статистика трафика** (`internal/traffic`, `traffic.json`). `flows.Registry.OnTraffic` получает приращения байт туннельных записей: `Sample` раз в 10 с для живых и остаток при `Close` (счётчик `counted` в записи, поэтому ничего не считается дважды); локальные прокси добавляют свои байты из обёрток `tunnelConn`/`tunnelUDP`. В колбэк передаются только ID сервера и имя exe, назначение туда не попадает, поэтому сайтов в статистике нет по построению. Хранится: сумма по дню на сервер (400 дней), на программу (92 дня), по часу на сервер (48 ч), последние имена серверов. Запись — раз в минуту и при отключении, атомарно; битый файл начинает статистику заново. Прямой трафик не считается (у Direct TCP нет Recv).
- Логи Hysteria и движка: кольцевые буферы на 10k строк, фильтр по уровню, поиск, автоскролл, сохранение в файл.

## 11. UI и прочее
- Вкладки: Профили · Правила · Соединения · Лог Hysteria · Лог движка · Настройки.
- Правила: список с drag&drop-сортировкой. Exe добавляется тремя способами: файловый диалог, список процессов с иконками (`SHGetFileInfo` → PNG base64), drag&drop.
  **Риск:** приложение запущено с правами администратора, поэтому UIPI блокирует OLE drag&drop из Explorer (medium integrity). План: `ChangeWindowMessageFilterEx(WM_DROPFILES, WM_COPYDATA, 0x0049)` + `DragAcceptFiles` на top-level HWND. Работоспособность с WebView2 проверю на шаге 4; если не заработает, останутся диалог и список процессов.
- Настройки: «Удалить правило брандмауэра», «Удалить устаревшую службу WinDivert» (активна, только если служба остановлена и указывает не на наш файл).
- Трей: значок двух видов — цветной, пока маршрутизация включена, серый при отключении и при ошибке (`trayIcons`: on/off); меню: «Открыть HyRoute», статус (неактивный пункт), «Подключить»/«Отключить», «Профиль правил: X ▸» (только при двух и больше загруженных профилях правил, §7.2), «Выход». Выбора сервера в трее нет. Значки записываются в `%ProgramData%\HyRoute\runtime` как `tray-<sha256>.ico` и загружаются через `systray.SetIconFromFilePath`: `systray.SetIcon` пишет файл в пользовательский `%TEMP%` под предсказуемым именем. `systray.Quit` при выходе вызывается, только если `systray.Run` уже зарегистрировал трей (`quitTray`); после выхода новый запуск трея не начинается. `systray.Run` крутится в цикле на потоке трея; `watchTray`/`restartTray` закрывают окно `SystrayClass`, пока `trayReady` не отработал (Explorer поднялся позже HyRoute или перезапускался): бэкофф 15 → 60 с, не больше 120 перезапусков. Запуски нумеруются (`tray.gen`), поздний `trayReady` закрытого запуска ничего не рисует; `tray.build` исключает `trayReady` и `restartTray` (порядок build → mu). `TaskbarCreated` пропускается через UIPI только после появления значка. Пока значка нет, окно остаётся на панели задач, крестик его не прячет. Подменю профилей правил (`trayrulesets.go`, `trayrulesets_windows.go`) — постоянный пул из 50 пунктов, который не удаляется (`Remove` в fyne.io/systray закрывает канал щелчков, и щелчок во время перестройки упал бы). Порядок вызовов продиктован systray v1.12.2 на Windows: подменю прикрепляется к пункту, только пока тот виден, поэтому родитель создаётся видимым, пока в него добавляются пункты, и лишь потом всё скрывается; любой сеттер (`SetTitle`, `Check`, `Enable`…) вставляет скрытый пункт, а `Hide` скрытого пишет «systray error». Поэтому при обновлении сначала `SetTitle` родителя, затем сеттеры только нужных пунктов и `Hide` только показанных — это чистая функция `trayPlan` с тестом. Меню читает лёгкий `RulesetsBrief` (только `c.mu`), щелчки слушает одна горутина на запуск трея (`reflect.Select`), переключение идёт в своей горутине с источником «трей»; при ошибке окно открывается. Названия в трее не скрываются (`&` удваивается, длинные обрезаются до 40 символов).
- Порядок `main`: проверка прав администратора, затем `--killswitch-check` (`signInCheck`, §8.1: без оставленной блокировки процесс тихо выходит), и только потом `--wait-pid`, один экземпляр, восстановление обновления и остальное.
- Один экземпляр (`instance_windows.go`): проверка в начале `main`, до любой инициализации, кроме проверки при входе (именованный мьютекс и события в пространстве `Local\` сеанса). Вторая копия показывает окно работающей и выходит; копия, запущенная, пока прежняя ещё завершается (или с `--wait-pid` после переноса), ждёт её выхода и продолжает сама.
- Манифест: `requireAdministrator` в `build/windows/wails.exe.manifest`.
- Расположение программы: `protectedLocation` = путь под `FOLDERID_ProgramFiles`/`ProgramFilesX86` плюс `AccessCheck` ограниченным токеном пользователя (`store.LimitedToken`/`store.Access`) на `FILE_ADD_FILE`, `FILE_ADD_SUBDIRECTORY`, `FILE_DELETE_CHILD`, `WRITE_DAC`, `WRITE_OWNER` для папки программы и папок над ней до корня Program Files и на `FILE_WRITE_DATA`/`APPEND_DATA`/`WRITE_DAC`/`WRITE_OWNER` для `HyRoute.exe`; непрочитанные права считаются разрешающими. Без разделённого токена — только путь. От него зависят автозапуск и проверка kill switch при входе. `MoveToProgramFiles` отказывается от целевой папки, открытой на запись, и пересоздаёт файлы в ней (`copyProgram`), чтобы они получили права папки, а не сохранили свои. Обязателен только `HyRoute.exe`; `hysteria.exe` и WinDivert копируются из runtime-папки (проверенные копии), остальные файлы пропускаются, если их нет. Если HyRoute уже в целевой папке, но права открыты, главная показывает отдельное предупреждение без «Перенести».
- Автозапуск (`internal/autostart`): задача Планировщика у каждого пользователя своя, «HyRoute (<SID>)», регистрируется через COM `RegisterTask` из XML (HighestAvailable, Priority 4 — обычный приоритет вместо фонового 7 по умолчанию, задержка 3 с) и запускает `HyRoute.exe --autostart`. Общая задача прежних версий «HyRoute» считается задачей своего пользователя; `AtLogon` поднимает приоритет процесса до обычного (CPU, I/O, память) и в фоне заменяет такую задачу, если она запускает этот же exe, задачей пользователя. Вторая задача того же вида — проверка kill switch при входе (§8.1). Задача читается (Command, CheckCommand, Disable, миграция) тоже через COM, `ITaskFolder.GetTask(...).Xml`, в UTF-16, а не через `schtasks /Query /XML`: тот печатает в кодовой странице консоли, и путь к exe с кириллицей не разбирался. `schtasks` остаётся только для `/Delete`.
- Папки данных в профиле (`store.Guard`): `%APPDATA%\HyRoute` и его `subs`, `geo`, `run`, `logs` принимаются, только если это обычные папки (не ссылки, без ссылок выше по пути), в которые пользователь может писать сам. HyRoute держит открытыми папку и скрытый системный файл `.hyroute-lock` в ней до выхода: папку нельзя переименовать, подменить или, опустошив, превратить в точку монтирования. Lock-файл создаётся относительно открытого хэндла папки, а не по пути, после чего папка проверяется ещё раз: пустую папку, которую успели превратить в точку подключения между проверкой и созданием lock-файла, Guard не принимает. Если `logs` проверку не прошла, журналы хранятся только в памяти (`SetLogDir`), `crash.log` не пишется. Данные WebView2 лежат не в профиле, а в `%ProgramData%\HyRoute\webview\<SID>` под `core.ProtectDir` (SYSTEM и Administrators — полный доступ, Users — чтение), вызов после `ProtectDir(runtimeDir)`; `store.Guard` для них не используется. Исключение — «Защита администратора» Windows 11: повышенный HyRoute работает под скрытой учётной записью администратора, а WebView2 сам понижает права до связанного (ограниченного) токена пользователя и в защищённую папку писать не может. Если SID связанного токена отличается от SID процесса (`profileSeparated`), папка данных — `%LOCALAPPDATA%\HyRoute\webview` этого пользователя (`KnownFolderPath` по связанному токену). HyRoute её не создаёт и не трогает: её создаёт WebView2, который работает с правами пользователя. Прежняя папка `%APPDATA%\HyRoute\webview` не используется. Если копия файла в общей `%ProgramData%\HyRoute\runtime` отличается от нужной и занята (её загрузил или запустил HyRoute другой версии в другом сеансе), эта сборка кладёт свои проверенные копии в защищённую подпапку `runtime\<16 hex SHA-256 набора имён и хешей>` и работает из неё. Такие подпапки не удаляются автоматически.
- `settings.json` не загружен (битый файл, правила новой версии): в памяти правила по умолчанию, и с ними весь трафик пошёл бы напрямую. Поэтому `Connect` (и «Подключаться сразу после запуска») отказывает с объяснением, пока файл не исправлен и HyRoute не перезапущен; файл не перезаписывается, задача проверки kill switch не меняется (M1). Пока `settings.json` или `proxies.json` не загружен, HyRoute не знает, на какие серверы ссылаются правила и прокси: серверы нельзя удалить, обновление подписки оставляет все пропавшие серверы с пометкой, а удаление подписки делает все её серверы ручными. Если не читается `prefs.json`, журналы пишутся только в память, а базы правил не обновляются в фоне (источник в памяти — по умолчанию, а не ваш), пока файл не исправлен: ручное обновление отказывает с объяснением, а в фоне качается только база, которая нужна правилу и которой нет.
- Локальные прокси (`internal/localproxy`): у каждого прокси лимит одновременных клиентских соединений (`DefaultMaxConns` = 1024, для прокси с доступом из LAN 256). Соединение сверх лимита закрывается сразу, ещё до авторизации; предупреждение в журнал не чаще раза в минуту. Обрыв туннеля или клиента передаётся другой стороне RST, а не FIN, для SOCKS5, CONNECT и plain HTTP, в том числе при Close (Disconnect, переподключение, правка прокси). Если клиент plain HTTP бросил ответ, туннель сбрасывается сразу, и остаток тела с сервера не дочитывается. Ошибка Accept не останавливает порт: повтор через 50 мс → 1 с, в журнал не чаще раза в минуту (то же у relay). `Expect: 100-continue` прокси подтверждает сам (100 Continue клиенту, Expect к серверу не передаётся). `Connection` разбирается как список токенов. Клиент HTTP/1.0 получает тело без chunked, конец тела отмечается закрытием соединения.
- SOCKS5 UDP ASSOCIATE локального прокси (`localproxy/udp.go`): UDP-сокет на том же адресе и номере порта, что и TCP (одно правило брандмауэра на порт: `HyRoute local proxies (TCP)` и `(UDP)` для прокси с доступом из LAN). Каждая ассоциация — своя ассоциация через туннель (`Endpoint.UDPAssociate`: Hysteria привязывает её к первому отправителю). Датаграмма принимается только от IP управляющего соединения и порта из запроса (или порта первой датаграммы, если в запросе 0); чужие и фрагментированные (FRAG ≠ 0) отбрасываются. Ожидающих первой датаграммы ассоциаций с одного IP — не больше 16. Ассоциация живёт, пока открыто управляющее TCP-соединение. Без UDP на сервере прокси (`UDPAvailable`) запрос отклоняется кодом ответа.
- **Резервная копия** (`internal/app/backup.go`). Секреты на диске запечатаны DPAPI под пользователя, поэтому копию папки перенести нельзя. Файл `.hyroute` — JSON `{format, version, kind, created, app, sealed|data}`. `kind: full` — профили с auth/obfs, подписки с URL, `settings.json`, прокси с паролями, prefs (без `skipVersion`); всегда зашифрован: PBKDF2-SHA256 (600 000 итераций, соль 16 байт) → AES-256-GCM, заголовок `format/version/kind` — AAD, так что подмена вида копии ломает проверку. `kind: rules` — только `settings.json`, открытым текстом. Восстановление — только при отключённом VPN (под `lifeMu`/`saveMu`), настройки проверяются `settings.Parse` до записи; ссылки правил на серверы, которых нет, переводятся на основной сервер (`remapProfiles`, число — в ответе). Запись: profiles, subscriptions (снимки старых подписок удаляются), proxies, prefs, settings, затем `Load()`; сбой посередине перечитывает то, что на диске. После — kill switch и базы правил, как после сохранения настроек.
- Уведомления (`frontend/src/toast.svelte.ts`, `lib/Toasts.svelte`): внизу справа, над диалогами, в порядке табуляции сразу после страницы. Видно до 3, остальные ждут в очереди; при очереди больше 10 первыми отбрасываются уведомления без кнопок, а уведомления с кнопками сверх 20 сворачиваются в сводку своей группы (`setFold`). Текст и надписи — функции, поэтому Privacy mode действует и на уже показанные. 8 с (ошибка 12 с); таймер стоит, пока на уведомлении курсор или фокус. `expireUndo` снимает «Отменить», когда Go уже не хранит операцию. Две live-области есть в странице всегда, даже пустые (иначе экранный диктор не объявит первое уведомление): ошибки — `role="alert"` (выше), остальное — `role="status"`, `aria-live="polite"`. Закрытое уведомление с фокусом передаёт его уведомлению на своём месте, а если их нет — `<main>`.

## 13. Тесты (unit, без драйвера, гоняются на Linux и Windows)
- `packet`: checksum (известный вектор + эталонная реализация), v4/v6, IPv6 extension headers, фрагменты, сборка UDP-ответа, RST на SYN.
- `engine/nat`: reflect-переписывание v4/v6, двусторонний lookup, коллизия `(R, lp)`, повтор SYN, замена закрытой записи, FIN/RST/грейс/idle.
- `divert`: раскладка `WINDIVERT_ADDRESS` (80 байт, битовые поля), декодирование SOCKET/FLOW-данных и host-order адресов, разбиение батча, фильтр (исключения без `!=`), тексты ошибок, проверка версии.
- `attrib`: точный ключ, IPv4-mapped, неуказанный local IP, bind, закрытие только своего endpoint'а, уведомления, чистка, разбор таблицы TCP IP Helper и снимок (владелец, LISTEN).
- `socks5`: CONNECT с user/pass, отказ авторизации, ошибки REP, домен, отмена по контексту, UDP ASSOCIATE.
- `relay`: туннель end-to-end через заглушку, half-close, хвост доходит до приложения, которое поставило чтение на паузу; RST при Close, пока хвост не подтверждён; RST от приложения завершает ожидание; Close с ограниченным ожиданием обработчиков, RST при недоступном туннеле (и ничего не уходит в upstream), RST при ошибке SOCKS, посторонние подключения, Close с активными соединениями, RST при Close, отмена ожидающего dial, передача сброса на другую сторону, Direct с адреса приложения, запросы к forward-прокси.
- `hysteria`: URI parse/gen (мульти-порт, percent-encoding, `hy2://`, IPv6, нестандартные параметры, ошибки), round-trip, генерация YAML (golden files), лог-парсер и классификация ошибок, supervisor с фейковым hysteria (подключение, туннель, удаление конфига, backoff при auth-ошибке, секреты не попадают в лог).
- `procinfo`: переиспользование PID.
- `rules`: домены (exact, `*.`, `.`, регистр, trailing dot, IDN/punycode), app (name/path/glob, наследование, неизвестный процесс), first match, составные правила, трёхзначный Evaluate (DNS-имена сходятся/расходятся, ветви сходятся, правила другого приложения не создают неоднозначности), `EvaluateSites` (имена CNAME-цепочки — один сайт), `MayTunnel`, ошибки компиляции.
- `dnscache`: TTL и его ограничения, несколько имён на IP, смена IP, CNAME-цепочки, IDN, отказ от запросов/NXDOMAIN/мусора, DNS over TCP, лимит размера, ответ принимается только на увиденный запрос, сайты CNAME-цепочек, ограниченный Sweep, публичные имена ECH из HTTPS-записей, ответ через туннель только на туннельный запрос.
- `sniff`: настоящий ClientHello из `crypto/tls`, фрагментация по сегментам и по TLS-записям, без SNI, IP в SNI, ECH (внешний SNI сохраняется), мусор, обрезанные данные, HTTP Host с портом, IP-литералы.
- `relay` (SNIFF): SNI → Tunnel с remote DNS, Host → Direct с неизменным буфером, таймаут, server-first порты, Block, туннель недоступен, NO-SNIFF всегда по IP.
- `engine` (ядро, синтетические пакеты): reflect туда и обратно, Direct со счётом байт и закрытием по FLOW_DELETED, RST при недоступном туннеле, IPv6-блок, Block по DNS-домену, SNIFF при неизвестном домене и решение relay, поздняя атрибуция, таймаут, IP Helper, исключения self и системного DNS, посторонний inbound на relay, блок QUIC, UDP Direct, UDP-туннель end-to-end через SOCKS5-заглушку (ответы собираются в пакеты), drop при недоступном туннеле, истечение сессий, DNS-сниф → решение на уровне пакетов, `exclusion: hysteria`, DoH/DoT Dnscache, переполнение pending + IP Helper, повторное использование порта закрытой NAT-записи, RST при остановке движка, перевыбор профиля UDP-потока, фрагменты не-TCP/UDP, IPv6 AH, соединения без состояния (открытые до старта): Tunnel/Block → RST с seq = ACK, Direct и исключения проходят, серверная сторона входящих соединений проходит, домен только из DNS cache, одно чтение таблицы IP Helper на много соединений, ограниченная память решений; RST отражённых соединений при отказе движка, без зависания на блокировках; решение по ECH в `RelayDecide` (GREASE ECH, известное публичное имя), IPv6-SYN с доменным правилом в туннель сбрасывается сразу.
- `settings`: значения по умолчанию, неизвестные поля, перезагрузка файла, битый файл не заменяет правила.
- `settings`: опции движка покрывают все поля вне правил (`TestEngineOptionsCoverSettings`).
- `app` (§7.3): ревизия и событие на каждую запись (`TestSettingsRevAndEvent`), отказ устаревшей копии и отсутствие ложных отказов после записи опций (`TestSaveSettingsRevision`), опции отдельно от правил (`TestSaveEngineOptions`), «Правила текстом» с ревизией, параллельные писатели, сбой записи ничего не меняет, в `settings.json` нет новых ключей.
- `store`: `readRegular` читает только обычный файл с одним именем в пределах лимита; жёсткая и символическая ссылка, папка, точка соединения (Windows, без прав администратора) отклоняются.
- `store` (§7.2): `rulesets.json` — строгий разбор, профиль «новее» с сохранением байтов, отказы (версия, ID, имена, отметка, размер), только обычный файл, `ConfigHash`, запись пары с возвратом прежних байтов при сбое `settings.json`; `ReadRaw`/`WriteRaw` не следуют по ссылкам.
- `rules`: `Check` без баз правил отклоняет то же, что `Compile`, и не обращается к базам.
- `app` (§7.2): файла нет до второго профиля; записи S/R/P и отметка (`TestMarkerForcesPair`); сверка при загрузке (прерванная запись, правка снаружи и возврат к прежним правилам, нет `settings.json`, битые файлы, профиль с ошибкой); токены и ревизии обоих режимов (`TestEditModeRevision`, `TestActiveRevisionRulesAt`, `TestEditorTokenCapturedAtOpen`); `Stopped`; отказ до `netManual`; нет компиляции под `c.mu`; «новее»; ссылки из неактивных профилей; параллельные переключения и правки под `-race`.
- `main`: `trayRulesetsView`, `trayPlan` — порядок вызовов systray.
- `rules`: `Registrable`/`Site`/`HostName` (публичные суффиксы, IP и короткие формы IPv4 вроде `1.2.3`, цифровой домен верхнего уровня, IDN, длины меток 63 и имени 253/254).
- `engine`: вид исключения (`self`/`hysteria`/`system-dns`) записывается в `Excluded`, правило пользователя с именем «exclusion: …» исключением не считается.

## 15. Шаг 4c: несколько профилей одновременно, подписки, обновления

### 15.1 Оценка влияния на текущую модель

До 4c в модели было ровно одно «активное» соединение. Эта мысль зашита в шести местах, и её пришлось убрать до того, как UI вырастет:

| Место | Было | Стало |
|---|---|---|
| `rules.Rule` | `action: tunnel` без указания, куда | `action: tunnel` + `profile: <ID>`. Пустой `profile` означает «основной профиль» (§15.2). `fallback: [ID, …]` — запасные профили ("" = основной), у маршрута по умолчанию `defaultFallback` |
| `rules.Set.Evaluate` | Сравнивал только действие (`Tunnel == Tunnel`) | Сравнивает **маршрут** = действие + профиль. Правила `Tunnel → DE` и `Tunnel → NL` для одного IP с разными доменами дают `NeedsDomain`, а не молча DE |
| `rules.Result`, `nat.Entry`, `flows.Record` | Нет профиля | `Profile` (стабильный ID) у результата, NAT-записи (NO-SNIFF знает профиль заранее), UDP-потока и записи «Соединений» |
| `engine.Core` / `relay.Server` | Одно поле `Tunnel` | `Tunnels.Get(profileID)`: у каждого профиля свой SOCKS5. Неизвестный или удалённый профиль даёт `nil`, соединение отклоняется (RST/drop), **никогда** не уходит в другой профиль или Direct |
| UDP-сессии | Ключ: сокет приложения `L:lp` | Ключ: `(L:lp, profile)`. Один сокет может слать в DE и NL одновременно, это две разные UDP ASSOCIATE |
| `hysteria.Supervisor` | Один на сеанс, секреты в `Redactor.Set` (замена всего набора) | Один на профиль, их держит `tunnels.Manager`. У каждого свои статус, backoff, SOCKS-порт, счётчики и журнал. Redactor хранит секреты группами по профилю (`SetGroup`) |
| Исключение IP сервера | `SetServerIPs(ips)` одного supervisor'а | Manager собирает **объединение** IP всех запущенных профилей (и временных проверок, §15.6) и отдаёт его движку. Горячая замена фильтра остаётся той же |
| `app.Status` | Один статус | Общий статус маршрутизации + список профилей: `connecting / connected / error`, сообщение, SOCKS-порт, рестарты, отклонено, байты |

Что осталось без изменений: WinDivert-хэндлы, reflect-NAT, relay, sniff, DNS-кэш, fail-open. Поток решает маршрут один раз (как и раньше), а маршрут теперь просто несёт профиль.

### 15.2 Запуск профилей: только нужные

- «Подключить» означает «включить маршрутизацию». Manager запускает Hysteria **только** для профилей, на которые ссылаются включённые правила и маршрут по умолчанию (`rules.Set.Profiles()`).
- Правила сохраняются «на горячую»: Manager сверяет набор нужных профилей и запускает недостающие, останавливает ненужные. Соединения через остановленный профиль рвутся, новые идут по новым правилам.
- Правка профиля, который сейчас запущен, перезапускает только его Hysteria.
- **Основной профиль** (бывший «активный»). Правило `Tunnel` без явного профиля и `defaultAction: tunnel` без `defaultProfile` идут через него. Это не переключатель «одного соединения»: DE, NL и основной работают одновременно. Зачем он нужен:
  - старые настройки продолжают работать без миграции;
  - одним выбором в шапке можно сменить сервер у всех правил, которым конкретный сервер не важен.
- Падение одного профиля затрагивает только его маршруты: они получают RST/drop и попадают в счётчик «отклонено» этого профиля. Direct и другие профили не затронуты.
- Fallback (`DE → NL → отказ`): `Result.Fallback` несёт запасные профили, `Core.pick` в момент решения берёт первый профиль цепочки, который может нести соединение (`Available`, для UDP `UDPAvailable`), и дописывает к правилу « (fallback)». Если недоступны все, решение остаётся на основном профиле и соединение отклоняется, как без fallback: напрямую Tunnel не уходит никогда. Запасные профили запускаются вместе с основным (`Set.Profiles`), поэтому переключение мгновенное. Уже открытые соединения через упавший профиль рвутся, новые идут через запасной, а после восстановления основного снова через него. В тексте правил: `-> DE -> NL` или `-> DE, NL`; `-> блок` в конце цепочки допустим и ничего не меняет. Запасной, совпадающий с сервером маршрута или повторяющий основной (в том числе после смены основного), интерфейс показывает зачёркнутым и удаляет из правила при сохранении настроек. Элемент цепочки (и сам сервер маршрута) может быть группой серверов (§15.7): `Core.pick` разрешает её в сервер группы в том же проходе по цепочке.

### 15.3 Идентичность профилей и подписки

- У каждого профиля постоянный случайный `id`. Правила ссылаются только на него, никогда на позицию или имя.
- `source`: `manual` или `sub:<subID>`. Профили подписки хранятся в общем `profiles.json` и в правилах используются так же, как ручные.
- **Обновление подписки** проходит в три шага: скачать, разобрать, проверить. Только если всё прошло, данные подписки заменяются атомарно. Ошибка сети или разбора оставляет старый список и записывается в `lastError`.
- **Смена ссылки:** новая ссылка сначала проверяется (`PreviewSubscription`). `EditSubscription` с токеном предпросмотра сохраняет URL и применяет уже скачанное тело как обычное обновление (снимок, профили, статус), без второго скачивания. Непроверенную ссылку сохранить нельзя (в `SubInput` нет поля `url`).
- **По очереди:** обновление, откат, смена ссылки и первый импорт одной подписки выполняются по очереди (`lockSub`, берётся до `mu`). Повторное обновление (планировщик и кнопка) ждёт текущее и скачивает заново. Разные подписки обновляются параллельно. Удаление подписки не ждёт: обновление, которое идёт в этот момент, увидит, что подписки нет, и ничего не сохранит.
- **Сопоставление при обновлении.** Нужно, чтобы правила не «переехали» на чужой сервер. Сопоставление строго один к одному, в три прохода по убыванию уверенности:
  1. та же ссылка без имени, то есть все параметры подключения совпадают;
  2. тот же `host:ports`;
  3. то же имя.
  Совпавший профиль сохраняет `id` и обновляет поля из ссылки. Настройки, которых в ссылке нет (скорость, интервалы port hopping, congestion, QUIC, fast open, CA, «Резолвить адрес в HyRoute»), остаются пользовательскими: обновление их не сбрасывает и Hysteria из-за них не перезапускает. Редактор сервера из подписки предупреждает, что поля из ссылки (название, адрес, пароль, obfs, SNI, pinSHA256, insecure) при обновлении подписки заменяются. Новый получает новый `id`. Исчезнувший:
  - если на него ссылается правило или локальный прокси (или это основной профиль), остаётся с пометкой `missing`. При удалении подписки такие профили становятся ручными. Правило показывает «Профиль больше отсутствует в подписке» и предлагает выбрать замену. Трафик не подменяется молча другим сервером;
  - если не используется, удаляется;
  - пока `settings.json` или `proxies.json` не загружен, ссылки правил и прокси неизвестны: все пропавшие серверы остаются с пометкой, а удаление подписки делает все её серверы ручными.
- **Формат.** Список `hysteria2://` / `hy2://` (по строкам или через пробелы) или тот же список в base64 (std/url, с паддингом и без), распознаётся автоматически. Остальные схемы (`vless://`, `vmess://`, `ss://`, `trojan://`, `tuic://`, `hysteria://` v1 …) пропускаются и считаются. YAML Clash и JSON sing-box не разбираются: пользователь получает понятную ошибку.
- **Preview перед добавлением:** «Найдено 14 Hysteria-профилей, 23 записи других протоколов проигнорированы». Сохраняется ровно то, что было показано: повторного скачивания нет.
- **Снимки.** Последнее успешное содержимое и предыдущее хранятся зашифрованными (DPAPI) в `subs\<id>.cur` / `.prev`. «Откатить» заново применяет предыдущий снимок по тем же правилам сопоставления. Тот же набор серверов (те же параметры подключения, даже если панель поменяла имена — например, дописала остаток трафика — или их порядок) снимки не сдвигает: текущий снимок перезаписывается, а предыдущий остаётся, так что откат после повторных обновлений возвращает прежнюю версию. Сначала сохраняются профили, затем снимок. Откат переставляет снимки только после того, как профили сохранены, поэтому неудачный откат ничего не меняет. Любая ошибка обновления, в том числе ошибка сохранения, записывается в `lastError`, и следующая попытка идёт по обычному расписанию повторов.
- **Секретность URL.** URL хранится зашифрованным (DPAPI, как пароли). В логах и диагностике показывается только `https://host/…`. Запрос идёт напрямую (собственный трафик HyRoute не маршрутизируется) и только на сервер подписки, с `User-Agent: HyRoute/<версия>`.
- **Интервалы:** вручную / при запуске / 6 ч / 12 ч / 24 ч. Планировщик в контроллере проверяет раз в минуту. Неудачное обновление «при запуске» (при входе в Windows сети часто ещё нет) повторяется раз в 15 мин до первого успеха.
- **Информация подписки.** Из ответа 200 читаются заголовки `subscription-userinfo` (upload, download, total, expire), `profile-title`, `profile-update-interval` и `support-url` (`panelHeaders`, `internal/app/subinfo.go`). Каждое значение ограничено по длине до разбора (userinfo 1 КБ, ссылка 2 КБ, заголовок до декодирования 4 КБ), все заголовки ответа — 64 КБ (`MaxResponseHeaderBytes` на `directTransport`). Числа — целые в `[0, 2^62]`, дробные отбрасываются; `expire` ≥ 1e11 считается миллисекундами, а срок после этого всё ещё ≥ 1e11 (после 5138 года) или раньше 2000 года (так выглядит «бессрочное» значение в секундах вроде 253402300799) отбрасывается. В `subscriptions.json` пишется каноническая форма (`userInfo`, тот же синтаксис, что читает 1.0.0) и время получения `infoAt`; файл пользователь может менять, поэтому `userInfo` разбирается заново при каждом чтении. Название очищается от управляющих, форматирующих (bidi, нулевой ширины) и private-use символов. Уровни: трафик `low` при остатке < 10 % (проверка делением, без умножения значений заголовка), `out` — израсходован; срок `low` < 72 ч, `out` — истёк; `total` = 0 или ≥ 1 ПиБ — «без лимита». Предупреждения (`Status.subAlerts`) для всех подписок, независимо от автообновления: срок считается всегда (он живой), трафик — только если известно время цифр (`infoAt`, иначе `lastUpdate`), старше 48 ч — с датой «данные сервиса на …». Ключ `уровень|t<уровень трафика, если он учтён>|e<уровень срока>|total|expire` держит «Скрыть» в WebView (`hyroute.subAck`) до смены положения; забытые подтверждения чистятся только при `Status.subsOK` (список подписок загружен). Ответ 200 с неразбираемым телом (панель истёкшего аккаунта) сохраняет цифры вместе с ошибкой; откат оставляет цифры и датирует их прежним `lastUpdate`, если `infoAt` не было. Ссылка поддержки публична (одна на панель), хранится открыто (`supportUrl`), проверяется `safeLink` (только `http(s)` с хостом, без userinfo, управляющих и форматирующих символов) при каждом показе и открытии и открывается только по ID подписки через Explorer (`OpenSubscriptionSupport`), никогда повышенным процессом. На маршрутизацию информация не влияет: ничего не отключается и не переключается.

### 15.4 Логи на диске, Privacy mode, диагностика

- **Логи.** Настройка «Хранить логи на диске» (по умолчанию включена). Выключено — только кольцевые буферы в RAM. Включено:
  - `logs\hyroute.log` и `logs\hysteria-<id>.log` для каждого профиля;
  - ротация по размеру (по умолчанию 5 МБ) и числу старых файлов (по умолчанию 3); копии с номерами больше текущего «Старых файлов» (например, после уменьшения настройки) удаляются при следующей ротации;
  - папка логов задаётся после загрузки настроек: при выключенной настройке ни одна строка запуска на диск не попадает;
  - кнопки «Очистить логи» и «Открыть папку».
- **Секреты вырезаются всегда:** auth, obfs, SOCKS-креды, URL и токены подписок.
- **Privacy mode** только меняет отображение, внутренний лог остаётся как есть. Маскируются:
  - публичные IPv4/IPv6 (`85.xxx.xxx.249`, `2a01:xxxx:…`), приватные и loopback остаются;
  - доменные имена (SNI, Host, имена из DNS), в том числе в Unicode (`.рф`) — остаётся только зона: `***.com`, имена файлов (`hysteria.exe`) не трогаются. md, zip и new — ещё и доменные зоны, поэтому имя вида `999.md` или `example.zip` маскируется как домен; именем файла считается только имя с ещё одним расширением перед ними (`geosite.dat.new`);
  - хосты серверов профилей;
  - URL подписок.
  Окно «Правила текстом» при включённом режиме показывает текст через `hide()` в режиме только для чтения, без автодополнения и результатов разбора; «Показать и редактировать» раскрывает его на один визит (сбрасывается при закрытии окна и при повторном включении режима).
  Кнопки «Копировать» копируют уже скрытый вариант. Экспорт лога спрашивает, какой вариант сохранить: оригинал или очищенный. Маскирование одно на стороне Go (`logx.Sanitizer`) и повторено в TS для отображения; тест держит их в согласии.
- **Диагностика** — текстовый отчёт:
  - версии HyRoute, Hysteria и WinDivert;
  - драйвер и правило брандмауэра;
  - relay и его порт;
  - каждый профиль: состояние, SOCKS-порт, рестарты, последняя ошибка;
  - подписки: время обновления, число профилей, ошибка, остаток трафика и срок;
  - последние понятные ошибки.
  Кнопка «Скопировать диагностику» учитывает Privacy mode, секреты вырезаны всегда.

### 15.5 Проверка профиля и «Почему сюда?»

- **«Проверить профиль».** Если профиль уже запущен, используется его Hysteria. Если нет, Manager запускает временную: её IP сервера добавляется в исключение, чтобы проверка не пошла в другой туннель. Исключения хранятся по экземпляру (уникальный ключ на каждый запуск Hysteria), а не по профилю, поэтому ещё не остановленная временная Hysteria не снимает исключение следующей проверки того же профиля. Проверяется:
  - TCP через SOCKS: HTTPS-запрос к `https://api.ipify.org`, результат — внешний IP и latency;
  - UDP: DNS-запрос к 1.1.1.1 через UDP ASSOCIATE, если сервер разрешает UDP;
  - на каждом шаге понятная ошибка.
- **«Почему этот адрес пойдёт сюда?»** `rules.Set.Explain(app, домен или IP)` возвращает трассу по всем правилам: совпало / почему нет (приложение, протокол, домен), победитель, действие и профиль. Для IP показываются имена из DNS-кэша по сайтам, если движок запущен (цепочка CNAME — один сайт, правило срабатывает по любому её имени); если сайты расходятся, решение показывается без имени (так решает движок, если SNI/Host не дал имени), а в заметке — какое правило сработает для каждого имени. Программа без расширения («chrome») проверяется как chrome.exe. Цепочку родителей (наследование) по имени exe не проверить: объяснение это оговаривает. Порт и протокол задаются в «Проверить адрес»; без порта он берётся из адреса (`x.com:8443`, `[2001:db8::1]:443`) или из ссылки (`https://` → 443, `http://` → 80), о чём говорит заметка, а порт из поля важнее (заметка «Порт из адреса (443) не учтён»). Без порта правила с портами считаются несовпавшими. UDP 443 при настройках QUIC по умолчанию объясняется без имени, как решает движок: если маршрут зависит от имени, победитель — синтетический шаг «Блокировка QUIC» (`rules.StepQUICBlock`, индекс −2).
- **Линтер правил:**
  - правило, полностью перекрытое вышестоящим, «никогда не сработает»;
  - `Tunnel` на отсутствующий или удалённый профиль;
  - `*.x` при явной нужде в `x`: подсказка;
  - сайт, который не может совпасть ни с одним именем (`rules.SiteProblem`: невозможные символы или пустые части имени), — предупреждение: `Compile` такие элементы сохраняет, чтобы старые настройки загружались, а «Правила текстом» отклоняют их как ошибку.

### 15.6 Обновления

**Ядро Hysteria** обновляется отдельно от HyRoute:
- проверяются `apernet/hysteria` releases, только стабильные с тегом `app/v2.*` (совместимость — мажор 2);
- ассет `hysteria-windows-amd64.exe` сверяется с `hashes.txt` того же релиза и с дайджестом ассета из API GitHub;
- ядра лежат в `%ProgramData%\HyRoute\core\<версия>\` с защищённым DACL: SYSTEM и Administrators — запись, Users — чтение. Если бы они лежали в `%APPDATA%`, процесс без админских прав мог бы подменить exe, который HyRoute запускает с правами администратора. Владельцем папки ставится Administrators (владелец сохраняет WRITE_DAC при любом DACL); папку, созданную заранее не администратором, HyRoute не принимает; путь `%ProgramData%` берётся из `KnownFolderPath`, а не из переменной окружения. Папки создаются сразу с защищённым DACL (CreateDirectory с дескриптором), без промежутка с DACL, унаследованным от `C:\ProgramData`. `core.json` читается, только если он и папка `core` принадлежат Administrators/SYSTEM/TrustedInstaller; иначе обновление ядра не используется (работает встроенное, в разделе обновлений показывается причина). Папку `updates`, созданную не администратором, HyRoute при старте не очищает;
- `core.json` хранит `current`, `previous` и их SHA256; хэш сверяется перед каждым запуском;
- новое ядро проверяется запуском `hysteria.exe version`. Если `hysteria version` не ответил, ошибка запоминается на минуту, потом проверка повторяется; пока версия текущего ядра неизвестна, обновление ядра не предлагается (показывается ошибка);
- во время активного соединения переключение не происходит: оно применяется при следующем подключении или по кнопке «Переподключить»;
- если новое ядро не стартует (процесс сразу падает не из-за сервера), доступен откат на `previous`, а статус подсказывает это;
- если встроенное ядро не старше скачанного (вышла новая версия HyRoute), работает встроенное. Скачанные ядра удаляются при первом запуске после подтверждённого обновления HyRoute: пока существует `update-journal.json` (новая версия ещё не прислала сигнал «здоров»), они остаются, чтобы прежняя версия после отката снова их нашла. Откат на `previous`, который не новее встроенного, тоже приводит к встроенному; после отката на встроенное ядро кнопки отката нет.

**HyRoute** обновляется через GitHub Releases своего репозитория. Репозиторий задаётся при сборке, `-X main.updateRepo=owner/repo`.
- Канал Stable берёт последний релиз без `prerelease`. Канал Beta предусмотрен в модели (берёт и `prerelease`; prerelease-версии сравниваются по semver: beta.10 > beta.9), в UI пока скрыт.
- Релиз — это `HyRoute-<ver>-windows-amd64.zip` + `SHA256SUMS`. Пакет собирает workflow `release.yml` по тегу `v*`. Версию сборки и имя пакета workflow задаёт явно (`HYROUTE_VERSION` = пушнутый тег); `build.ps1` и `package.ps1` падают, если HEAD не этот тег. Локально без переменной версия по-прежнему берётся из `git describe`.
- **Ход обновления:**
  1. Показать текущую и новую версию и changelog (тело релиза), кнопки «Обновить / Позже».
  2. Скачать в `%ProgramData%\HyRoute\updates\<ver>\`, сверить SHA256 (`SHA256SUMS` + дайджест API), распаковать, сверить каждый файл. Если за время загрузки проверка нашла другую версию, скачанный пакет не предлагается: загрузку нужно повторить; вторая загрузка параллельно не запускается.
  3. Штатно остановиться: снять фильтры, закрыть WinDivert, остановить все Hysteria.
  4. Запустить **отдельный** `hyroute-updater.exe` из новой версии, скопированный в staging, и выйти.
- **Работа updater'а:**
  1. Ждёт завершения PID HyRoute без лимита и заново сверяет хэши. Если exe переименован, HyRoute передаёт `--exe`, и заменяется именно этот файл.
  2. Каждый заменяемый файл: `X` → `X.old`, новый копируется на место. Любая ошибка — откат всех `.old`.
  3. Запускает новый HyRoute с `--updated-from <старая версия>` и ждёт сигнала «здоров» (именованное событие) до 3 минут. Нет сигнала или процесс упал — откат и запуск старой версии (updater передаёт ей `--update-failed <целевая версия>`; раньше передавалась заменяемая); если до обновления HyRoute был подключён, она получает `--reconnect` и подключается снова. «Подключаться сразу после запуска» после отката тоже работает.
  4. `.old` удаляются только после сигнала.
- **Ограничения:**
  - Целостность проверяется по SHA256. Подпись релизов своим ключом (ed25519) — следующий шаг, если понадобится защита от компрометации аккаунта GitHub.
  - **Приватный репозиторий:** API GitHub без токена релизы не отдаёт. Для автообновления нужен публичный репозиторий, хотя бы отдельный `HyRoute-releases`.
  - Сборки без тега (`dev`) по умолчанию не проверяют обновления автоматически, ручная проверка работает.
  - У загрузок (обновления, ядро) нет общего таймаута: загрузка обрывается, только если сервер ничего не присылает 60 с.

- Журнал обновления (`internal/update/journal.go`): до первой замены updater записывает план (какие файлы заменяются, какие добавляются) в `%ProgramData%\HyRoute\update-journal.json` с fsync. Журнал удаляется только после сигнала «новая версия работает» (Commit) или полного отката. Если updater умер посередине (питание, kill), следующий запуск HyRoute без `--update-event` находит журнал, откатывает то, что успело замениться (файлы с `.old`, недописанные `.new`, добавленные), запускает восстановленный exe (с `--autostart`, если сам был запущен задачей входа) и выходит: он сам мог быть новым exe. Это делается, только если `%ProgramData%\HyRoute` и журнал принадлежат Administrators, SYSTEM или TrustedInstaller (текущему пользователю — только без разделённого UAC-токена; проверка до чтения файла) и `target` журнала совпадает с папкой запущенного exe: этот код работает с правами администратора, а папку мог создать обычный процесс. Имена в журнале — только простые имена файлов; поле `exe` хранит имя заменяемого exe. Запущенный exe нельзя удалить, но можно переименовать: он откладывается как `<имя>.<наносекунды>.bad` и удаляется при следующем старте; другие файлы `*.bad` в папке программы не трогаются. Журнал хранит `reconnect` (HyRoute был подключён до обновления), и восстановление передаёт прежней версии `--reconnect`. Updater, чей PID записан в журнале, считается живым, только если процесс с этим PID создан не позже `started` (иначе номер занял другой процесс).
- Сигнал «работает»: окно загружено и, если до обновления HyRoute был подключён (`--reconnect`), `Connect` вернулся успешно — драйвер открыт, фильтры стоят. Недоступный сервер откат не вызывает. Ожидание updater — до 3 минут, потом откат и запуск прежней версии.

### 15.7 Группы серверов

Группа — именованный упорядоченный список серверов и стратегия выбора. Это цель маршрута, как сервер: её ID стоит в тех же полях (`Rule.Profile`, `Rule.Fallback`, `DefaultProfile`, `DefaultFallback`, `LocalProxy.Profile`, основная цель). Новых полей в `settings.json`, `proxies.json` и `profiles.json` нет.

- **ID и файл.** Серверы и группы делят одно пространство ID: у сервера 12 hex, у группы `grp-` + 12 hex (`groups.ValidID`, `IsGroupID`). Группы, настройки пробы и основная группа лежат в `groups.json` (формат 1, строгий разбор, до 1 МиБ, чтение через `readRegular`). Файл пишется, только когда пользователь пользуется группами: создаёт, меняет или удаляет группу, меняет пробу, выбирает или снимает основную группу, удаляет сервер, который есть в группе. Все записи идут через `saveGroupsLocked`: висящие ID серверов убираются из всех групп (`Prune`), весь файл проверяется правилами загрузки (пустая группа допустима), затем `installGroupsLocked` — то же, чем пользуется восстановление из копии. Пока `groups.json` или `profiles.json` не загружен, запись запрещена (с пустым списком серверов `Prune` вычистил бы всех участников).
- **Основная цель.** `mainTargetLocked()` — единственное место: `main` из `groups.json`, иначе активный сервер `profiles.json`. Основная группа живёт только в `groups.json`, поэтому после отката на v1.0.0 основным остаётся сервер. Если `groups.json` битый, основная группа берётся из снисходительного чтения (`MainOf`): её соединения отклоняются, а не уходят через другой сервер.
- **Где выбирается сервер.** Только в `Core.pick(res, udp, Hint)` (`engine/groups.go`), в момент решения о новом потоке. Разрешение в две фазы: сначала цепочка (цель, затем запасные) просматривается без изменений состояния (`Peek`/`PeekUDP`) — берётся первая здоровая цель, иначе первая «деградированная»; потом выбор фиксируется (`Choose`/`ChooseUDP`) только на этой цели. Поэтому деградированная группа раньше в цепочке не двигает свой круг и текущий сервер, когда поток ушёл дальше. Без групп в цепочке путь прежний, бит в бит. IPv6-поток, который всё равно отклонит блок IPv6, только просматривает. Устаревший путь фрагментов (`fragRoute`) `pick` не вызывает. `Hint` — программа, сайт и IP: сайт берётся из имени, увиденного у этого соединения (SNI/Host, CONNECT прокси), иначе из DNS-кэша, если все имена адреса — один сайт (`SiteOf`), иначе ключ — IP.
- **Стратегии.** «По порядку» (с возвратом на первый: член, здоровый без перерыва 30 с, забирает новые соединения), «Самый быстрый» (EWMA задержки, α = 0,3; переход, только если другой быстрее больше чем на порог, по умолчанию 50 мс), «По кругу» (один счётчик на TCP и UDP), «Случайно», «Закреплять сайт» (rendezvous-хэш «программа + сайт»: при уходе сервера двигаются только его ключи). Здоровый член = `usable` (как у сервера) и без штрафа: серия неудачных соединений к разным адресам (опция «после N ошибок», штраф 60 с, затем ровно одно пробное соединение, `TrialTimeout` 15 с) или две неудачные пробы подряд, когда через другой член группы проба с тех пор прошла. Если здоровых нет, используются просто работающие (деградация), после того как вся цепочка проверена на здоровые. `ChooseUDP` пробных соединений не берёт и текущий сервер не двигает. `Pick.Failover` (для статистики) — выбор деградированный или член, которого выбор взял бы при здоровье всех, недоступен.
- **Сигналы здоровья.** Только от рабочих конечных точек: `tunnels.Manager.OnHealth` (статус) и `OnDial` (каждый Dial и UDP ASSOCIATE, кроме отменённых и помеченных `tunnels.Quiet` — ими ходит «Проверить» сервера). Временные конечные точки проверок ничего не сообщают. Заглушка SOCKS5 тоже сообщает статус через хуки. `ResetSession` при подключении обнуляет всё, что могло штрафовать (серии, пробы, время работы, отклонения), и текущий сервер групп «по порядку» с возвратом.
- **Проба задержки.** `Prober` раз в 5 с берёт членов используемых групп, которые работают сейчас, и тех, чья проба устарела (интервал по умолчанию 60 с) или кто только что подключился, до 8 одновременно. `GET` на адрес пробы (по умолчанию `http://cp.cloudflare.com/generate_204`) только через SOCKS5 члена, время до первого байта, 5 с на всё, чтение ограничено строкой статуса (1 КиБ), редиректов нет, TLS проверяется. Проба, прерванная отключением или бюджетом, не считается отказом. После пробы текущий сервер групп «по порядку» и «самый быстрый» пересчитывается (только он: без пробного соединения и шага круга). «Проверить» у группы работает и без подключения: рабочие члены проверяются на месте, остальные через временный Hysteria (до 4 сразу, всего 60 с, не больше одной проверки на группу; при подключении — только если в исключениях есть место для 4 адресов).
- **Что работает.** Две разные «используемости»: ссылки (правила, в том числе выключенные, маршрут по умолчанию, запасные, прокси, основная) защищают группу от удаления и от опустошения подпиской (`groupUsedLocked`, `groupPinsLocked`); запуск серверов, пробы и проверки в статусе следуют включённой маршрутизации (`usedGroups` из `routingLocked`). Сервер, который используется только через группы, не переводит статус в «сервер недоступен», пока у группы есть рабочий член; группа, у которой не работает никто, — переводит («Группа «X»: все серверы недоступны»).
- **Блокировки.** Состояние групп в контроллере под `c.mu`, `probeStop` под `lifeMu`. `groups.Runtime.mu` — самая внутренняя блокировка: колбэк `usable` (блокировка менеджера туннелей) вызывается до неё, журнал и `OnSwitch` — после. Определения меняются атомарно (`SetGroups`), решение читает их без блокировки.
- **Отказ — закрыто.** Группа без рабочих членов, пустая, удалённая, неизвестная или битый `groups.json`: цель остаётся ID группы, `Core.tunnel` отдаёт `groupMiss` (недоступен, считает отклонение группы), TCP получает RST, UDP отбрасывается, relay отклоняет. Напрямую поток не уходит ни в одной ветке. Пока `groups.json` битый, все серверы защищены: удалить нельзя, подписка оставляет пропавшие. После отката на v1.0.0 цели-группы выглядят как удалённый сервер и тоже отклоняются.
