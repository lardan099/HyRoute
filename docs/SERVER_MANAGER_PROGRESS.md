### P1-01 Каркас controller — выполнено

- `cmd/hyroute-server`: флаги + env `HYROUTE_SERVER_*` (`internal/srvmgr/config`),
  bind по умолчанию `127.0.0.1:8480`, предупреждение в журнале, если
  адрес не loopback; graceful shutdown по SIGINT/SIGTERM (10 с).
- SQLite (`modernc.org/sqlite`, без CGO): `internal/srvmgr/store` —
  интерфейсы, `store/sqlite` — реализация. Файл БД создаётся с правами
  0600, каталог данных 0700; WAL, foreign keys, busy timeout.
  Миграции `migrations/NNNN_name.sql` (embed), каждая в своей транзакции,
  без пропусков номеров; БД более новой схемы не открывается.
  Первая миграция — `settings` и `audit_log`; таблицы остальных сущностей
  добавляют задачи, которым они нужны.
- `/api/v1/health`; структурированные ошибки `{"error": {code, message,
  details}}`; неизвестный `/api/...` — JSON 404, а не страница UI;
  заголовки безопасности (CSP без внешних источников, запрет фреймов,
  nosniff, no-referrer); ограничение тела запроса 1 МБ; паника в handler —
  500 без текста паники в ответе.
- `web/admin`: Svelte 5 + Vite, стили и темы скопированы из клиента,
  строки — в `src/i18n/ru.ts`, навигация Overview/Servers/Cascades/Rules/
  Presets/Deployments/Logs/Settings (history-роутер, controller отдаёт
  `index.html` для не-API путей), Overview показывает health.
  `web/admin/dist` коммитится и встраивается (`web/admin/embed.go`).
- CI: проверка типов, сборка админки и сверка `web/admin/dist` с исходниками.
  CLAUDE.md: проверки для `web/admin`.
- Тесты: конфигурация, миграции (чистая БД, повторное открытие,
  инкрементальная, откат упавшей миграции, отказ на более новой схеме,
  проверка имён), HTTP-слой, запуск и остановка controller целиком.
- Известное: `go get modernc.org/sqlite` поднял косвенную зависимость
  `github.com/mattn/go-isatty` 0.0.20 → 0.0.24 (её использует и клиент
  через Wails); на поведение клиента не влияет.
- Без `ReadTimeout`/`WriteTimeout` у HTTP-сервера: SSE-потоки живут долго;
  тела запросов ограничены размером.

### P1-02 Аутентификация админки — выполнено

- `internal/srvmgr/auth`: argon2id (m=64 MiB, t=3, p=2, PHC-строка;
  хеш с другими параметрами пересчитывается при входе), сессии в БД по
  SHA-256 токена (idle 12 ч, абсолютный срок 7 дней, last_seen пишется не
  чаще раза в минуту), CSRF-токен выводится из токена сессии HMAC'ом —
  хранить его не нужно, а без HttpOnly cookie его не вычислить.
- Первый запуск: одноразовый setup token (32 байта) в журнале и в файле
  `<data-dir>/setup-token` (0600); файл удаляется после создания владельца.
  Владелец создаётся в транзакции «только если пользователей нет» — две
  одновременные попытки дают одного владельца (тест), повтор после
  рестарта с устаревшим токеном тоже невозможен.
- Rate limit в памяти: 5 неудач на имя за 5 минут, 20 на адрес за 15
  минут; 429 с `Retry-After`. Для несуществующего имени проверяется
  фиктивный хеш — время ответа одинаковое. Попытки под rate limit не
  пишутся в audit log (не забить БД при переборе).
- Cookie `hyroute_session`: HttpOnly, SameSite=Strict, Secure — если TLS
  или доверенный reverse proxy на loopback прислал
  `X-Forwarded-Proto: https` (`--trust-proxy`). Без TLS на 127.0.0.1 —
  без Secure, иначе браузер не вернёт cookie.
- Все изменяющие запросы: `X-CSRF-Token` + отказ, если
  `Sec-Fetch-Site`/`Origin` указывают на другой сайт; тела — только
  `application/json` (формы чужих сайтов не пройдут). Логин и setup тоже
  отклоняют межсайтовые запросы (login CSRF).
- Роли: readonly получает 403 на любой изменяющий запрос, кроме выхода
  и завершения своих сессий (иначе он не смог бы выйти); пользователями
  управляют только owner/admin; второго owner создать нельзя.
- API: `GET/POST /setup`, `POST/GET/DELETE /session`, `GET /sessions`
  (`?all=1` для owner/admin), `DELETE /sessions/{id}`, `GET/POST /users`.
- UI: экраны первого запуска и входа, имя и роль в боковой панели,
  «Настройки»: выход, сессии с завершением, пользователи и добавление.
  Проверено в Chromium (Playwright): первый запуск → обзор → добавление
  пользователя → перезагрузка страницы → выход → неверный пароль → вход
  пользователем только для чтения.
- Решение: отключение пользователя есть в хранилище (`SetUserDisabled`),
  но не в API/UI — полный RBAC и управление пользователями — Phase 4.

### P1-03 Секреты и redaction — выполнено

- `internal/srvmgr/secrets`: envelope encryption — у каждого значения свой
  DEK (AES-256-GCM), DEK запечатан версией master key (AES-256-GCM).
  Формат: `HRS1` | версия ключа | nonce+DEK | nonce | шифротекст. Контекст
  (например `server/12/ssh_password`) и версия входят в AAD обоих слоёв:
  значение, перенесённое в другую строку, не расшифруется.
- Master key: `HYROUTE_MASTER_KEY` или файл (`--master-key-file`, по
  умолчанию `<data-dir>/master.key`). Формат — строки или через запятую
  `<версия>:<base64 32 байт>` (или просто base64 = версия 1); старшая версия
  шифрует новые значения, остальные открывают старые (ротация), `Rewrap`
  переводит значение на текущую версию. Файл: обычный (не symlink), на
  Unix только владелец (иначе отказ с подсказкой `chmod 600`); если ключа
  нет — создаётся файл 0600 и в журнал пишется предупреждение сделать его
  копию.
- `internal/srvmgr/redact`: шаблоны (ключ=значение в YAML/JSON/logfmt/query
  для password/secret/token/passphrase/api key/private key/auth, ссылки
  `hysteria2://`/`hy2://`/`hysteria2+realm://` целиком, пароль в URL,
  Authorization, PEM private key, токен Telegram-бота), точные значения,
  зарегистрированные во время работы (`Redactor.Add`), структурная вычистка
  YAML (скалярные значения секретных ключей, все значения `userpass`,
  шаблоны в остальных строках; порядок и комментарии сохраняются),
  обёртка `slog.Handler`.
- Применено: журнал controller (все строки через `redact`), `details`
  ошибок API. Журналы jobs подключатся в P1-06.
- Решение: setup token больше не пишется в журнал — только путь к файлу
  (иначе он противоречит правилу «секреты не в журналах»).
- Внутренние ошибки handler'ов теперь пишутся в журнал (клиент видит
  только «внутренняя ошибка»).
