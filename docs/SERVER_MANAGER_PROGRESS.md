### P1-02 Аутентификация админки — выполнено

- `internal/srvmgr/auth`: argon2id (m=64 MiB, t=3, p=2, PHC-строка;
  хеш с другими параметрами пересчитывается при входе), сессии в БД по
  SHA-256 токена (idle 12 ч, абсолютный срок 7 дней, last_seen пишется не
  чаще раза в минуту), CSRF-токен выводится из токена сессии HMAC'ом —
  хранить его не нужно, а без HttpOnly cookie его не вычислить.
- Первый запуск: одноразовый setup token (32 байта) в журнале и в файле
  `<data-dir>/setup-token` (0600); файл удаляется после создания владельца.
  Владелец создаётся в транзакции «только если пользователей нет» — две
  одновременные попытки дают одного владельца (тест), повтор после
  рестарта с устаревшим токеном тоже невозможен.
- Rate limit в памяти: 5 неудач на имя за 5 минут, 20 на адрес за 15
  минут; 429 с `Retry-After`. Для несуществующего имени проверяется
  фиктивный хеш — время ответа одинаковое. Попытки под rate limit не
  пишутся в audit log (не забить БД при переборе).
- Cookie `hyroute_session`: HttpOnly, SameSite=Strict, Secure — если TLS
  или доверенный reverse proxy на loopback прислал
  `X-Forwarded-Proto: https` (`--trust-proxy`). Без TLS на 127.0.0.1 —
  без Secure, иначе браузер не вернёт cookie.
- Все изменяющие запросы: `X-CSRF-Token` + отказ, если
  `Sec-Fetch-Site`/`Origin` указывают на другой сайт; тела — только
  `application/json` (формы чужих сайтов не пройдут). Логин и setup тоже
  отклоняют межсайтовые запросы (login CSRF).
- Роли: readonly получает 403 на любой изменяющий запрос, кроме выхода
  и завершения своих сессий (иначе он не смог бы выйти); пользователями
  управляют только owner/admin; второго owner создать нельзя.
- API: `GET/POST /setup`, `POST/GET/DELETE /session`, `GET /sessions`
  (`?all=1` для owner/admin), `DELETE /sessions/{id}`, `GET/POST /users`.
- UI: экраны первого запуска и входа, имя и роль в боковой панели,
  «Настройки»: выход, сессии с завершением, пользователи и добавление.
  Проверено в Chromium (Playwright): первый запуск → обзор → добавление
  пользователя → перезагрузка страницы → выход → неверный пароль → вход
  пользователем только для чтения.
- Решение: отключение пользователя есть в хранилище (`SetUserDisabled`),
  но не в API/UI — полный RBAC и управление пользователями — Phase 4.

### P1-03 Секреты и redaction — выполнено

- `internal/srvmgr/secrets`: envelope encryption — у каждого значения свой
  DEK (AES-256-GCM), DEK запечатан версией master key (AES-256-GCM).
  Формат: `HRS1` | версия ключа | nonce+DEK | nonce | шифротекст. Контекст
  (например `server/12/ssh_password`) и версия входят в AAD обоих слоёв:
  значение, перенесённое в другую строку, не расшифруется.
- Master key: `HYROUTE_MASTER_KEY` или файл (`--master-key-file`, по
  умолчанию `<data-dir>/master.key`). Формат — строки или через запятую
  `<версия>:<base64 32 байт>` (или просто base64 = версия 1); старшая версия
  шифрует новые значения, остальные открывают старые (ротация), `Rewrap`
  переводит значение на текущую версию. Файл: обычный (не symlink), на
  Unix только владелец (иначе отказ с подсказкой `chmod 600`); если ключа
  нет — создаётся файл 0600 и в журнал пишется предупреждение сделать его
  копию.
- `internal/srvmgr/redact`: шаблоны (ключ=значение в YAML/JSON/logfmt/query
  для password/secret/token/passphrase/api key/private key/auth, ссылки
  `hysteria2://`/`hy2://`/`hysteria2+realm://` целиком, пароль в URL,
  Authorization, PEM private key, токен Telegram-бота), точные значения,
  зарегистрированные во время работы (`Redactor.Add`), структурная вычистка
  YAML (скалярные значения секретных ключей, все значения `userpass`,
  шаблоны в остальных строках; порядок и комментарии сохраняются),
  обёртка `slog.Handler`.
- Применено: журнал controller (все строки через `redact`), `details`
  ошибок API. Журналы jobs подключатся в P1-06.
- Решение: setup token больше не пишется в журнал — только путь к файлу
  (иначе он противоречит правилу «секреты не в журналах»).
- Внутренние ошибки handler'ов теперь пишутся в журнал (клиент видит
  только «внутренняя ошибка»).

### P1-04 Инвентарь серверов — выполнено

- Сущность `model.Server`: название (уникальное без учёта регистра), метки
  (до 16), страна (ISO-код, для флага), расположение, адрес (домен или IP,
  без порта и схемы), порт и пользователь SSH (по умолчанию 22 и root),
  способ входа (пароль или ключ), роль (standalone/entry/relay/exit),
  заметки, состояние (new/deploying/healthy/degraded/offline/
  needs_attention).
- Учётные данные SSH — в `server_credentials`, каждое значение запечатано
  `secrets` с контекстом `server/<id>/<kind>`; сервер и его данные пишутся
  в одной транзакции (`SealFunc` получает ID внутри транзакции).
  `servers.Service.Credentials` — единственный путь к открытым данным
  (для SSH-слоя, P1-05); API отдаёт только `hasPassword/hasKey/
  hasKeyPassphrase`.
- Ключ проверяется при сохранении (`ssh.ParsePrivateKey[WithPassphrase]`):
  зашифрованный ключ без пароля и неверный пароль — понятные ошибки поля.
  Смена способа входа удаляет данные прежнего способа; при изменении
  пустые поля учётных данных оставляют сохранённые.
- API: `GET/POST /servers`, `GET/PATCH/DELETE /servers/{id}`; ошибки
  проверки — 400 `invalid` с именем поля в `details`; readonly — 403.
  Действия пишутся в audit log.
- UI: «Серверы» — список (флаг, метки, адрес, роль, состояние), диалог
  добавления/изменения (сохранённые данные не показываются, подсказка
  «сохранён — оставьте пустым»), удаление с подтверждением; «Обзор» —
  список серверов с состоянием. Проверено в Chromium.
- Тест: в файлах БД (основной, WAL, SHM) нет пароля, пароля ключа и тела
  ключа; запечатанное значение не открывается для другого сервера.
- Ошибка поля ввода вынесена в `model.FieldError` (общая для auth и servers).

### P1-05 Безопасный SSH-слой — выполнено

- `internal/srvmgr/remote`: `Executor` (Run argv, Stream, ReadFile,
  атомарный WriteFile), ошибки (`HostKeyUnknownError`,
  `HostKeyChangedError`, `ErrAuthFailed`, `ErrSudoRequired`,
  `UnreachableError`, `ExitError`), `Quote`/`CommandLine` — каждый аргумент
  в одинарных кавычках, окружение `env LC_ALL=C LANG=C`, `sudo -n --`
  (без запроса пароля). Тест прогоняет враждебные аргументы (`$(…)`,
  обратные кавычки, `;`, перевод строки) через настоящий `/bin/sh`.
  Первая typed operation — `RunProbe` (кто мы, root/sudo, ядро, архитектура).
- `remote/sshexec`: `x/crypto/ssh` + `pkg/sftp`. Ключ перед паролем,
  keyboard-interactive для паролей, keepalive, отмена по контексту
  (SIGKILL + закрытие сессии), лимит вывода 32 МБ. `WriteFile`: SFTP во
  временный каталог `mktemp -d` → `install -m/-o/-g` рядом с целью →
  `mv -f` (атомарно). `FetchHostKey` — только ключ хоста, без входа.
- `remote/fake` — сценарный executor (правила по префиксу argv, файлы в
  памяти, журнал вызовов, режим «только чтение» для импорта).
- `remote/sshtest` — SSH-сервер внутри процесса: пароль/ключ, счётчик
  попыток входа, exec через функцию (по умолчанию локальный `/bin/sh`),
  SFTP, смена ключа хоста, сигналы.
- `internal/srvmgr/connect`: `Connect` (учётные данные из инвентаря,
  проверка ключа, регистрация паролей в redactor), `Check` (probe;
  без root/sudo — `ErrSudoRequired` вместе с данными probe), `Trust`
  (TOFU и явный re-trust, audit log).
- Миграция 0004: `host_keys`. Смена адреса/порта сервера забывает ключ.
- API: `POST /servers/{id}/check`, `POST /servers/{id}/host-key`; ошибки
  ключа несут отпечатки в поле `data`. UI: «Проверить» в списке серверов,
  диалог сверки отпечатка (с командой `ssh-keygen -lf` для типа ключа),
  отдельное предупреждение со флажком «я понимаю» при смене ключа.
  Проверено в Chromium против SSH-сервера в отдельном процессе.
- Тесты Done: первое подключение требует подтверждения и не отправляет
  учётные данные (счётчик попыток входа = 0), смена ключа блокирует
  подключение до явного re-trust, неверный пароль → `ErrAuthFailed`,
  без sudo → `ErrSudoRequired`, закрытый порт → `UnreachableError`.
- Решение: пользователь SSH — root или с `sudo -n` (NOPASSWD); sudo с
  паролем не поддерживается (понятная ошибка).
- Новая зависимость: `github.com/pkg/sftp` (+ `github.com/kr/fs`).

### P1-06a Движок заданий и хранение — выполнено

- P1-06 разбита на P1-06a (движок) и P1-06b (SSE, API, страница).
- Миграция 0005: `jobs` (параметры без секретов, `data` — значения между
  шагами, секреты — отдельным запечатанным полем с контекстом
  `job/<id>/secret`, аренда), `job_steps`, `job_logs` (строки уже после
  redaction). У сервера не больше одного незавершённого задания
  (проверка в транзакции создания).
- `internal/srvmgr/jobs`: вид задания (`Kind`) даёт список шагов по
  параметрам (детерминированно — перезапущенный controller строит тот же
  список и сверяет имена). Шаг: фаза (состояние задания), `Safe`, `Done`
  (уже сделано → пропуск), `Run`, `Undo`.
- Выполнение: фаза шага становится состоянием задания; `Env` даёт
  параметры, секреты, `Set/Get` (переживают перезапуск), журнал,
  соединение с сервером (открывается при первом обращении, закрывается в
  конце). Ошибка шага: сообщение для людей (`jobs.Fail`) + технические
  детали через redaction; откат `Undo` шагов, сделанных этим заданием
  (пропущенные «уже было» не откатываются).
- Повтор: только проваленное задание; с первого незавершённого шага,
  сдвигаясь назад до ближайшего `Safe`.
- Восстановление: при старте все незавершённые задания (кроме ещё не
  начатых) переходят в `recovering`; `Kind.Recover` проверяет фактическое
  состояние сервера и решает: выполнено / продолжить с безопасного шага /
  провалено. Без `Recover` — провал с понятным сообщением.
- Heartbeat продлевает только аренду (отдельная операция хранилища, чтобы
  не затирать состояние, которое пишет шаг).
- События (состояние, шаг, строка журнала) рассылаются подписчикам —
  основа SSE в P1-06b; медленный подписчик теряет события, а не тормозит
  задание.
- Тесты (`-race`): успешное задание, провал, повтор с безопасного шага,
  откат при сбое старта, восстановление после «убитого» процесса (с
  `Recover` и без), секреты не попадают ни в журнал, ни в ошибки, ни в
  параметры; одно задание на сервер.

### P1-06b Живой журнал, API и страница Deployments — выполнено

- API: `GET /jobs` (фильтр по серверу, постранично), `GET /jobs/{id}` с
  шагами, `GET /jobs/{id}/logs`, `POST /jobs/{id}/retry` (readonly — 403),
  `GET /jobs/{id}/events` — SSE: подписка до чтения сохранённого журнала
  (ничего не теряется между ними), повтор строк после `Last-Event-ID`
  (браузер переподключается сам), затем живые события `log`/`step`/`job`,
  `end` при завершении; keepalive-комментарий раз в 20 с;
  `X-Accel-Buffering: no` для nginx.
- Controller: движок заданий запускается вместе с HTTP и останавливается
  после него (прерванное задание восстановится при следующем старте);
  контекст запросов отменяется в начале остановки, чтобы SSE-потоки не
  держали `Shutdown`.
- UI «Развёртывания»: список (вид, сервер, состояние, начало,
  длительность), `/deployments/{id}`: шаги с состояниями, ошибка с
  раскрываемыми подробностями, живой журнал (`EventSource`, автопрокрутка,
  пока пользователь не прокрутил вверх), «Повторить» для проваленного.
  Проверено в Chromium на демонстрационном задании (dev-сервер в `.dev/`,
  не коммитится): живой журнал → ошибка на шаге запуска → повтор →
  «Выполнено».
- Исправлено по результатам проверки: сообщение для людей больше не
  дублируется в технических деталях; ошибка шага — «сообщение (причина)».
- Тесты: API списка/деталей/журнала/повтора, запрет повтора для readonly
  и для непроваленного задания; SSE-поток через настоящий HTTP-сервер —
  повтор сохранённого журнала, живые события, `end`.

### P1-08 Typed model конфига Hysteria — выполнено

- `internal/hyconfig`: серверный конфиг — все поля Full Server Config

  listen, tls, acme (включая dns и устаревшие disableHTTP/alt*Port), ech,
  auth, obfs (salamander, gecko), masquerade, bandwidth,

  http; режимы forwarding/tproxy/tun не моделируются и сохраняются как
  неизвестные.
- Неизвестные поля: каждый уровень хранит нераспознанные ключи
  (`Unknown`, пары `yaml.Node`) и пишет их после известных в исходном
  порядке. Ключи сопоставляются без учёта регистра, как в Hysteria

  внутри неизвестных значений раскрываются (якорь мог стоять на
  известном поле), с лимитом против alias-бомб; `<<` и несколько
  документов — понятная ошибка.
- Валидация (`Validate` → `[]Problem` с полем, текстом по-русски,
  ошибка/предупреждение) повторяет проверки Hysteria: tls xor acme,
  обязательные поля по выбранному типу, списки значений (без учёта
  регистра), порты и диапазоны listen, скорости с единицами и минимумом
  65536 Б/с, окна QUIC ≥ 16384, maxIdleTimeout 4–120 с, udpIdleTimeout
  2–600 с, пароль obfs ≥ 4 байт, размеры пакетов gecko, уникальные имена
  outbounds, bind IP vs device, masquerade, acl file xor inline, пользователи
  userpass (двоеточие, совпадение без учёта регистра). Предупреждения:
  trafficStats без секрета, mimic, число без единиц, короткий пароль,
  Realms, неизвестные поля.
- Генератор клиента `ClientFor(server, ClientOptions)`: адрес и порты из
  listen (IPv6 в скобках, диапазон для port hopping + hopInterval), auth
  (password, выбранный пользователь userpass как `user:pass`; для
  http/command — только явно заданный), SNI первого ACME-домена при
  подключении по IP, самоподписанный сертификат — `insecure` + `pinSHA256`,
  obfs (только пароль), mimic, скорости, socks5/http на loopback;
  результат проходит `Client.Validate`.
- Тесты: round-trip полного, ACME и «будущего» конфига (сравнение как

### P1-10a Загрузка бинарника Hysteria — выполнено

### P1-10b Job deploy — выполнено

- `internal/srvmgr/deploy`: задание `deploy` из шагов connect → preflight →
  prepare → binary → user → tls → config → unit → firewall → start →
  verify → commit. Каждый шаг с `Done` сверяет фактическое состояние
  сервера (SHA-256 бинарника и конфига, содержимое unit и автозапуск,
  pin сертификата, пользователь, активность службы) и пропускается, если
  всё уже так. Повторное развёртывание с теми же параметрами ничего не
  пишет, не перезапускает службу и не создаёт новую ревизию (тест).
- Установка как у официального скрипта: `/usr/local/bin/hysteria`,
  `/etc/hysteria/config.yaml`, `hysteria-server.service`, пользователь
  `hysteria` с домашним каталогом `/var/lib/hysteria`, те же
  capabilities и `NoNewPrivileges`; добавлены `Restart=on-failure`.
  Конфиг и ключ — 0640 root:hysteria (у официального скрипта конфиг 0644).
- Секреты (пароль auth, пароль obfs, самоподписанный сертификат и ключ)
  создаются до запуска задания и лежат в зашифрованных секретах задания:
  шаги детерминированы и после перезапуска controller. Пароли — 24
  случайных байта в base64url. Для самоподписанного сертификата
  `sniGuard: disable` (клиенты могут подключаться по IP без SNI).
- Откат: заменяемые файлы сохраняются с суффиксом `.hyroute-prev`; при
  падении любого шага после изменений файлы возвращаются (или удаляются
  при первой установке), служба останавливается, а первым по порядку
  отката — последним по времени — шаг `prepare` снова запускает прежнюю
  версию, если она работала. Движок: хук `Finished` (состояние сервера:
  healthy / needs_attention / прежнее), `Env.CreatedBy`,
  `ErrNothingToUndo` (откат шага без изменений не пишет «Откачено»).
- Чужая установка (конфиг не совпадает с последней ревизией controller)
  — отказ с предложением импорта; с `replace` — замена с копиями.
  Порт-хоппинг требует nftables или iptables на сервере.
- Firewall: ufw/firewalld — открываются UDP-порты (и TCP 80/443 для
  ACME); политика DROP в nftables/iptables — только предупреждение.
- Проверка после запуска: служба active и UDP-порт слушает процесс
  hysteria (для ACME ожидание втрое дольше); при падении в журнал
  задания попадают последние строки journald (через redaction).
- Ревизии конфига в БД (`0006_server_configs`): YAML зашифрован с
  контекстом `server/<id>/config/<rev>`, meta без секретов (версия,
  listen, порты, режим TLS, pin, SNI, obfs).
- Тесты на симуляторе сервера (файлы, пользователи, systemd, ss, curl,
  ufw): свежая установка с obfs и hopping (пути, права файлов, ufw,
  ревизия, meta, секреты не попали в журнал и data), падение install,
  подмена бинарника, падение старта на свежей установке с откатом,
  неудачное обновление с возвратом прежней версии, повтор без изменений,
  relay-загрузка, чужая установка и замена, ACME-откат не трогает чужой
  сертификат, перезапуск controller посреди развёртывания, параметры,
  сертификат. `-race` чисто.

### P1-10c API и UI развёртывания — выполнено

- `deploy.Submitter`: проверяет параметры (ошибки — `FieldError` с
  русским текстом), создаёт секреты и ставит задание. Сервер, который
  HyRoute уже разворачивал, сохраняет пароли auth и obfs из текущей
  ревизии конфига (расшифровка и разбор typed model), сертификат остаётся
  на сервере (шаг tls сверяет pin с ревизией): ссылки клиентов не ломаются
  при повторном развёртывании и при смене параметров.
- API: `POST /api/v1/servers/{id}/deploy` (параметры без секретов; без
  подтверждённого ключа SSH — `host_key_required`, занятый сервер —
  `server_busy`), `GET /api/v1/servers/{id}/config` — сводка текущей
  ревизии (версия, порты, TLS, SNI, pin, obfs; сам конфиг и пароли не
  отдаются).
- Админка: кнопка «Развернуть» у сервера; для нового сервера «Добавить и
  развернуть» → подключение и подтверждение ключа → форма. Форма:
  самоподписанный сертификат или Let's Encrypt (домен, email, проверка
  HTTP/TLS), порт, port hopping, сайт-маскировка, Salamander; в
  «Дополнительно» — SNI, версия, источник загрузки, не трогать
  брандмауэр, замена чужой установки. Повторное развёртывание открывает
  форму с параметрами последнего успешного и говорит, что пароли
  сохранятся. Прогресс — существующая страница задания (SSE), с русскими
  названиями шагов; итог — карточка «Hysteria 2 работает» (версия, порты,
  TLS, pin, obfs, ревизия). Отчёт preflight у развёртывания показывается,
  только если сервер не готов.
- Тесты: Submitter (неверные параметры, нет сервера, повтор без
  изменений, добавление obfs сохраняет пароль auth и pin, `CurrentSecrets`),
  API (нет ключа, неверные параметры, 202 без секретов в params, занято,
  сводка конфига без пароля, readonly).
- Проверка в браузере (Playwright, временный стенд: controller с
  симулятором VPS и тестовым SSH-сервером, в репозиторий не входит):
  добавление сервера → подтверждение ключа → форма → ошибка в диапазоне
  портов → живой прогресс → итог; чужая установка — понятная ошибка;
  повторное развёртывание — форма заполнена.

### P1-11 Импорт — разбита на P1-11a (обнаружение и задание), P1-11b (API и UI)

### P1-11a Обнаружение и задание импорта — выполнено

- `remote.ReadOnly`: обёртка исполнителя, через которую идёт весь импорт.
  Запись файлов отклоняется, команды — только чтения из typed-операций и
  только с читающими флагами (`systemctl show/list-units/…`, `stat`,
  `cat`, `sha256sum`, `ss -Hlntup`, `ps -o unit=`, `getent passwd`,
  `<…/hysteria*> version`); `hostname NAME`, `ss -K`, `journalctl
  --vacuum`, `systemctl restart` и всё прочее — `ErrNotReadOnly`. Так
  «ничего не менять на сервере» проверяется не только тестом, но и во
  время работы.
- Новые typed-операции: `Stat` (права, владелец), `ServiceUnits`
  (службы по шаблону, экземпляры шаблонных unit), `UnitOfPID`,
  `UserHome`; `Listener.PID`; у `SystemdUnit` — Group, WorkingDirectory,
  UnitFileState, Restart. sshexec: чтение отсутствующего файла через sudo
  теперь `fs.ErrNotExist`, как по SFTP (раньше — ExitError; шаги deploy,
  проверяющие файлы, ошиблись бы у пользователя с sudo).
- `internal/srvmgr/importer`: служба ищется среди стандартной
  `hysteria-server.service`, `hysteria*` (в том числе
  `hysteria-server@name`) и служб процессов с именем hysteria на
  слушающих портах; из нескольких берётся работающая, остальные
  перечисляются. Из ExecStart — программа и `-c/--config` (относительный
  путь — от WorkingDirectory, `~` — домашний каталог пользователя службы);
  без флага — места, где Hysteria ищет config.yaml. Конфиг разбирается
  typed model; сертификат читается (ключ — никогда): самоподписанный даёт
  pin, у выданного CA проверяется срок.
- Проверки → находки (warn — сервер «Требует внимания», info — к
  сведению): конфиг с паролями читают или меняют все; Hysteria от root;
  служба не работает / не в автозапуске / без Restart; ошибки и замечания
  валидации; неизвестные поля; короткие пароли auth и obfs; нет, истёк
  или скоро истечёт сертификат; нестандартные пути; другие службы
  Hysteria; устаревшая версия; userpass и внешняя проверка паролей (для
  ссылок); нет маскировки.
- Задание `import`: connect → inspect (отчёт в data задания, без
  секретов) → save (конфиг читается ещё раз и должен совпасть по SHA-256
  с прочитанным; ревизия `import` зашифрована; запись об установке).
  Повторный импорт без изменений ничего не добавляет.
- Таблица `installations` (`0007`): пути программы, конфига, служба,
  пользователь, версия, managed. Deploy записывает свою установку
  (managed), импорт — найденную (managed=false; установка, которую HyRoute
  развернул сам и которая на месте, остаётся managed). Deploy не считает
  импортированную установку своей: без замены — отказ с объяснением,
  импортированная в нестандартных местах не заменяется вовсе (иначе
  рядом работали бы две Hysteria); при замене пароли импортированного
  конфига переходят в новый, ссылки клиентов не ломаются.
- Снимка сервера владельца (`reference/server-snapshot/`) нет: импорт
  проверен на синтетических фикстурах — установка официальным скриптом
  (`get.hy2.sh`, значения фейковые), самодельная служба от root с
  относительным `-c`, самоподписанным сертификатом, неизвестным полем и
  слабым паролем, поиск конфига без `-c`, сертификат от CA на исходе,
  собственная установка HyRoute (без находок, pin совпадает), ошибки (нет
  systemd, нет Hysteria, нет или сломан конфиг, программа не Hysteria).
  Во всех тестах исполнитель — fake с ReadOnly под `remote.ReadOnly`:
  ни одной записи. Задание: ревизия и установка в БД, состояние сервера,
  пароли не попадают в отчёт и журнал, повтор, изменение конфига во время
  импорта. `-race` чисто.

### P1-13 Редактор конфига — разбита на P1-13a (кандидат), P1-13b (задание apply), P1-13c (UI)

### P1-13a Кандидат конфига: секреты, поля, проверка, diff — выполнено

- `internal/srvmgr/apply`: `Mask` скрывает значения полей с именами
  секретов (`*password`, `*secret`, `*token`, …) и все пароли `userpass`
  на уровне `yaml.Node` — порядок, комментарии и неизвестные поля
  остаются. `Unmask` возвращает текущие значения туда, где кандидат
  оставил `[REDACTED]`, по пути поля; элементы списков сопоставляются по
  `name` (переставленные outbounds не перепутают пароли), без имени — по
  номеру; скрытое значение без прежнего — ошибка поля. `MaskUnchanged`
  скрывает только совпадающие с текущими секреты: новый или
  сгенерированный пароль виден и не теряется при следующей правке.
- Основные поля (`Fields`: listen, TLS файлом или ACME, sniGuard, пароль
  auth, Salamander, маскировка proxy, скорости, ignoreClientBandwidth,
  speedTest, disableUDP, udpIdleTimeout) ⇄ typed model; остальное
  (ACL, outbounds, другие режимы, неизвестные поля) не трогается. Пустой
  пароль — генерируется. Правка через поля переписывает YAML через
  модель (комментарии уходят — это видно в diff).
- `Build`: кандидат из текста (и полей) → восстановление секретов →
  разбор → `Validate` → diff с текущей ревизией (обе стороны без старых
  секретов; LCS по строкам) → список изменённых секретов → `OK`, если
  нет ошибок. `Editor.Render` требует, чтобы базовая ревизия была ещё
  текущей (иначе `config_changed`).
- API: `GET /servers/{id}/config/edit`, `POST /servers/{id}/config/render`
  (ничего не сохраняет и не трогает сервер).
- Тесты: маскирование с комментариями и путями, обратное восстановление,
  перестановка outbounds, скрытое значение без прежнего, кандидат из
  текста и из полей (ACME вместо файлов, новый пароль, снятие obfs,
  маскировка), генерация пароля, круг «правка → рендер → правка», diff,
  API (маскирование в ответе, поля, битый YAML, устаревшая ревизия).

### P1-13b Задание применения с откатом — выполнено

- Задание `apply` (кандидат — в зашифрованных секретах задания, в
  параметрах — только базовая ревизия и хеши): connect → validate
  (typed-проверка; файл на сервере должен совпадать с базовой ревизией —
  правка вручную через SSH останавливает задание с предложением
  импортировать заново; на повторе после сбоя принимается и уже
  установленный кандидат) → prepare (было ли активно, прежнее состояние
  сервера) → backup (`cp -p` в `.hyroute-prev`) → install (атомарная
  запись с правами и владельцем прежнего файла) → restart → verify
  (служба active и UDP-порт listen у процесса hysteria; для ACME
  ожидание втрое дольше) → commit (ревизия `edit`, сводка через
  `importer.ConfigMeta`, копия удаляется).
- Откат при любой ошибке после записи: прежний файл возвращается из
  копии, служба перезапускается с ним (или останавливается, если была
  остановлена); в отчёт — последние строки journald, отредактированные
  паролями и текущего, и нового конфига. Состояние сервера после отката —
  прежнее; если откат не завершился — «Требует внимания».
- Отдельной проверки конфига у Hysteria нет (команды «проверить без
  запуска» в v2 нет): её роль играет перезапуск с откатом.
- `Applier.Submit`: кандидат с ошибками проверки и кандидат без
  изменений (по diff и списку секретов — YAML после разбора
  сериализуется заново) — ошибки поля; устаревшая базовая ревизия —
  `config_changed`. API `POST /servers/{id}/config/apply`.
- Тесты на симуляторе сервера (restart запускает конфиг с диска):
  успешное применение (порт, пароль сохранён, права 0640
  root:hysteria, копия удалена, ревизия 2 `edit`, meta, состояние),
  повтор без изменений, устаревшая ревизия; невалидный конфиг отклонён
  до установки — и в Submit, и в самом задании (ни записи, ни restart);
  служба не стартовала → прежний файл, служба снова работает, ревизия не
  добавлена, журнал без пароля; конфиг изменён на сервере вручную →
  отказ без записи. API: нет установки, невалидный, без изменений, 202,
  занято.
- Исправление после коммита P1-13b: он ушёл без гофмата теста и при
  упавшем `TestJobEventsStream` под `-race` (проверки запускались, но
  коммит от них не зависел). Тест поймал настоящую гонку в SSE задания
  (P1-06): если задание заканчивалось, пока поток отдавал сохранённые
  строки, `end` уходил без строк, записанных в этот момент. Теперь перед
  `end` поток дочитывает журнал из БД (и при завершении, замеченном по
  событию подписки). 100 прогонов под `-race` без сбоев. Проверки теперь
  идут одним скриптом, и коммит делается только после его успеха.

регулярной сверки состояния серверов (Phase 4); у Hysteria нет проверки
конфига без запуска — её роль играет перезапуск с откатом; ссылки
строятся на адрес SSH сервера (отдельный публичный адрес — позже).

## P1-16 Исправления по внешнему ревью

### P1-16a Движок заданий: данные отката не теряются

- `Env.Set` пишет данные задания в БД до возврата (`SetJobData`;
  `UpdateJob` данные больше не пишет, чтобы старая копия не перезаписала
  новую). Ошибка записи возвращается и в любом случае валит шаг.
- Раньше данные уходили в БД только в начале следующего шага: при
  падении controller между концом шага и следующим сохранением (или
  посреди шага) флаг «была копия» терялся, и откат удалял новый файл
  вместо восстановления прежнего.
- Копии файлов (deploy: бинарник, сертификат, ключ, конфиг, unit; apply:
  конфиг) записывают SHA-256 исходного файла или `absent` до копии и до
  изменения. `remote.RestoreFile` восстанавливает копию только при
  совпадении хеша, удаляет только файл, которого не было, и ничего не
  трогает, если копия не та (`ErrBackupMismatch` — в журнале с просьбой
  проверить файл). Повтор шага сохраняет первую запись. Флаги старого
  формата («1») понимаются.
- Флаг «изменено» ставится до изменения (лишний перезапуск безопаснее
  пропущенного).
- Найдено тестом: шаг, пропущенный после перезапуска (его результат уже
  на сервере от этого же задания), не попадал в откат. Теперь откат
  проходит по выполненным и пропущенным шагам и по упавшему шагу; каждый
  `Undo` действует только по своим записям. `undoStart` останавливает
  службу, только если этот шаг её перезапускал.
- Состояние сервера после неудачи учитывает, было ли что откатывать
  (`Env.Rollback()`): упавшая установка, ничего не изменившая, не
  переводит сервер в «Требует внимания».
- Ошибка чтения `JobSecret` больше не проглатывается: задание падает с
  причиной.
- Тесты: `TestSetSurvivesKilledProcess`, `TestUnreadableSecretFailsJob`,
  `TestRestartMidStepKeepsRollbackRecord` (controller падает сразу после
  записи нового конфига; после перезапуска проверка не проходит, и
  возвращается прежний конфиг, а не удаляется файл). Старый код этот
  тест не проходит.

### P1-16b Маскирование конфига

- Подтверждено: значение с якорем (`shared: &pw …`) под обычным ключом,
  использованное как `auth.password: *pw`, раньше оставалось в ответе
  редактора целиком; так же пароли в URL и в неизвестных полях.
- `apply.secretsOf` — единый список секретов документа: значения под
  секретными ключами и в `userpass`; значение, на которое ссылается alias
  в таком месте (и весь `userpass`, подставленный alias), — по пути, где
  оно определено; любая строка, в которой redactor находит секрет (пароль
  в URL, ссылка hysteria2://, закрытый ключ). Комментарии проходят через
  redactor; при сохранении без правок `Unmask` возвращает исходные
  комментарии.
- После формы (typed model) alias превращается в копию значения:
  `MaskUnchanged` скрывает и значения по путям секретов текущего конфига,
  а `lookup` проходит через alias.
- `redact.YAML` (запасной путь для журналов) тоже следует за alias.
- `GET /config/edit` — только роли с правом записи (`writers`);
  `render` и так был POST для них. Маскирование — вторая линия, а не
  единственная.
- Тесты: `TestMaskFollowsAliasesURLsAndComments` (anchor, userpass за
