# Правила

## Модель и матчинг

```jsonc
{
  "id": "uuid", "name": "Discord", "enabled": true,
  "apps":    [{ "pattern": "discord.exe", "kind": "name|path|glob", "inheritChildren": true }],   // любая из программ; пусто = любая
  "domains": [".discord.com", "*.discord.gg", "discord.media"],   // любой из сайтов; exact | *.x (только поддомены) | .x (x и поддомены)
  // старая форма "app": {...} / "domain": {"pattern": ...} по-прежнему читается
  "profile": "<id сервера>",                   // для tunnel; пусто = основной
  "protocol": "any|tcp|udp",
  "ports":    "443,8000-8100",                // порты назначения: порт или диапазон; нет поля = любые (ports)
  "action":   "tunnel|direct|block",
  "failMode": "open"                          // зарезервировано (kill switch теперь глобальный, [failure.md, «Kill switch (WFP)»](failure.md#kill-switch-wfp))
}
```
- Путь нормализуется: `/` → `\`, без префикса `\\?\`, сравнение без учёта регистра. Пути в
  правилах пишутся в форме `C:\…`: путь процесса приходит в ней же (`QueryFullProcessImageName`), а
  `\Device\HarddiskVolumeN\…` к букве диска не приводится.
  `name` сравнивается с basename, `glob` проверяется по полному пути: `*` —
  любая последовательность символов, включая `\` (как в Proxifier: `C:\Games\*` покрывает все
  вложенные папки), `?` — один символ. Тип определяется автоматически, если не задан: есть `*`/`?` →
  glob, есть `\` или `/` → path, иначе name.
- Приложение без атрибуции (`Unknown`) не совпадает ни с одним правилом по приложению. Наследование
  (`inheritChildren`) проверяет цепочку предков из дерева процессов ([interception.md, «Атрибуция
  процесса»](interception.md#атрибуция-процесса)).
- Режим задаёт `defaultAction`: «только выбранные через туннель» даёт Direct, «все, кроме выбранных»
  даёт Tunnel.
- Порядок применения: исключения ([interception.md, «Обязательные
  исключения»](interception.md#обязательные-исключения)), затем пользовательские правила сверху вниз
  (first match), затем default.
- **Порты** (`internal/rules/ports.go`). `ports` — список портов назначения: `"443"` или
  `"8000-8100"`, между элементами «ИЛИ», с остальными условиями (программы, сайты, протокол) — «И».
  Порт назначения движок знает всегда (`Subject.Dst` у всех мест решения, у фрагментов — из
  первого), поэтому условие решается на уровне пакета: `base` проверяет его вместе с протоколом, и
  поток на порт, которого нет в правиле, не ждёт имени сайта (не `NeedsDomain`). При компиляции
  элементы проверяются (1..65535, `lo <= hi`; не больше 256 на правило — только при вводе: редактор,
  текст правил, `ParsePortList`; сохранённый список не ограничен, как в v1.2.0), сортируются и
  сливаются в диапазоны (`80, 81-90` → `80-90`), совпадение — бинарный поиск; порт 0 (неизвестен) не
  совпадает никогда. Порты проверяются и у выключенных правил: иначе испорченный вручную порт
  расширил бы правило при экспорте или включении. Правило может состоять только из портов («TCP 22 →
  напрямую» для всех программ и сайтов); правило только с протоколом по-прежнему ошибка. Безымянное
  правило только из портов называется по ним («TCP 22», «порт 443») — одинаково в Go (`ruleName`,
  снаружи пакета `RuleLabel` — им подписаны и предупреждения о серверах правил) и в UI (`ruleTitle`,
  элементы канонизируются так же: `"0443"` → «порт 443»). В JSON поле пишется, только если порты
  есть (`omitempty`), строкой в форме v1.2.0 (`"80,443,27000-27200"`, `PortList.MarshalJSON`), чтобы
  после отката на 1.2 файл читался; читается и эта строка, и массив (`["443", 8000]`). Строку из
  одних разделителей (`","`) ввод отклоняет (редактор, текст правил), а не делает «любым портом»; в
  файле (так сохранял редактор v1.2.0) она читается, как читал v1.2.0: портов нет, правило на любой
  порт, при записи поле пропадает. У правил без портов settings.json остаётся в формате 1.0.0, а
  1.0.0/1.1 с портами файл не прочтут (`DisallowUnknownFields`) — это отказ, а не расширение правил.
  QUIC (UDP 443) при «Точное определение сайта» и «Блокировать QUIC…» решается без имени
  (`rules.NamelessUDP`, общий для `packetSites`, Explain и Lint): правило «сайт + UDP 443» там не
  срабатывает, об этом предупреждают lint и редактор. Lint (`LintWith` с настройками движка) ещё
  подсказывает («info»), что UDP-порт 49152–65535 без программы ловит и ответы локальных
  UDP-серверов.
- **Правила текстом** (`internal/app/rulestext.go`). Весь список можно выгрузить текстом, поправить
  и загрузить обратно, или добавить много правил пачкой. Формат: одна строка — одно правило `что ->
  куда [| опции]`. Блок `[chrome.exe]` ограничивает строки под ним одной программой (в них пишутся
  только сайты: программа в такой строке — ошибка, правило для неё пишется после `[*]`), `[*]` (а
  также `[все]`, `[всё]`, `[all]`, `[]`) снимает ограничение и означает все программы, `* -> …`
  задаёт «всё остальное» и допускается один раз, вне блока программы и без опций. Опции `tcp` и
  `udp` вместе — ошибка (это любой протокол). Сервер указывается именем, его уникальной частью или
  `id:`; неоднозначное имя — ошибка. При любой ошибке ничего не сохраняется, в ответе номера строк.
  Экспорт и импорт дают те же правила (тест round-trip). `=game.exe` — программа без дочерних
  процессов, маски `*`/`?` (кроме `*.x`) — программы по полному пути; элемент или название с
  пробелами, `|`, `->` или начальным `#` пишется в кавычках, название без кавычек с `.`, `\`, `/`
  или `*` — ошибка (просим кавычки); путь с пробелами без кавычек (абсолютный путь не к `.exe`, за
  которым идёт относительный путь, а для пути без расширения — программа или голое слово)
  отклоняется, элемент в кавычках всегда цельный, и экспорт берёт в кавычки абсолютный путь не к
  `.exe`; элемент-сайт с невозможными символами (`«youtube.com»`, `(a.com)`, `a.com!`) или пустыми
  частями (`..a.com`, `a..com`, `domain:.a.com`) — ошибка (`rules.SiteProblem`); ссылка на
  `www.сайт` даёт сайт без `www.`; строки с `выкл` тоже компилируются и проверяются (без
  предупреждений); сервер с зарезервированным именем выгружается как `id:`. В `[ ]` допустимы только
  программы (имя с точкой без `.exe` принимается с предупреждением). Программу, которую строка
  прочла бы иначе (`vmmem` как `vmmem.exe`, `my.app` как сайт, одинокое `*` как «всё остальное»),
  экспорт пишет с префиксом `app:` (`app:vmmem`, `=app:my.app`); кавычка внутри элемента в кавычках
  удваивается. Опции портов (`ports`): `tcp 443`, `udp/27000-27100`, `tcp:22`, `порт 443`, `порты
  80, 443` (элементы через запятую, точку с запятой или пробел, диапазон через `-`, `–`, `—`, в том
  числе с пробелами); несколько опций с портами (текст v1.2.0: `| порт 443 | порт 8443`) сливаются в
  один список, разные протоколы в одной строке — ошибка, опция из одних разделителей (`порт ,`) —
  ошибка. `* -> X | tcp 22` — правило только по порту (с именем: `SSH: * -> …`, под `[chrome.exe]` —
  для этой программы), `* -> X` без порта — по-прежнему «всё остальное». Экспорт пишет опцию
  канонически (`ruleOptionText`, общий с конвертером ACL), программу-маску `*` с портами — как
  `app:*`, а неверные сохранённые порты — обезвреженными (`rawPortItem`), чтобы импорт показал
  ошибку в этой строке, а не расширил правило.
- Внутри списка `apps` условия объединяются через «ИЛИ», внутри `domains` тоже. Между списками —
  «И»: если заданы и программы, и сайты, правило ловит только соединения этих программ к этим
  сайтам. UI объясняет это и предлагает два правила, если нужна вся программа целиком.

## Адреса и базы правил (geosite / geoip)

- В `domains` кроме сайтов можно писать: `geosite:youtube` (категория geosite.dat,
  `geosite:google@cn` — только записи с атрибутом, `geosite:google@cn@ads` — записи со всеми
  атрибутами, как в Xray; если ни у одной записи категории таких атрибутов нет, это предупреждение,
  а не пустой элемент), `geoip:ru` (категория geoip.dat), IP (`1.2.3.4`), сеть (`10.0.0.0/8`,
  `2001:db8::/32`), `keyword:слово`, `regexp:RE2`, `full:x` (= `x`), `domain:x` (= `.x`). Поле в
  JSON то же, `domains`: адресные элементы (`IsAddressItem`) компилируются в отдельный список `ips`.
- Назначение правила = «сайты ИЛИ адреса»: правило совпадает, если IP назначения входит в любой
  адресный элемент или имя подходит под любой доменный. IP известен всегда, поэтому трёхзначная
  оценка: адресное совпадение сразу терминально; правило только с адресами, которые не совпали, не
  влияет на исход и не требует sniff.
- Формат баз — protobuf v2ray (`GeoSiteList`/`GeoIPList`), читается без зависимостей
  (`internal/geodata`). Файл 70+ МБ целиком не грузится: при первом обращении строится индекс
  «категория → смещение» (≈15 мс на 74 МБ), категория декодируется, только когда её использует
  правило, и кешируется до смены файла; категории, которых нет во включённых правилах (например,
  проверенные в редакторе), выбрасываются из памяти планировщиком (раз в 10 минут и после сохранения
  правил). Домены: отсортированные `full` и `suffix` с бинарным поиском по суффиксам имени,
  `keyword`, `regexp` (шаблон в нижний регистр не переводится, а компилируется с `(?i)`, без учёта
  регистра). IP: слитые отсортированные диапазоны v4/v6, бинарный поиск; `reverse_match`
  поддерживается. `geoip:private` встроен и работает без баз.
- Нет базы или категории — это предупреждение (`Set.Warnings`, lint, текстовый импорт), а не ошибка:
  правило компилируется и такой элемент ничего не ловит. Иначе обновление базы, где убрали
  категорию, при старте сбросило бы все правила пользователя на значения по умолчанию.
- Источник — пресет (по умолчанию runetfreedom/russia-v2ray-rules-dat: всё из v2fly плюс
  `ru-blocked`, `ru-available-only-inside`; Loyalsoldier; v2fly) или свои ссылки. Обновление:
  `.sha256sum` рядом с файлом → если совпадает с установленным, ничего не качается; иначе новая
  версия ставится. Установленным считается файл на диске: его SHA-256 сверяется при каждой проверке,
  поэтому испорченный файл (сбой питания, ошибка диска) ставится заново даже той же версией.
  Скачивание — во временный файл со случайным именем (`os.CreateTemp`, CREATE_NEW) с fsync, затем
  проверка SHA-256 и формата (индекс строится, есть категории), старый файл → `.prev`, новый на
  место. geo.json и `.prev.json` пишутся так же (временный файл + rename), а читаются без прохода по
  ссылкам (FILE_FLAG_OPEN_REPARSE_POINT, отказ при NumberOfLinks ≠ 1): папка доступна на запись
  программам пользователя, а HyRoute работает с правами администратора. Редирект с https на http не
  выполняется. Адрес суммы — путь файла + `.sha256sum`, query сохраняется. Ответы 401/403/404/410 и
  ответ не вида `<sha256> имя` значат «сумма не опубликована»: файл ставится без пометки
  «проверена». Сетевая ошибка, 5xx и 429 — файл не ставится. Откат меняет файл и `.prev` местами,
  «всё или ничего». Восстановленный откатом файл закреплён (`heldFor`/`rolledBackFrom` в geo.json):
  для того же источника он не считается недостающим, а плановое обновление не ставит версию, от
  которой откатились (более новую ставит). Ручное «Проверить обновления»/«Скачать заново» и смена
  источника закрепление снимают. `.prev.json` описывает только файл в `.prev`; если описание не
  совпадает с файлом, при откате состояние строится по самому файлу. После обновления правила
  перекомпилируются и уходят в сессию; новые соединения идут по новой базе.
- Принадлежность файла источнику определяется по URL в `geo.json` (`FileState.url`). Свои ссылки —
  только `https://`; сохранённые раньше `http://` не скачиваются, причина видна в «Базы правил».
  Неудачная смена источника или своих ссылок оставляет базу «недостающей», повтор идёт с паузой.
- Базы качаются, только если их используют включённые правила (кроме `geoip:private`), и решается
  это по каждой базе отдельно: при правилах только с `geoip:` `geosite.dat` не качается и не
  обновляется по расписанию, если не остался файл от прежнего источника (его заменяют один раз).
  Ручное обновление работает с обеими базами. Проверка — при сохранении правил, при старте и каждые
  N часов (по умолчанию 12, настраивается). Недостающая база качается даже при выключенном
  автообновлении. Прямая загрузка не удалась (GitHub часто режется) — повтор через туннель основного
  профиля, если он подключён. После ошибок, в том числе при автообновлении, — пауза с ростом до 6 ч,
  а не повтор через N часов.
- «Проверить адрес» для сайта при наличии адресных правил резолвит его IPv4 и показывает, по какому
  адресу проверялись geoip/IP.
- Инспектор списков (`internal/geodata/inspect.go`, `internal/app/inspect.go`, страница «Списки»):
  обратный поиск — какие категории содержат имя или IP. Индекса нет: все категории файла сканируются
  параллельно по индексу смещений, без построения множеств (≈170 мс на 74 МБ geosite, ≈40 мс на
  geoip). include: в .dat уже раскрыты, поэтому родительские категории находятся сами. Для имени ещё
  резолвятся A/AAAA и проверяется geoip. Результаты сортируются по приоритету (явные значения для
  anthropic/telegram/openai/…, сервисы 700, category-* 100, geoip 80, агрегаты — реестры, регионы,
  страны — 40), при равенстве — меньший список выше. Просмотр категории держит в памяти только
  последнюю открытую. Конвертер ACL (как и в Hysteria, срабатывает первое совпадение: строка
  `all`/`*` без протокола задаёт «Всё остальное», а строки ниже неё пропускаются с предупреждением):
  строки `action(resource[, proto/port])` → корневые домены `*.x suffix` (geosite раскрывается по
  базе, keyword/regexp пропускаются с подсчётом) или правила HyRoute (direct → напрямую, reject →
  блок, остальные выходы → vpn; подряд идущие с одним действием склеиваются, порядок сохраняется;
  `reject(all, udp/443)` указывает на настройку «Блокировать QUIC»). Протокол и порт переносятся
  (`aclProtoPort` повторяет `parseProtoPort` Hysteria: строку, которую Hysteria не примет, конвертер
  пропускает с предупреждением; начальный порт 0 значит «любой порт»): `proxy(x.com, tcp/443)` → `|
  tcp 443`, `*/80` → `| порт 80`; строки склеиваются, только если совпадают действие, протокол и
  порты. `action(all, tcp/22)` → правило только по порту `* -> … | tcp 22`, `all` с протоколом без
  порта → `| udp 1-65535`; `reject(all, …)` и `direct(all, …)` добавляются выключенными: на сервере
  первое блокировало только трафик через него, а второе означало выход сервера напрямую (трафик
  клиента всё равно шёл через VPN), правило же HyRoute заблокировало бы и прямой трафик или пустило
  бы трафик всех программ мимо VPN. Исключение прежнее: `reject(all, udp/443)` — указание на
  «Блокировать QUIC». Строки с перенаправлением (третий аргумент) пропускаются; такая строка
  `all`/`*` без протокола и порта всё равно завершает список, как в Hysteria. Строка «Сейчас
  HyRoute» на странице «Списки» спрашивает о TCP к веб-порту сайта (порт из запроса, для `http://` —
  80, иначе 443) и, если в правилах есть порты, называет его.

## Профили правил

- **Что общее, что своё.** Профиль правил — это `rules.Config` (`defaultAction`, `defaultProfile`,
  `defaultFallback`, `rules`). Всё, что в `settings.Settings` вне `Config` (опции движка), общее,
  как и основной сервер, прокси, группы и DNS. Поле, которое должно быть своим у каждого профиля,
  добавляется в `rules.Config`.
- **Файлы.** `settings.json` всегда хранит правила включённого профиля и главный для них: v1.0.0 и
  все пути записи работают как раньше. `rulesets.json` (`internal/store/rulesets.go`) появляется
  только со вторым профилем: версия формата, `active`, список `{id, name, config}` и — только между
  двумя записями пары — `pending {was, to}`: хэши правил в `settings.json` до и после (`ConfigHash`,
  sha256 JSON правил, разобранных из записываемых байтов). Копия включённого профиля в
  `rulesets.json` обновляется при каждой записи этого файла; `configOfLocked` для включённого
  профиля всегда отдаёт живые правила.
- **Чтение.** `LoadRulesets` читает через `readRegular` (ссылка, точка соединения, папка — «не
  обычный файл»), не больше 16 МиБ. Оболочка разбирается строго (`DisallowUnknownFields`; `version`
  больше известной — «создан более новой версией HyRoute»), каждый `config` тоже строго, но профиль,
  в правилах которого есть только неизвестные поля, загружается как «новее» (`Newer`): его байты
  сохраняются при каждой записи файла, включить, открыть или скопировать его нельзя, переименовать,
  переместить и удалить можно. ID `^[0-9a-f]{8,32}$`, не больше 50 профилей, имя 1–40 символов без
  управляющих и форматных (bidi, zero-width), уникально без учёта регистра.
- **Три вида записи**, все под `saveMu`:
  - S — только `settings.json` (правка правил включённого профиля): `rulesets.json` не трогается,
    его копия просто стареет;
  - R — только `rulesets.json` (создание без включения, переименование, порядок, удаление, правка
    неактивного): `rulesetsOnlyState` освежает копию включённого профиля живыми правилами;
  - P — пара, `Store.WriteRulesPair`: 1) сырые байты `rulesets.json` (`ReadRaw`, даже битые); 2)
    `rulesets.json` с `pending`; 3) `settings.json` — при ошибке байты шага 1 возвращаются
    (`WriteRaw`; файла не было — он удаляется); 4) `rulesets.json` без `pending` (ошибка не страшна:
    следующая запись снова будет парой). P — переключение, создание с включением и любая запись
    `settings.json`, пока на диске есть отметка или `settings.json` отстаёт от работающих правил
    (`rulesetsForCommit`). Если не удалось и вернуть байты, отметка в памяти заставит следующую
    запись переписать `rulesets.json`, а перезапуск до неё завершит прерванную операцию (в журнале).
    Если файла не было (первое создание с включением), вместо отметки следующая запись одного
    `settings.json` сначала удаляет оставшийся `rulesets.json` (`rsLeftover`, строка в диагностике);
    перезапуск до неё так же завершит прерванную операцию. Установка пары — всегда
    `installPairLocked` (он же снимает «`settings.json` отстаёт»), а не один
    `installRulesetsLocked`.
- **Загрузка** (`reconcileRulesets`, без блокировок; её же вызывает откат резервной копии): нет
  `rulesets.json` — функции нет; битый — `rulesetsBroken`: текущие правила работают, переключение,
  создание, правка неактивных и удаление серверов запрещены, файл не перезаписывается; нет
  `settings.json` — правила включённого профиля из копии (опции движка по умолчанию), следующая
  запись — пара; если при этом копия не загрузилась (`rulesets.json` битый, включённый профиль
  «новее» или не компилируется), в памяти правила по умолчанию вместо неизвестных —
  `rsLoad.RulesUnknown`, и `Load` ставит его в `settingsBroken`, как для битого `settings.json`:
  подключение и запись правил отклоняются (иначе трафик шёл бы напрямую, а записанные правила по
  умолчанию после починки `rulesets.json` заменили бы включённый профиль); есть `pending` и хэш
  `settings.json` равен `was` — прерванная запись: правила берутся из `rulesets.json`, следующая
  запись — пара; иначе главный `settings.json`, и отличие от копии принимается в профиль (правка
  v1.0.0 или руками, включая возврат к прежним правилам). Единственная неоднозначность: HyRoute упал
  во время записи пары (или не смог снять отметку), а до следующего запуска `settings.json`
  отредактировали снаружи ровно в прежние правила — тогда запись пары завершится (в журнале имя
  профиля). Во время загрузки файлы не пишутся.
- **Неактивные профили** проверяются `rules.Check` (синтаксис без баз правил, матчеры geosite/geoip
  не строятся) при загрузке и после каждой записи (`prepRulesets`: только новые, изменённые и бывший
  включённый); ошибка хранится в `rsErrors`, такой профиль нельзя включить, но можно открыть без
  включения и исправить (его правка компилируется полностью, с базами). Компиляция и ввод-вывод
  никогда не идут под `c.mu`: между двумя короткими секциями под `saveMu`. `rulesets`, `rsErrors` и
  `rsAt` при изменении заменяются целиком, а не правятся на месте.
- **Токены и ревизии.** Страница шлёт `EditGuard{Ruleset, Rev, EditRev}`. `Ruleset` — ID включённого
  профиля (`"implicit"` до создания файла; принимается и после, пока включён первый профиль) или
  `"edit:<id>"` для правки неактивного без переключения. Он проверяется первым: копия другого
  профиля отклоняется своим текстом («Профиль правил сменился на «X»…», в режиме правки «…включили
  или удалили…»; `errors.Is(err, errRulesetChanged)`). Затем ревизия ([«Сохранение правил и
  ревизии»](#сохранение-правил-и-ревизии)): для включённого — `Rev < rulesAt`; для неактивного —
  `EditRev < rsAt[id]`, где `rsRev` растёт при каждой установке списка, а `rsAt[id]` — `rsRev`
  последней установки, изменившей правила именно этого профиля. Поэтому переименование, порядок,
  создание, удаление, правки и переключения других профилей правку X не отклоняют.
  `Status.ruleset.rev` = `rsRev`: страница в режиме правки перезагружается при `rev > editRev`, в
  обычном — при смене `Status.ruleset.token` или росте `settingsRev`.
- **Переключение** (`SwitchRuleset(id, src, opts)`; `ActivateRuleset` для «Сетей»). Сначала
  `switchPrecheck` (файлы загружены, профиль есть и загружается): отказ приходит до `netManual`, и
  отклонённое переключение не считается ручным выбором. Для окна, трея и CLI затем `netManual()` (до
  `saveMu`); с `SourceNetwork` вызывающий уже держит блокировку «Сетей». Порядок блокировок
  `netActMu → saveMu → mu`, `lifeMu` не берётся; «Переподключить» (`SwitchOptions.Reconnect`) —
  публичный `Reconnect` после снятия всех блокировок. Переключение — это коммит настроек (растут
  `settingsRev` и `rulesAt`, вызывается `OnSettings`), затем `Session.SetRules` и
  `tunnels.Manager.Sync`: новые соединения идут по новому профилю, открытые — по прежнему, кроме
  идущих через серверы, которые новому профилю не нужны: `Sync` их останавливает, и эти соединения
  закрываются (`SwitchResult.Stopped` — имена серверов). Редкий отказ уже после `netManual`
  (компиляция с текущими базами, запись файла, гонка с другой записью) всё равно считается ручным
  выбором.
- **Ссылки.** `eachRulesConfigLocked` — единственный обход правил всех профилей:
  `explicitRefsLocked` (ссылка из неактивного помечается « (профиль правил «X»)», `DeleteProfile`
  подсказывает «Открыть без включения»), `geoDue` (базы, нужные неактивному профилю, тоже
  скачиваются и обновляются). Пока `rulesets.json` битый, каждый сервер считается используемым. Что
  запущено, решает только включённый профиль (`routingLocked`).
- **Трей** — [app.md, «Интерфейс и система»](app.md#интерфейс-и-система).

## Сохранение правил и ревизии

Правила меняются с нескольких страниц сразу («Правила», «Главная», «Списки», «Правила текстом», а
дальше и из «Соединений», трея, CLI), и каждая держит свою копию. Без проверки страница с устаревшей
копией молча вернула бы чужое изменение, а «Настройки» со своей копией — старые правила вместе с
переключателем.

- **Один путь записи** (`internal/app/settings.go`). `commitSettingsLocked(st, next)` вызывается под
  `saveMu`: проверка и запись `settings.json` (`next` — запись `rulesets.json` вместе с ним; какой
  из видов S/R/P, решается внутри, [«Профили правил»](#профили-правил)), затем под `c.mu` установка
  правил и `applyRoutingLocked`. Хвост (журнал, базы правил, kill switch, `OnChange`, `OnSettings`)
  выполняется после снятия `saveMu`, без блокировок. Ошибка записи не меняет ни правил в памяти, ни
  ревизии. Порядок блокировок прежний: `saveMu` → `c.mu`.
- **Писатели:**
  - `SaveRulesIn(EditGuard, cfg)` — только правила (`rules.Config`); опции движка остаются текущими,
    что бы ни было в копии страницы. Страницы «Правила», «Главная», «Списки» (привязка
    `SaveSettings(SettingsView)`).
  - `SaveEngineOptions(EngineOptions)` — только опции движка (`settings.EngineOptions`: те же ключи
    JSON, что у `Settings` вне правил), правила остаются текущими. Страница «Настройки»; без
    проверки ревизии: изменению правил она помешать не может. Синхронизация задачи проверки kill
    switch — в этой привязке.
  - `editRulesIn(EditGuard, fn)` — правка свежей копии правил под `saveMu`, так что между чтением и
    записью никто не вклинится. Порядок: сначала часть проверки, не зависящая от правил
    (`guardTargetLocked`: какие правила адресованы, дальше токен профиля правил), и копия — в одной
    секции `c.mu`, так что отказ приходит раньше `fn` и его не скроет ни `false`, ни ошибка `fn`;
    затем `fn`; затем правило ревизии (`guardRevLocked`) на изменённых правилах. «Правила текстом»
    (`ApplyRulesText(text, replace, guard)`), дальше правило из соединения и CLI.
  - `SaveSettingsIn(EditGuard, st)` — всё сразу; для внутренних вызовов и тестов. `SaveSettings(st)`
    = `SaveSettingsIn(EditGuard{}, st)`.
  - Новая опция движка добавляется и в `Settings`, и в `EngineOptions`
    (`TestEngineOptionsCoverSettings`).
- **Ревизия.** `settingsRev` (atomic): +1 за каждую успешную запись, при установке под `c.mu`; 1
  после `Load`. `rulesAt` (под `c.mu`) — ревизия последней записи, изменившей правила (сравнение как
  в `settings.json`, через JSON). Запись одних опций движка `rulesAt` не двигает. Ревизию несут
  `SettingsView.rev` (читается в той же секции `c.mu`, что и копия), `RulesTextView.rev`,
  `SaveResult.rev`, `Status.settingsRev` и событие Wails `settings` (payload — новая ревизия,
  `ctl.OnSettings`).
- **Отказ.** Запись с `EditGuard{Rev}` отклоняется, если `Rev != 0 && Rev < rulesAt` и присланные
  правила отличаются от текущих: «Правила изменились в другом месте (например, из «Соединений»):
  изменение не сохранено, список обновлён — повторите.» Копия, устаревшая только из-за записи опций,
  и копия с теми же правилами проходят. `Rev = 0` — без проверки (внутренние вызовы, CLI).
  Добавление пачкой в «Правилах текстом» ревизию не шлёт: правила добавляются после текущих.
- **Страницы.** `ui.settingsRev` — наибольшая увиденная ревизия (статус раз в секунду и событие
  `settings`). «Правила» и «Главная» перезагружают копию при `ui.settingsRev > rev`, но только в
  простое: не во время своей записи, не при открытом редакторе правила, тексте или перетаскивании.
  Записи «Правил» идут цепочкой в порядке кликов, и каждая шлёт ревизию, полученную предыдущей. Если
  за время перезагрузки пришла новая ревизия, после неё страница перезагружается ещё раз; неудачная
  перезагрузка не повторяется, пока ревизия не вырастет снова. После отказа «Правила» и «Главная»
  показывают ошибку и перезагружаются. «Правила текстом» после отказа замены текст пользователя не
  трогают: обновляется только ревизия, так что повторное «Сохранить список» заменит им новые правила
  сознательно, а кнопка «Показать текущие правила» / «Вернуть мой текст» меняет текст в редакторе,
  не теряя ни один из двух.
- `EditGuard.Ruleset` и `EditRev` (и `SettingsView.editRev`, `warnings`) — для профилей правил:
  токен набора правил и ревизия неактивного профиля при его правке.

## Правило из соединения

Меню строки «Соединений» (правая кнопка, «…», клавиша меню/Shift+F10, «Создать правило…» в
подробностях; `ConnMenu.svelte`) создаёт обычное правило из того, что показывает строка, и ставит
его так, чтобы оно сразу сработало.

- **Что движок знал о потоке.** В записи потока хранятся предки владельца (`Record.Parents`: путь
  или имя, ближайший первым, до `procinfo.MaxDepth`) и сайты DNS-кэша, по которым решал `decide`
  (`Record.Sites`: `Cache.Sites`, одно чтение кэша на решение, не больше 16 сайтов по 8 имён,
  `SitesPartial` при обрезке). В UI они не уходят (`json:"-"`), остаются в кольце закрытых.
  `Fields.ECH` ставит relay, если в ClientHello было расширение ECH, что бы ни решил движок.
  `Fields.Excluded` — вид обязательного исключения. Go находит запись по ID (`Registry.Lookup`:
  живые, затем оба кольца закрытых — соединений и строк DNS) и сверяет PID, протокол, адрес, процесс
  и путь (ID начинаются заново в каждой сессии). Найдена — исключение, ECH, домен, предки и сайты
  берутся из записи, а не из данных WebView. Нет — из строки; сайты DNS группируются по живому кэшу
  (`DNSSites`), имена, которых там нет, становятся отдельными сайтами (`SitesPartial`). Строка
  DNS-запроса (`Stage "dns"`, `domainSrc` `query`) — это имя без соединения: правило строится только
  по имени (протокол и адрес неизвестны), пункты программы скрыты, если спрашивала служба DNS
  Windows (`attrib` `dnscache`), «Проверить адрес» получает имя.
- **Где встаёт правило** (`internal/rules/connrule.go`). `Winner` — правило, которое решает поток
  сейчас, ровно как движок: по точному имени; по сайтам — `firstMatchAny` каждого сайта (цепочка
  CNAME — один сайт), при согласии маршрутов побеждает правило первого сайта, при расхождении —
  решение без домена (`EvaluateNoDomain`), это «неоднозначно». Шаг сайта (`siteWinner`) и сравнение
  маршрутов (`sameRoute`) общие с `Set.EvaluateSites`; совпадение проверяет
  `TestWinnerAgreesWithEngine`. `Place` — первое включённое правило, которое *может* поймать поток:
  любым именем любого сайта или без имени; `geosite:`/`geoip:` из ещё не скачанной базы (`pending`)
  считаются совпадающими, неизвестная категория — нет. Неизвестный протокол или порт (строки
  DNS-запросов) удовлетворяет условию на них. `Place <= Winner` всегда.
- **Добавить или изменить** (`internal/app/connrules.go`, `AddConnRule`). Быстрый пункт при `Place
  == Winner` и тех же условиях у решающего правила (`SameMatch`: программы, сайты, протокол, порты
  без учёта порядка и регистра) меняет в нём действие и сервер (запасные сохраняются, только если
  сервер тот же); иначе новое правило вставляется над `Place`. Правило из редактора всегда новое:
  над `Place`, если ловит поток, иначе над первым пересекающимся (`PlaceRule`). После вставки Go
  считает: `OverriddenBy` — правила выше, пересекающиеся с новым (`Intersects`: протокол, порты,
  программы, сайты и адреса; родство процессов не учитывается), `Shadowed` — правила ниже, которые
  оно закрывает целиком, `Narrowed` — правила между `Place` и прежним победителем с другим
  маршрутом, `NotEffective` — правило ловит поток, но у адреса несколько сайтов с разными правилами.
  Имя провайдера ECH (`PublicName` сессии или встроенный список `dnscache.KnownPublicName`) никогда
  не становится правилом сайта: быстрое правило, которое его ловит, отклоняется.
- **Запись и отмена.** Всё — одна правка через `editRulesIn` под `saveMu` ([«Сохранение правил и
  ревизии»](#сохранение-правил-и-ревизии)) с токеном профиля правил, для которого строилось меню.
  Отмена — в памяти, последние 20 операций (`connUndo` под своим листовым `undoMu`, порядковый номер
  `Seq` для UI), по ID правила и токену профиля: удаляет добавленное, возвращает изменённое, только
  пока правило ровно такое, каким его сделали. Смена профиля — отказ с названием профиля, запись
  остаётся; восстановление из резервной копии очищает список (`clearConnUndo`).
- **UI.** Сообщение (`showConnResult`, группа тостов `connrule`) называет правило заголовком
  страницы «Правила» (`ruletitle.ts`), где оно стоит и что его перекрывает; «Открыть правило» ищет
  его на «Правилах» через `locateRule` (по ID; по индексу, пока ревизия не менялась; иначе по
  единственному равному правилу). Редактор «Правил» сохраняет правку в то же правило, где бы оно
  теперь ни стояло, а если его изменили или удалили — предлагает добавить черновик новым. Правила,
  созданные в UI, получают ID.

## Объяснение маршрута и линтер

- **«Почему этот адрес пойдёт сюда?»** `rules.Set.Explain(app, домен или IP)` возвращает трассу по
  всем правилам: совпало / почему нет (приложение, протокол, домен), победитель, действие и профиль.
  Для IP показываются имена из DNS-кэша по сайтам, если движок запущен (цепочка CNAME — один сайт,
  правило срабатывает по любому её имени); если сайты расходятся, решение показывается без имени
  (так решает движок, если SNI/Host не дал имени), а в заметке — какое правило сработает для каждого
  имени. Программа без расширения («chrome») проверяется как chrome.exe. Цепочку родителей
  (наследование) по имени exe не проверить: объяснение это оговаривает. Порт и протокол задаются в
  «Проверить адрес»; без порта он берётся из адреса (`x.com:8443`, `[2001:db8::1]:443`) или из
  ссылки (`https://` → 443, `http://` → 80), о чём говорит заметка, а порт из поля важнее (заметка
  «Порт из адреса (443) не учтён»). Без порта правила с портами считаются несовпавшими. UDP 443 при
  настройках QUIC по умолчанию объясняется без имени, как решает движок: если маршрут зависит от
  имени, победитель — синтетический шаг «Блокировка QUIC» (`rules.StepQUICBlock`, индекс −2).
- **Линтер правил:**
  - правило, полностью перекрытое вышестоящим, «никогда не сработает»;
  - `Tunnel` на отсутствующий или удалённый профиль;
  - `*.x` при явной нужде в `x`: подсказка;
  - сайт, который не может совпасть ни с одним именем (`rules.SiteProblem`: невозможные символы или
    пустые части имени), — предупреждение: `Compile` такие элементы сохраняет, чтобы старые
    настройки загружались, а «Правила текстом» отклоняют их как ошибку.
