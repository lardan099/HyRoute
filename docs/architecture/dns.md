# DNS

## Доменная атрибуция

**DNS cache** (`internal/dnscache`) наполняется от H2: UDP целиком, TCP 53 только если сообщение
уместилось в сегмент (MVP). Ответ из H2 принимается, только если он отвечает на исходящий запрос,
увиденный H2 (тот же транспорт, локальный IP:порт, IP:порт сервера, txid и вопрос), не позже 30 с и
один раз; посторонние пакеты с порта 53 игнорируются. Ответы, пришедшие через туннель (`udp.go`),
принимаются по тому же правилу: запрос регистрируется при отправке в туннель (`udpSend`), ответ
сверяется в `udpSession.read` до доставки приложению. Размер ограничен строго, 200 000 пар: при
переполнении вытесняется пара, истекающая раньше других из 8 случайных. Один ответ добавляет не
больше 256 пар. Хранит:
- `name → {(сайт, ip) → expiry}` и `ip → {(сайт, name) → expiry}`; TTL берётся из ответа, но не
  меньше 60 с и не больше 24 ч: служба DNS-клиента Windows отвечает программам из своего кэша весь
  TTL записи (MaxCacheTtl по умолчанию — сутки), не спрашивая сеть;
- CNAME-цепочки разворачиваются: `ip` привязывается к запрошенному имени и ко всем именам цепочки, и
  все они — один сайт (сайт назван по запрошенному имени). Доменное правило срабатывает для сайта,
  если подходит любое его имя (`rules.Set.EvaluateSites`); расходиться могут только разные сайты на
  одном IP (соседи по CDN);
- публичные имена ECH из HTTPS/SVCB-ответов хранятся отдельно (`Cache.PublicName`, не больше 4096
  имён и не дольше 1 ч: любая зона может объявить публичным любое имя);
- `Sweep` раз в 5 с просматривает не больше 4096 пар, чтобы не держать блокировку; истёкшие пары,
  ещё не удалённые, при поиске не видны. Поэтому счётчик «пар в DNS-кэше» в статистике
  (`Stats.DNSPairs` = `Cache.Len`) приблизительный: в него входят истёкшие, ещё не удалённые пары, а
  CDN-имя, общее для двух запрошенных имён, считается дважды;
- при смене IP у домена старые пары живут до своего TTL, это не ошибка;
- при старте опционально подгружается кэш ОС через `DnsGetCacheDataTable`. Функция
  недокументированная и даёт только имена; имена резолвятся заново через `DnsQuery` с флагом
  `NO_WIRE_QUERY`, то есть только из кэша ОС.

Нормализация имени: lower-case, без trailing dot, IDN в punycode (`golang.org/x/net/idna`, профиль
Lookup). Нормализация одинаковая для правил, DNS, SNI и Host.

**Приоритет источников:** SNI (в том числе внешний SNI ECH-hello, если это не известное публичное
имя ECH) > HTTP Host > DNS cache (по сайтам: имена одной CNAME-цепочки — один сайт) > Unknown. SNI
всегда перекрывает неоднозначное DNS-сопоставление. DoH/DoT браузеров мы не видим. Поэтому общий IP
CDN может лежать в cache под именем соседнего сайта, и решение по DNS для веба было бы неверным
(заблокированный сайт ушёл бы Direct по имени разрешённого соседа). При `exactWebDomains`
веб-соединения, итог которых зависит от домена, всегда идут через SNIFF: DNS cache остаётся запасным
источником, если SNI/Host не найден. QUIC с неизвестным доменом режется, и браузер уходит на TCP.
Цена — такие Direct-соединения проходят через relay. Решения, которые от домена не зависят (правило
по приложению, нет доменных правил), по-прежнему принимаются на пакетах. Настройка применяется при
перечитывании правил.

## DNS-политики

«Настройки» → «DNS» (`dns.json`, по умолчанию всё выключено). Настройки общие, не по профилям
правил. Без них движок видит DNS только пассивно (H2), путь пакетов байт в байт прежний: указатель
`Core.DNSPol` пуст, фильтр H1 не меняется.

**Что перехватывается** (`Core.dnsTarget`). Windows (SMHNR) и встроенный резолвер Chrome шлют один
запрос DNS-серверам всех адаптеров и берут первый положительный ответ, поэтому сервер назначения
классифицируется сначала по принадлежности адаптеру (фоновый снимок `SysDNSView`, `sysdns.Snapshot`:
DNS-серверы адаптеров со шлюзом по умолчанию и без, суффиксы DNS и пространства NRPT), потом по
диапазону:
- основной: DNS-сервер адаптера со шлюзом или публичный адрес, ничей (программа сама спрашивает
  `8.8.8.8`);
- другой адаптер: DNS-сервер любого другого адаптера, любого диапазона (корпоративный VPN, Tailscale
  `100.100.100.100`, виртуальные адаптеры): прямые имена ему не меняются, а отрицательный ответ
  туннеля на имя «через VPN» уходит этому серверу (`dnspolicy.ForSecondary`);
- прочие частные, CGNAT и link-local адреса, loopback, TCP к IPv6 link-local — как раньше. Промах
  просит новый снимок в фоне (не чаще раза в 5 с), пакетная петля никогда не ждёт ОС. Поэтому ответ
  на UDP-запрос к DNS-серверу с IPv6 link-local адресом HyRoute не усекает флагом TC (повтор по TCP
  ушёл бы мимо политики): лишние адреса отбрасываются, а если не помещается и один — SERVFAIL.

**Порядок решения** (`dnspolicy.Policy.Classify`, до него движок пропускает не стандартные
рекурсивные запросы и свой трафик — PID HyRoute и его Hysteria):
1. имена серверов Hysteria (постоянно), проверки Windows и хост своего прямого сервера (постоянно),
   хосты, к которым HyRoute обращается сам (2 минуты: `app.OwnDial` перед каждым прямым соединением
   HyRoute записывает хост в набор контроллера `dnspolicy.OwnNames` — есть сессия или нет, — а
   движок каждой сессии читает этот набор через `Core.OwnName`, так что загрузка, начатая до или во
   время подключения, покрыта с первого пакета) — как раньше, кто бы ни спрашивал;
2. локальные имена (одна метка, `.local`, `.lan`, `.home.arpa`, `.arpa` и др., суффиксы адаптеров,
   кроме публичных суффиксов (`com`, `co.uk`, `com.ru`; `rules.Registrable`) — их задаёт сеть через
   DHCP, и `com` сделал бы локальным весь домен верхнего уровня; остаток: сеть может назвать
   суффиксом обычный домен, и его имена уйдут её серверу, NRPT, имена входа роутеров) — как раньше;
3. «Не давать браузерам обходить DNS»: канарейка Firefox — NXDOMAIN; с «Отключать ECH» HTTPS/SVCB —
   NODATA;
4. «DNS по правилам»: `rules.Set.EvaluateName` по одному имени. Протокол, порты и адрес неизвестны,
   программа известна только у собственного резолвера программы. Правило с неизвестной частью и
   совпавшим сайтом — «кандидат»: VPN у победителя или любого кандидата выше — через VPN (первое
   такое правило), «блок» — только если блок у всех, иначе напрямую. Правила без сайтов с
   неизвестной частью не считаются. С «Сверяться с правилами по IP и geoip» правило «Напрямую» по
   адресу выше решающего (кроме только локальных диапазонов) оставляет имя как раньше. Туннель: AAAA
   при «Не пускать IPv6 в VPN» — NODATA, иначе разрешается через сервер правила (с запасными; член
   группы выбирает `Core.pick` с `Hint.Stable`: поиск без побочных эффектов, один сайт — один член);
   блок — NXDOMAIN;
5. напрямую: со «Шифровать прямые DNS-запросы» разрешается своим DoH/DoT; сбой, отмеченный
   недоступным сервер, NXDOMAIN или NODATA для A — запрос уходит как раньше.

**UDP** (`udpOut` → `dnsUDP` перед `udpRoute`): владелец из таблицы атрибуции; неизвестный владелец
(свежий сокет программы) ждётся вне петли, как у нового соединения (до 100 мс). Ответ собирается и
инжектится входящим от сервера, которому шёл запрос; сам запрос никуда не уходит. Разрешение идёт в
горутине (не больше 256 одновременно; нет места — туннельное имя SERVFAIL, прямое как раньше). Ответ
передаётся через `dnscache.AddAnswerFor` (только пара «наш запрос — его ответ»).

**TCP**: SYN к перехватываемому серверу отражается в relay в режиме `nat.DNS` (`Entry.DNSDest`
фиксирует вид сервера на соединение), `Core.ServeDNS` отвечает на сообщения (не больше 32, 60 с, 10
с простоя). То, что политика не берёт, передаётся одному соединению к исходному серверу по маршруту,
который соединение получило бы сегодня (служба DNS и частный сервер — напрямую, иначе по правилам на
адрес; туннель без запасного пути, блок — RST). Ответы с чужим ID (остаток многосоставного ответа)
пропускаются. Передача зоны (AXFR/IXFR) отдаёт остаток соединения серверу целиком: копирование в обе
стороны, как у обычного соединения relay. Разрешение идёт в контексте relay: `Abort` его прерывает.

**Строки «Соединений»**: запросы, на которые ответил HyRoute, собираются в строку на (PID, имя,
правило, маршрут, сервер, исход) со счётчиком, закрываются через 30 с тишины или 5 минут и хранятся
в своём кольце (1000), не вытесняя соединения. Статистика их не считает.

**Резолвер** (`dnsproxy.Resolver`): кэш по (путь, профиль, имя, тип, DO, CD) с TTL ≤ 300 с (негативы
≤ 60 с), singleflight, клиенты DoH (HTTP/2, без прокси окружения, без User-Agent), DoT и TCP (только
через туннель). Через туннель клиент звонит через SOCKS5 Hysteria (`Endpoint.Dial` на каждый
дозвон), у пресетов — на их bootstrap-адреса. Здоровье на клиент: 3 ошибки подряд — «не отвечает» на
30 с, потом 60, 120 с, после паузы один пробный запрос. Ответы через туннель ограничиваются 300 с,
негативы 60 с (`Reply`).

**Отказ** — всегда в сторону «не отправлять напрямую»: туннель недоступен, резолвер туннеля не
отвечает или отмечен, нет места, паника — SERVFAIL ([failure.md, «Два сценария
отказа»](failure.md#два-сценария-отказа)). Единственное исключение — пауза портала на 5 минут
(«Разрешить имена напрямую на 5 минут»): имя через VPN при **недоступном** туннеле уходит как
раньше.

**Браузеры и DoH**: с «Не давать браузерам обходить DNS» соединения браузера (имя exe из списка) на
443/853 к известным адресам и именам DoH (`dnspolicy.IsDoHAddr`/`IsDoHHost`, имена из DNS-кэша, SNI
в relay) блокируются в `decide`, `untrackedRoute` и `RelayDecide`; включение сбрасывает уже открытые
(`Core.DropDoH` + `relay.AbortWhere`).

**Переключения в сессии** (`Session.SetDNS`): включение — сначала фильтр (`SetDNSCapture`), потом
политика; выключение — сначала политика, потом RST DNS-соединениям (`Core.AbortDNS`,
`relay.AbortWhere`) пока фильтр их ещё отражает, потом фильтр. `applyRoutingLocked` вызывает
`SetDNS` раньше `SetRules`: новый сервер запускает Hysteria с уже известным именем.

**Кэш DNS Windows** (`DnsFlushResolverCache`, не чаще раза в 2 с): при запуске HyRoute с включённой
политикой, при подключении, при изменении настроек DNS, при сохранении правил (и переключении
профиля) с «DNS по правилам», когда туннель поднялся после SERVFAIL или паузы, при начале паузы и
после отключения; при выходе (`Shutdown`) ожидающая очистка выполняется сразу, до возврата, без
ограничения частоты (не дольше 3 с).
