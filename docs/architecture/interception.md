# Перехват: WinDivert, атрибуция, исключения

## Ключевые решения

| Вопрос | Решение |
|---|---|
| Перехват | **WinDivert 2.2.2** (DLL + подписанный `WinDivert64.sys` рядом с exe, драйвер грузится при первом `WinDivertOpen`, отдельный инсталлятор не нужен) |
| Биндинги | Свои, на `windows.NewLazyDLL` (без cgo). Open/RecvEx/SendEx/Shutdown/Close/SetParam/GetParam + `WINDIVERT_ADDRESS`. Только x64: `UINT64`-аргументы передаются одним регистром, сборка под 386 намеренно не компилируется |
| Ядро | `hysteria-windows-amd64.exe` app/v2.12.3, режим `socks5`, дочерний процесс в Job Object |
| Как трафик попадает в SOCKS5 | TCP: «отражение» пакетов (reflect, как в примере WinDivert `streamdump`) в локальный relay-listener. UDP: на уровне пакетов, без listener'а. Датаграммы уходят через SOCKS5 UDP ASSOCIATE, ответы собираются в пакеты и инжектятся обратно |
| Что перехватывается | **Только outbound** (+ снифф DNS-ответов). Входящий трафик Direct-соединений в user space не попадает, поэтому скачивание не просаживается |
| Туннель недоступен | Tunnel-соединения отклоняются (RST/drop), напрямую не уходят. Direct и Block работают как обычно |
| UI | Wails v2 + Svelte + TS, трей через `energye/systray`, single-instance lock |

### Почему WinDivert, а не Windows Packet Filter (ndisapi)
1. **Атрибуция процесса из ядра.** У WinDivert есть слои `SOCKET` и `FLOW` поверх WFP ALE: событие
   приходит с `ProcessId`, 5-tuple и `EndpointId`. Событие `SOCKET_CONNECT` генерируется на
   ALE_AUTH_CONNECT, *до* отправки SYN. ndisapi работает на уровне NDIS, PID там нет. ProxiFyre для
   этого опрашивает таблицы IP Helper, и там неизбежна гонка.
2. **Reinject с разворотом направления.** Outbound-пакет можно переписать и инжектить как inbound.
   На этом держится прозрачный relay для TCP.
3. **Фильтр в ядре.** Loopback, приватные сети и IP сервера Hysteria отсекаются до user space.
4. **Не нужен инсталлятор драйвера.** ndisapi ставит драйвер через MSI.

Минусы WinDivert: выше накладные расходы на пакет, чем у ndisapi. Их гасят батчинг `RecvEx`/`SendEx`
и перехват только outbound. Последний релиз вышел в 2022 году, но версия стабильная. Лицензия
LGPLv3, динамическая загрузка DLL допустима.
Общий риск для обоих драйверов: часть античитов (Vanguard, FACEIT, иногда EAC) и AV ругаются на
загруженный пакетный драйвер. Это указано в README.

## Хэндлы WinDivert

Приоритет в WinDivert 2.x: **большее значение видит пакет раньше** (диапазон −30000…30000, 0 —
«средний», по умолчанию). Пакет, инжектнутый хэндлом с приоритетом P, дальше видят только хэндлы с
приоритетом < P, сам хэндл его повторно не получает.

| # | Слой | Приоритет | Флаги | Фильтр (упрощённо) | Назначение |
|---|---|---|---|---|---|
| H1 | NETWORK | **1000** (1001 при горячей замене; при каждой замене все прежние H1 сразу перестают принимать пакеты и закрываются через 3 с) | — (inline) | `outbound and !loopback and (tcp or udp) and not <exclusions>`<br>`or (inbound and tcp.DstPort == RELAY_PORT)` | Основной: решения, NAT, reflect. Второе условие ловит внешние попытки подключиться к relay, такие пакеты дропаются |
| H2 | NETWORK | 1010 | SNIFF, RECV_ONLY | `!loopback and ((outbound and (udp.DstPort == 53 or (tcp.DstPort == 53 and tcp.PayloadLength > 0))) or (inbound and (udp.SrcPort == 53 or (tcp.SrcPort == 53 and tcp.PayloadLength > 0))))` | Пассивный разбор DNS: исходящие запросы запоминаются, ответ принимается только на увиденный запрос |
| H3 | SOCKET | 1020 | SNIFF, RECV_ONLY | `!loopback and (event == CONNECT or event == BIND or event == CLOSE)` | Атрибуция PID, запись раньше первого пакета |
| H4 | FLOW | 1030 | SNIFF, RECV_ONLY | `!loopback` | ESTABLISHED/DELETED: чистка, длительность соединения |

`<exclusions>` в H1 задаются диапазонами прямо в фильтре: `0/8, 10/8, 127/8, 169.254/16, 172.16/12,
192.168/16, 224/4, 240/4` (включая 255.255.255.255), для IPv6 `::/127, fe80::/10, fc00::/7,
ff00::/8`, плюс **все IP сервера Hysteria**. Опционально добавляется `100.64/10` (CGNAT/Tailscale),
по умолчанию выключено. IP серверов нормализуются (без zone, без дублей, без адресов из
фиксированных диапазонов), их не больше 100 (компилятор фильтров WinDivert вмещает 107), иначе
Connect или запуск профиля получает ошибку. Применённый список меняется только после успешного
открытия хэндла; `tunnels.Manager` при ошибке откатывает список профиля.
Каждое исключение записывается как `(ipv6 or ip.DstAddr < A or ip.DstAddr > B)` / `(ipv6 or
ip.DstAddr != X)` (и симметрично для IPv6). Причины: в языке фильтров WinDivert `not`/`!`
применяется только к одиночной проверке, `not (…)` — ошибка разбора (`WinDivertOpen` → 87); а
проверка поля, которого у пакета нет (`ip.*` у IPv6-пакета), ложна, поэтому другое семейство
пропускается явно. Фильтры проверяются настоящим компилятором и вычислителем WinDivert 2.2.2,
собранным под Linux (`tools/wdfilter`, тест `internal/divert/filter_wdfilter_test.go`).

**DNS-политики** ([dns.md, «DNS-политики»](dns.md#dns-политики)). Пока включена хоть одна настройка
DNS, в H1 диапазоны исключений сгруппированы отдельно и к ним добавлено «или»: `((<диапазоны>) or
udp.DstPort == 53 or fragment or tcp.DstPort == 53 or tcp.SrcPort == RELAY)`. Так перехватывается
DNS к частным и link-local адресам (роутер), все фрагменты к ним (WinDivert читает порты только в
первом фрагменте, решение принимает `Core.dnsHold`) и ответы relay частному адресу, отражённому в
него. IP серверов Hysteria и loopback по-прежнему не попадают. Это 4 теста фильтра: 45 постоянных
плюс 2 на адрес сервера, со 100 адресами 245 из 256. Без политики фильтр байт в байт прежний;
включение и выключение меняют H1 горячей заменой (`Engine.SetDNSCapture`).

Параметры H1: `QUEUE_LENGTH=8192`, `QUEUE_TIME=2000ms`, `QUEUE_SIZE=8MB`. Пакеты H1 читает один цикл
на хэндл: `RecvEx` пачками по 64, решение и `SendEx` в том же цикле, поэтому пакеты одного
соединения не переупорядочиваются.

### Сосуществование с zapret, GoodbyeDPI и другими программами на WinDivert

Проверено по исходникам: `winws` из zapret (`nfq/darkmagic.c`) и GoodbyeDPI (`src/goodbyedpi.c`)
открывают свои NETWORK-хэндлы с **приоритетом 0**.

**Порядок прохождения пакета.** H1 стоит выше (1000), поэтому новый outbound-пакет сначала попадает
к нам:
- **Direct**: реинжектим без изменений через H1. Дальше пакет идёт к хэндлам с приоритетом < 1000,
  то есть к zapret/GoodbyeDPI, и обход DPI работает как без нас.
- **Tunnel**: пакет превращается в inbound к локальному relay. Фильтры DPI-обходчиков ловят outbound
  на 80/443, так что до них он не доходит. Ответы relay (`tcp.SrcPort == RELAY`) мы тоже ловим
  первыми и разворачиваем в inbound.
- **Трафик Hysteria к серверу** исключён фильтром H1 и идёт мимо нас сразу к zapret. Если в zapret
  включены фейки для UDP (например, `--wf-udp=443` с fake QUIC) и порт сервера под них попадает,
  zapret может подмешивать мусорные датаграммы. Hysteria с obfs их отбрасывает, но при проблемах
  сервер нужно добавить в исключения zapret. Это есть в README.

**Почему не ниже zapret.** Тогда zapret первым видел бы Tunnel-соединения: резал бы ClientHello на
сегменты и инжектил фейковые пакеты с намеренно битой контрольной суммой или малым TTL. Эти пакеты
шли бы к нам, мы отражали бы их в relay и **пересчитывали контрольную сумму**, превращая фейк в
«валидные» данные. Поток в relay был бы испорчен.

**Один движок на машину.** Блокировка единственного экземпляра Wails действует в пределах сеанса
Windows, а две копии HyRoute (быстрая смена пользователя, RDP) перехватывали бы трафик друг друга.
Поэтому `session.Start` захватывает Global-мьютекс `Global\HyRoute-engine-3f9b2c71`
(`engine.LockMachine`), `Stop` его отпускает. Занят другим сеансом → `ErrOtherEngine` («HyRoute уже
подключён в другом сеансе Windows…»). Мьютекс создаётся с владельцем BUILTIN\Administrators и DACL
только для SYSTEM и администраторов. Объект с этим именем, которым владеет кто-то другой (его может
создать любой процесс без прав администратора), не считается чужим HyRoute: подключение идёт без
межсеансовой блокировки. Внутри процесса перед мьютексом стоит семафор с ожиданием до 15 с: Connect
сразу после отключения ждёт остановки прежнего движка, иначе `ErrStillStopping`.

**Уникальные уровни.** В документации WinDivert: «A packet is only diverted once per priority
level». Если два хэндла на одном уровне ловят один и тот же пакет, кто его получит, не определено, и
второй может его вообще не увидеть. Поэтому ни один наш хэндл не стоит на 0, и у каждого свой
уровень.

**Чужой драйвер WinDivert.** Все программы на WinDivert 2.x используют одну и ту же службу ядра
`WinDivert` и устройство `\\.\WinDivert`. Как работает `WinDivertOpen` (dll/windivert.c):
1. Если устройство уже есть (драйвер загружен другой программой), DLL открывает его и **не** грузит
   наш `.sys`. Проверка версии пропускает любой драйвер с major ≥ 2.
2. Если устройства нет, но служба `WinDivert` уже зарегистрирована, DLL запускает **тот `.sys`, на
   который указывает служба** (например, `C:\zapret\...\WinDivert64.sys`), а не наш.
3. Иначе регистрирует службу на наш `.sys`, запускает её и сразу помечает на удаление. Драйвер
   выгружается, когда закроется последний хэндл у всех программ.

Что делает HyRoute:
- Перед открытием читает службу `WinDivert` через SCM: существует ли, запущена ли, её `ImagePath`.
  Если путь не наш, в лог и UI идёт «Драйвер WinDivert предоставлен другой программой: `<путь>`».
- После открытия читает `WINDIVERT_PARAM_VERSION_MAJOR/MINOR`. Нужна 2.2 или новее. Если загружен
  2.0/2.1 (старые сборки GoodbyeDPI/zapret), хэндлы закрываются, а в UI понятная ошибка: какая
  версия загружена, откуда, и что делать (закрыть ту программу или перезагрузиться). Молча работать
  на непроверенном драйвере не будем.
- Драйверы WinDivert 1.x (службы `WinDivert1.0`…`WinDivert1.4`, очень старый GoodbyeDPI) — это
  другое устройство, наши приоритеты на них не действуют, и порядок не определён. Если такая служба
  запущена, выводим предупреждение.
- Ошибка загрузки `WinDivert.dll` не кэшируется: следующий Connect пробует снова. DLL без нужных
  экспортов выгружается.
- Коды ошибок `WinDivertOpen` переводятся в сообщения (`internal/divert/errors.go`):

| Код | Причина | Сообщение в UI |
|---|---|---|
| 2 / 3 | нет `.sys` или служба указывает на удалённый файл | нет файла рядом с exe → «переустановите». Служба указывает на чужой отсутствующий файл → «остаток удалённой программы» + кнопка «Удалить устаревшую службу WinDivert» (удаляет только **остановленную** службу) |
| 5 | нет прав | запустить от администратора |
| 87 | фильтр или параметры отклонены | внутренняя ошибка + путь драйвера другой программы, если служба `WinDivert` указывает на него |
| 577 | подпись драйвера не принята | файлы повреждены или политика запрещает сторонние драйверы |
| 654 | несовместимый загруженный драйвер | закрыть программы на WinDivert или перезагрузиться, с указанием пути |
| 1072 | драйвер выгружается | повторить через пару секунд (1 автоповтор через 2 с, только для первого хэндла в `Engine.Start`) |
| 1275 | драйвер заблокирован | антивирус, античит или ВМ без поддержки драйверов |
| 1753 | отключена служба BFE | включить Base Filtering Engine |

## Атрибуция процесса

```
H3 SOCKET_CONNECT/BIND  ─┐
H4 FLOW_ESTABLISHED      ├─► ConnTable
                         │     key5: (proto, localIP, localPort, remoteIP, remotePort) → {pid, endpointId, ts}
                         │     port: (proto, localPort, remote)                        → {pid, endpointId}   (local IP не указан в событии)
                         │     bind: (proto, localPort)                                 → {pid, endpointId}
                         │     byEndpoint: endpointId → set(key)
H3 SOCKET_CLOSE ─────────┤  удаление всех ключей endpoint'а (только если ключ ещё принадлежит ему)
H4 FLOW_DELETED ─────────┘  финал статистики в «Соединениях» и закрытие NAT-записи (ConnTable не трогается)
```

Каждая запись истекает отдельно, через 30 мин без обновления; `bind` живёт, пока его сокет даёт
события. Таблица ограничена 32768 записями, при переполнении вытесняются дольше всех не
обновлявшиеся. После промаха поиск идёт дальше: `bind`, pending queue, IP Helper.

Поиск PID для нового пакета, по убыванию точности:
1. точный `key5`;
2. `(proto, localPort, remote)`, затем `bind` по (proto, localPort). Для UDP-сокетов без connect это
   основной путь;
3. **pending queue**: пакет паркуется максимум на **100 мс**, ожидая события H3/H4 (таблица будит
   ожидающих при каждой вставке, без поллинга). Через **20 мс** делается синхронный
   `GetExtendedTcpTable/GetExtendedUdpTable (OWNER_PID)`;
4. таймаут: процесс `Unknown`. Правила только по приложению не сработают, доменные и default
   сработают.

Pending queue ограничена: 128 flow, 8 пакетов на flow и 8 МБ на всё. Если нет места для нового flow,
владелец сразу синхронно запрашивается у IP Helper (attrib `iphelper`); только если его там нет,
пакет решается как `Unknown` (attrib `pending-full`), трафик не блокируется. Пакеты уже ждущего flow
сверх 8 (или сверх 8 МБ) отбрасываются: UDP-приложение повторит. Оба случая считает `pendingFull` в
статистике движка (диагностика). Повторные SYN одного flow в очереди сливаются.

**Снимок таблицы TCP.** Кроме точечного `LookupTCPOwner` есть снимок `attrib.ReadTCPTable` /
`TCPSnapshot`: `GetExtendedTcpTable` обеих семей адресов, строки LISTEN включены, 4in6-строки из
IPv6-таблицы нормализуются так же, как ключи поиска. По нему движок определяет владельца соединений
без состояния и серверную сторону входящих соединений ([routing.md, «Где принимается
решение»](routing.md#где-принимается-решение), «Смена правил»).

**PID → процесс.** `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, затем
`QueryFullProcessImageNameW` и `GetProcessTimes`. Запись кэша ключуется парой `(pid, creationTime)`:
при каждом обращении время создания процесса под этим PID сверяется заново (`OpenProcess` +
`GetProcessTimes`), и если PID занял другой процесс, запись запрашивается заново вместе с цепочкой
предков. Запись завершившегося процесса отдаётся, пока PID никто не занял; раз в 5 с такие записи
удаляются.

**Дерево процессов** для правил с наследованием. Раз в 0,5 с снимается
`NtQuerySystemInformation(SystemProcessInformation)`: в отличие от `CreateToolhelp32Snapshot` он
отдаёт `CreateTime` каждого процесса, и PID, переиспользованный процессом с тем же родителем, не
выглядит прежним процессом. Toolhelp остаётся запасным вариантом, если запрос не удался (без ctime).
Есть и on-demand запрос при промахе. Для каждого `(pid, ctime)` запоминается цепочка предков:
(родительский PID, ctime родителя < ctime ребёнка) + путь. Цепочка переживает смерть лаунчера:
лаунчер запустил игру и закрылся, а правило лаунчера с «наследовать» продолжает действовать на игру.
Глубина до 8. Ограничение: лаунчер, который запустил процесс и вышел между двумя снимками, ни разу не
выйдя в сеть, в дерево не попадает, и правило «и дочерние» для его потомков не срабатывает (точно ловить
такие запуски могла бы только трассировка ETW).

**Dnscache.** PID службы берётся через `QueryServiceStatusEx("Dnscache")`. Его трафик на 53 порт и
TCP на 443/853 (DoH/DoT) к DNS-серверам сетевых адаптеров (`GetAdaptersAddresses` в
`internal/sysdns`, тот же список берёт kill switch, [failure.md, «Kill switch
(WFP)»](failure.md#kill-switch-wfp); список перечитывается не чаще раза в 5 с при промахе) считается
системным: Direct, в правила не идёт. Остальной TCP 443 этого PID решают правила: Dnscache может
делить svchost с другими службами. DNS-трафик остальных процессов (например, встроенный резолвер
Chrome) маршрутизируется как обычный, и в cache он попадает в любом случае.

## Обязательные исключения

Приоритет у них выше любых правил.

| Что | Как |
|---|---|
| Loopback, RFC1918, link-local, multicast, broadcast | В фильтре H1, в user space не попадает |
| IP сервера Hysteria (все порты, что покрывает port hopping) | В фильтре H1 исключается **весь IP**, а не порты. Список — все A/AAAA-записи хоста |
| Процесс Hysteria | `hysteria.exe`, чей родитель — HyRoute: его flow решаются как Direct («exclusion: hysteria»). Remote IP его сокетов в исключения фильтра не добавляются |
| Наш процесс | SOCKS5 к Hysteria идёт через loopback и уже исключён. Любой flow с PID HyRoute решается как Direct («exclusion: self»). Direct-upstream relay'я (SNIFF → Direct) исключается так же, по PID: событие `SOCKET_CONNECT` приходит раньше SYN. Идея с `selfPorts` через `bind` в `net.Dialer.Control` отброшена: на Windows Go сам делает `bind` перед `ConnectEx`, и повторный `bind` падает с WSAEINVAL |
| Служебный трафик relay | Пакеты с `tcp.SrcPort == RELAY_PORT` обрабатываются только NAT'ом (обратное отражение), правила к ним не применяются |
| DNS HyRoute и его Hysteria; имена серверов Hysteria, проверки Windows, хост своего прямого DNS-сервера, хосты, к которым HyRoute обращается сам (2 мин) | DNS-политики ([dns.md, «DNS-политики»](dns.md#dns-политики)) такие запросы не трогают: свой трафик по PID (`Core.own`), имена — по имени, кто бы ни спрашивал (служба DNS-клиента спрашивает за всех). **Резолв сервера.** Режим «pin IP» включён по умолчанию.
- Резолв идёт через системный резолвер (Go на Windows → `GetAddrInfoW` → служба Dnscache).
  DNS-трафик Dnscache — обязательное исключение, в туннель он не попадает никогда, поэтому курицы и
  яйца нет: резолв сервера работает и когда туннель недоступен.
- Резолвим при **каждом** запуске и перезапуске Hysteria. Порядок: резолв → обновление исключения в
  фильтре (синхронно) → запись YAML → запуск процесса. Первый пакет Hysteria уходит, когда
  исключение уже действует.
- Исключаются **все** полученные адреса (A и AAAA). Hysteria получает один из них: `server:
  <IP>:<ports>`, предпочтительно IPv4, а `tls.sni` равен домену, если SNI не задан явно. Если запуск
  с закреплённым адресом завершился, не подключившись (кроме занятого локального порта и ошибки
  конфигурации), следующий запуск закрепляет следующий адрес набора: сначала остальные IPv4, потом
  IPv6, затем снова по кругу. После успешного подключения выбор начинается с первого IPv4.
- Раз в 5 минут, пока Hysteria работает, хост резолвится заново. Если набор адресов изменился,
  фильтр получает объединение старого и нового наборов, а закреплённый IP остаётся в исключении, пока
  процесс им пользуется, даже если нового набора в нём нет: DNS-балансировка отдаёт разные части пула,
  и это не повод рвать все соединения. Сервер, который действительно пропал, Hysteria сообщает сама
  (Lost, затем перезапуск), а следующий запуск закрепляет адрес из нового набора. При перезапуске
  исключение сужается до нового набора. Без
  «Резолвить адрес в HyRoute» исключение за время жизни процесса только растёт (объединение всех
  адресов, увиденных при перерезолвах) и сужается до нового набора только при перезапуске Hysteria.

Фильтр обновляется без разрыва: открывается новый H1 на другом уровне (1000 ↔ 1001), старый получает
`WinDivertShutdown(RECV)`, дренирует очередь и закрывается. При замене на уровень ниже принимающего
инжект приостанавливается (`swapMu`) от открытия нового хэндла до переключения `e.send`, дальше
инжектит только новейший хэндл. NAT-состояние живёт в памяти движка, а не в хэндле, поэтому
соединения не рвутся.
