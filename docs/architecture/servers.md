# Серверы, подписки, группы, локальные прокси

В коде сервер Hysteria называется профилем (`profiles.json`, `Rule.Profile`, `tunnels`); «профиль
правил» — другое понятие, набор правил (`rulesets.json`, [rules.md, «Профили
правил»](rules.md#профили-правил)).

## Hysteria: профиль, конфиг, процесс

Поля профиля берутся только из официального конфига: `server` (host, ports: `443` или
`443,20000-50000`), `auth`, `tls.{sni, insecure, pinSHA256, ca}`, `obfs.type = salamander|gecko` +
`password` (для gecko `minPacketSize`/`maxPacketSize`), `transport.udp.{hopInterval |
minHopInterval+maxHopInterval}`, `bandwidth.{up, down}`, `congestion.{type, bbrProfile}`,
`quic.{initStreamReceiveWindow, maxStreamReceiveWindow, initConnReceiveWindow, maxConnReceiveWindow,
maxIdleTimeout, keepAlivePeriod, disablePathMTUDiscovery, disableChromeParrot}`, `fastOpen`,
`tls.ech` (продвинутое).

Сгенерированный YAML (golden-файлы в `internal/hysteria/testdata`):
```yaml
server: 203.0.113.10:443,20000-50000   # pin IP ([interception.md, «Обязательные исключения»](interception.md#обязательные-исключения)) или host как есть
auth: <secret>
tls: { sni: example.com, insecure: false, pinSHA256: "..." }
obfs: { type: salamander, salamander: { password: <secret> } }
transport: { udp: { hopInterval: 30s } }
bandwidth: { up: 50 mbps, down: 200 mbps }
socks5:
  listen: 127.0.0.1:<свободный порт>
  username: <random 16>      # чтобы чужие локальные процессы не пользовались туннелем
  password: <random 32>
  disableUDP: false
```
- Файл пишется в `%APPDATA%\HyRoute\run\hy-<n>.yaml` с защищённым DACL: SYSTEM и Administrators;
  текущий пользователь — только если HyRoute запущен без повышения (тогда и Hysteria работает с его
  правами). HyRoute держит файл открытым с разрешением только на чтение для других, пока Hysteria не
  сообщит «connected to server» или не завершится: программы пользователя без прав администратора не
  могут переписать, удалить или переименовать конфиг, пока его читает Hysteria с правами
  администратора (папку `run` от подмены защищает `store.Guard`). Затем файл закрывается и
  удаляется.
- Запуск: `hysteria.exe client -c <file>`, env `HYSTERIA_LOG_FORMAT=json`,
  `HYSTERIA_LOG_LEVEL=info`, `HYSTERIA_DISABLE_UPDATE_CHECK=1`. Процесс создаётся `CREATE_SUSPENDED
  | CREATE_NO_WINDOW`, добавляется в Job `KILL_ON_JOB_CLOSE`, затем потоки возобновляются (`os/exec`
  не отдаёт хэндл главного потока, поэтому через Toolhelp-снимок потоков).
- Порт SOCKS5 выдаётся `reservePort`: он закреплён за своим процессом до его выхода, поэтому
  несколько одновременно стартующих профилей не получают один и тот же порт. Hysteria сначала
  подключается к серверу и только потом открывает SOCKS5, а порт до этого момента может занять чужое
  исходящее соединение (особенно если динамический диапазон Windows начинается с низких портов).
  Поэтому: bind-ошибка — отдельный вид `ErrPortBusy` с перезапуском через 200 мс на новом порту;
  Connected выставляется только после того, как порт принимает TCP (ожидание до 15 с, иначе
  перезапуск); если соединение с SOCKS5 работающего профиля отклонено (connection refused) и порт
  три раза подряд не отвечает, процесс перезапускается.
- Статусы берутся из JSON-лога (stderr, ключи `level`/`time`/`msg`): `connected to server` (плюс
  открытый порт SOCKS5, см. выше) даёт Connected (с полем `udpEnabled`: если сервер запретил UDP,
  UDP-Tunnel отклоняется с предупреждением). Ошибки `authentication error` / `x509` / `certificate`
  / `CRYPTO_ERROR` / `timeout` превращаются в понятные сообщения («Неверный пароль», «Сертификат не
  прошёл проверку: используйте pinSHA256 или insecure», «Сервер не отвечает: проверьте порт или
  obfs-пароль»). `fatal` и выход процесса переводят в Error с backoff.
- URI: `hysteria2://` и `hy2://`, auth в userinfo с percent-decode (`user:pass` → `auth: user:pass`,
  как в Hysteria), мульти-порт, `obfs`, `obfs-password`, `sni`, `insecure=1|0`, `pinSHA256`, `ech`,
  `#name`. Authority разбирается вручную: `net/url` отвергает хосты вида `host:443,20000-50000`.
  Экспорт делается обратно тем же форматом, без bandwidth и режимов (так требует спецификация).
- Нестандартные ссылки из панелей (Xray, v2rayN, Throne) тоже принимаются:
  - `allowInsecure` → `insecure`;
  - `peer` → `sni`, если `sni` нет;
  - `mport` добавляется к портам;
  - `pcs` (pinnedPeerCertSha256 из Xray) → `pinSHA256`;
  - `fm` (Xray finalmask, JSON `{"udp":[{"type":"salamander","settings":{"password":…}}]}`) → obfs
    salamander;
  - `obfs-password` без `obfs` → **предполагается salamander**. Сама Hysteria такой пароль молча
    игнорирует, поэтому это допущение (на тестовом сервере оно подтвердилось), и оно попадает в
    предупреждения импорта.

  Косметические параметры других протоколов (`security`, `alpn`, `fp`, `type`) пропускаются молча,
  про неизвестные выводится предупреждение.
- `pinSHA256` задаёт проверку **только по пину**: в YAML добавляется `insecure: true`. Иначе
  Hysteria проверяет ещё и цепочку CA, и самоподписанный сертификат с правильным пином отвергается.
- Ссылки в тексте и в подписке разделяются по строкам: ссылка идёт до конца строки или до следующей
  `scheme://`. Поэтому имена с пробелами и emoji (`#🇳🇱 Нидерланды напрямую`) не обрезаются. Имя не
  служит идентификатором: правила ссылаются на постоянный `id`.
- Маскирование: единый `Redactor` знает текущие auth, obfs-password и SOCKS-креды (в сыром и
  URL-escaped виде) и заменяет их на `***` во всех логах, включая вывод Hysteria.

## Несколько серверов одновременно

Серверов работает несколько одновременно, и через каждый идут свои маршруты:

- **Маршрут = действие + сервер.** `Rule.Profile` — стабильный ID сервера или группы, пусто —
  основной сервер; запасные — `Rule.Fallback` и `defaultFallback`. `rules.Set.Evaluate` сравнивает
  маршрут целиком: `Tunnel → DE` и `Tunnel → NL` для одного IP с разными доменами дают
  `NeedsDomain`, а не молча DE.
- **Сервер несут** `rules.Result`, `nat.Entry` (NO-SNIFF знает его заранее), UDP-поток и запись
  «Соединений».
- **Туннель по ID.** `engine.Core` и `relay.Server` берут его через `Tunnels.Get(id)`: у каждого
  сервера свой SOCKS5. Неизвестный или удалённый сервер даёт `nil`, и соединение отклоняется
  (RST/drop) — никогда не уходит через другой сервер или напрямую.
- **UDP-сессия** ключуется по `(L:lp, сервер)`: один сокет может слать в DE и NL одновременно, это
  две разные UDP ASSOCIATE.
- **Процессы.** `hysteria.Supervisor` — один на сервер, их держит `tunnels.Manager`: у каждого свои
  статус, backoff, SOCKS-порт, счётчики и журнал. Redactor хранит секреты группами по серверу
  (`SetGroup`).
- **Исключение IP.** Manager собирает объединение IP всех запущенных серверов и временных проверок и
  отдаёт его движку; фильтр меняется горячей заменой
  ([interception.md](interception.md#обязательные-исключения)).
- **Статус** (`app.Status`): общий статус маршрутизации и список серверов — `connecting / connected
  / error`, сообщение, SOCKS-порт, рестарты, отклонено, байты.

WinDivert-хэндлы, reflect-NAT, relay, sniff, DNS-кэш и fail-open от числа серверов не зависят: поток
решает маршрут один раз, маршрут несёт сервер.


## Запуск серверов: только нужные

- «Подключить» означает «включить маршрутизацию». Manager запускает Hysteria **только** для
  профилей, на которые ссылаются включённые правила и маршрут по умолчанию (`rules.Set.Profiles()`).
- Правила сохраняются «на горячую»: Manager сверяет набор нужных профилей и запускает недостающие,
  останавливает ненужные. Соединения через остановленный профиль рвутся, новые идут по новым
  правилам.
- Правка профиля, который сейчас запущен, перезапускает только его Hysteria.
- **Основной сервер.** Правило `Tunnel` без явного профиля и `defaultAction: tunnel` без
  `defaultProfile` идут через него. Это не переключатель «одного соединения»: DE, NL и основной
  работают одновременно. Зачем он нужен:
  - старые настройки продолжают работать без миграции;
  - одним выбором в шапке можно сменить сервер у всех правил, которым конкретный сервер не важен.
- Падение одного профиля затрагивает только его маршруты: они получают RST/drop и попадают в счётчик
  «отклонено» этого профиля. Direct и другие профили не затронуты.
- Fallback (`DE → NL → отказ`): `Result.Fallback` несёт запасные профили, `Core.pick` в момент
  решения берёт первый профиль цепочки, который может нести соединение (`Available`, для UDP
  `UDPAvailable`), и дописывает к правилу « (fallback)». Если недоступны все, решение остаётся на
  основном профиле и соединение отклоняется, как без fallback: напрямую Tunnel не уходит никогда.
  Запасные профили запускаются вместе с основным (`Set.Profiles`), поэтому переключение мгновенное.
  Уже открытые соединения через упавший профиль рвутся, новые идут через запасной, а после
  восстановления основного снова через него. В тексте правил: `-> DE -> NL` или `-> DE, NL`; `->
  блок` в конце цепочки допустим и ничего не меняет. Запасной, совпадающий с сервером маршрута или
  повторяющий основной (в том числе после смены основного), интерфейс показывает зачёркнутым и
  удаляет из правила при сохранении настроек. Элемент цепочки (и сам сервер маршрута) может быть
  группой серверов ([«Группы серверов»](#группы-серверов)): `Core.pick` разрешает её в сервер группы
  в том же проходе по цепочке.

## Идентичность серверов и подписки

- У каждого профиля постоянный случайный `id`. Правила ссылаются только на него, никогда на позицию
  или имя.
- `source`: `manual` или `sub:<subID>`. Профили подписки хранятся в общем `profiles.json` и в
  правилах используются так же, как ручные.
- **Обновление подписки** проходит в три шага: скачать, разобрать, проверить. Только если всё
  прошло, данные подписки заменяются атомарно. Ошибка сети или разбора оставляет старый список и
  записывается в `lastError`.
- **Смена ссылки:** новая ссылка сначала проверяется (`PreviewSubscription`). `EditSubscription` с
  токеном предпросмотра сохраняет URL и применяет уже скачанное тело как обычное обновление (снимок,
  профили, статус), без второго скачивания. Непроверенную ссылку сохранить нельзя (в `SubInput` нет
  поля `url`).
- **По очереди:** обновление, откат, смена ссылки и первый импорт одной подписки выполняются по
  очереди (`lockSub`, берётся до `mu`). Повторное обновление (планировщик и кнопка) ждёт текущее и
  скачивает заново. Разные подписки обновляются параллельно. Удаление подписки не ждёт: обновление,
  которое идёт в этот момент, увидит, что подписки нет, и ничего не сохранит.
- **Сопоставление при обновлении.** Нужно, чтобы правила не «переехали» на чужой сервер.
  Сопоставление строго один к одному, в три прохода по убыванию уверенности:
  1. та же ссылка без имени, то есть все параметры подключения совпадают;
  2. тот же `host:ports`;
  3. то же имя.
  Совпавший профиль сохраняет `id` и обновляет поля из ссылки. Настройки, которых в ссылке нет
  (скорость, интервалы port hopping, congestion, QUIC, fast open, CA, «Резолвить адрес в HyRoute»),
  остаются пользовательскими: обновление их не сбрасывает и Hysteria из-за них не перезапускает.
  Редактор сервера из подписки предупреждает, что поля из ссылки (название, адрес, пароль, obfs,
  SNI, pinSHA256, insecure) при обновлении подписки заменяются. Новый получает новый `id`.
  Исчезнувший:
  - если на него ссылается правило или локальный прокси (или это основной профиль), остаётся с
    пометкой `missing`. При удалении подписки такие профили становятся ручными. Правило показывает
    «Профиль больше отсутствует в подписке» и предлагает выбрать замену. Трафик не подменяется молча
    другим сервером;
  - если не используется, удаляется;
  - пока `settings.json` или `proxies.json` не загружен, ссылки правил и прокси неизвестны: все
    пропавшие серверы остаются с пометкой, а удаление подписки делает все её серверы ручными.
- **Формат.** Список `hysteria2://` / `hy2://` (по строкам или через пробелы) или тот же список в
  base64 (std/url, с паддингом и без), распознаётся автоматически. Остальные схемы (`vless://`,
  `vmess://`, `ss://`, `trojan://`, `tuic://`, `hysteria://` v1 …) пропускаются и считаются. YAML
  Clash и JSON sing-box не разбираются: пользователь получает понятную ошибку.
- **Preview перед добавлением:** «Найдено 14 Hysteria-профилей, 23 записи других протоколов
  проигнорированы». Сохраняется ровно то, что было показано: повторного скачивания нет.
- **Снимки.** Последнее успешное содержимое и предыдущее хранятся зашифрованными (DPAPI) в
  `subs\<id>.cur` / `.prev`. «Откатить» заново применяет предыдущий снимок по тем же правилам
  сопоставления. Тот же набор серверов (те же параметры подключения, даже если панель поменяла имена
  — например, дописала остаток трафика — или их порядок) снимки не сдвигает: текущий снимок
  перезаписывается, а предыдущий остаётся, так что откат после повторных обновлений возвращает
  прежнюю версию. Сначала сохраняются профили, затем снимок. Откат переставляет снимки только после
  того, как профили сохранены, поэтому неудачный откат ничего не меняет. Любая ошибка обновления, в
  том числе ошибка сохранения, записывается в `lastError`, и следующая попытка идёт по обычному
  расписанию повторов.
- **Секретность URL.** URL хранится зашифрованным (DPAPI, как пароли). В логах и диагностике
  показывается только `https://host/…`. Запрос идёт напрямую (собственный трафик HyRoute не
  маршрутизируется), с `User-Agent: HyRoute/<версия>`; перенаправления панели выполняются (не больше
  10), но с https на http — никогда: такая подписка не обновляется, а ошибка говорит почему.
- **Интервалы:** вручную / при запуске / 6 ч / 12 ч / 24 ч. Планировщик в контроллере проверяет раз
  в минуту. Неудачное обновление «при запуске» (при входе в Windows сети часто ещё нет) повторяется
  раз в 15 мин до первого успеха.
- **Информация подписки.** Из ответа 200 читаются заголовки `subscription-userinfo` (upload,
  download, total, expire), `profile-title`, `profile-update-interval` и `support-url`
  (`panelHeaders`, `internal/app/subinfo.go`). Каждое значение ограничено по длине до разбора
  (userinfo 1 КБ, ссылка 2 КБ, заголовок до декодирования 4 КБ), все заголовки ответа — 64 КБ
  (`MaxResponseHeaderBytes` на `directTransport`). Числа — целые в `[0, 2^62]`, дробные
  отбрасываются; `expire` ≥ 1e11 считается миллисекундами, а срок после этого всё ещё ≥ 1e11 (после
  5138 года) или раньше 2000 года (так выглядит «бессрочное» значение в секундах вроде 253402300799)
  отбрасывается. В `subscriptions.json` пишется каноническая форма (`userInfo`, тот же синтаксис,
  что читает 1.0.0) и время получения `infoAt`; файл пользователь может менять, поэтому `userInfo`
  разбирается заново при каждом чтении. Название очищается от управляющих, форматирующих (bidi,
  нулевой ширины) и private-use символов. Уровни: трафик `low` при остатке < 10 % (проверка
  делением, без умножения значений заголовка), `out` — израсходован; срок `low` < 72 ч, `out` —
  истёк; `total` = 0 или ≥ 1 ПиБ — «без лимита». Предупреждения (`Status.subAlerts`) для всех
  подписок, независимо от автообновления: срок считается всегда (он живой), трафик — только если
  известно время цифр (`infoAt`, иначе `lastUpdate`), старше 48 ч — с датой «данные сервиса на …».
  Ключ `уровень|t<уровень трафика, если он учтён>|e<уровень срока>|total|expire` держит «Скрыть» в
  WebView (`hyroute.subAck`) до смены положения; забытые подтверждения чистятся только при
  `Status.subsOK` (список подписок загружен). Ответ 200 с неразбираемым телом (панель истёкшего
  аккаунта) сохраняет цифры вместе с ошибкой; откат оставляет цифры и датирует их прежним
  `lastUpdate`, если `infoAt` не было. Ссылка поддержки публична (одна на панель), хранится открыто
  (`supportUrl`), проверяется `safeLink` (только `http(s)` с хостом, без userinfo, управляющих и
  форматирующих символов) при каждом показе и открытии и открывается только по ID подписки через
  Explorer (`OpenSubscriptionSupport`), никогда повышенным процессом. На маршрутизацию информация не
  влияет: ничего не отключается и не переключается.

## Проверка сервера

- **«Проверить профиль».** Если профиль уже запущен, используется его Hysteria. Если нет, Manager
  запускает временную: её IP сервера добавляется в исключение, чтобы проверка не пошла в другой
  туннель. Исключения хранятся по экземпляру (уникальный ключ на каждый запуск Hysteria), а не по
  профилю, поэтому ещё не остановленная временная Hysteria не снимает исключение следующей проверки
  того же профиля. Проверяется:
  - TCP через SOCKS: HTTPS-запрос к `https://api.ipify.org`, результат — внешний IP и latency;
  - UDP: DNS-запрос к 1.1.1.1 через UDP ASSOCIATE, если сервер разрешает UDP;
  - на каждом шаге понятная ошибка.

## Группы серверов

Группа — именованный упорядоченный список серверов и стратегия выбора. Это цель маршрута, как
сервер: её ID стоит в тех же полях (`Rule.Profile`, `Rule.Fallback`, `DefaultProfile`,
`DefaultFallback`, `LocalProxy.Profile`, основная цель). Новых полей в `settings.json`,
`proxies.json` и `profiles.json` нет.

- **ID и файл.** Серверы и группы делят одно пространство ID: у сервера 12 hex, у группы `grp-` + 12
  hex (`groups.ValidID`, `IsGroupID`). Группы, настройки пробы и основная группа лежат в
  `groups.json` (формат 1, строгий разбор, до 1 МиБ, чтение через `readRegular`). Файл пишется,
  только когда пользователь пользуется группами: создаёт, меняет или удаляет группу, меняет пробу,
  выбирает или снимает основную группу, удаляет сервер, который есть в группе. Все записи идут через
  `saveGroupsLocked`: висящие ID серверов убираются из всех групп (`Prune`), весь файл проверяется
  правилами загрузки (пустая группа допустима), затем `installGroupsLocked` — то же, чем пользуется
  восстановление из копии. Пока `groups.json` или `profiles.json` не загружен, запись запрещена (с
  пустым списком серверов `Prune` вычистил бы всех участников).
- **Основная цель.** `mainTargetLocked()` — единственное место: `main` из `groups.json`, иначе
  активный сервер `profiles.json`. Основная группа живёт только в `groups.json`, поэтому после
  отката на v1.0.0 основным остаётся сервер. Если `groups.json` битый, основная группа берётся из
  снисходительного чтения (`MainOf`): её соединения отклоняются, а не уходят через другой сервер.
- **Где выбирается сервер.** Только в `Core.pick(res, udp, Hint)` (`engine/groups.go`), в момент
  решения о новом потоке. Разрешение в две фазы: сначала цепочка (цель, затем запасные)
  просматривается без изменений состояния (`Peek`/`PeekUDP`) — берётся первая здоровая цель, иначе
  первая «деградированная»; потом выбор фиксируется (`Choose`/`ChooseUDP`) только на этой цели.
  Поэтому деградированная группа раньше в цепочке не двигает свой круг и текущий сервер, когда поток
  ушёл дальше. Без групп в цепочке путь прежний, бит в бит. IPv6-поток, который всё равно отклонит
  блок IPv6, только просматривает. Устаревший путь фрагментов (`fragRoute`) `pick` не вызывает.
  `Hint` — программа, сайт и IP: сайт берётся из имени, увиденного у этого соединения (SNI/Host,
  CONNECT прокси), иначе из DNS-кэша, если все имена адреса — один сайт (`SiteOf`), иначе ключ — IP.
- **Стратегии.** «По порядку» (с возвратом на первый: член, здоровый без перерыва 30 с, забирает
  новые соединения), «Самый быстрый» (EWMA задержки, α = 0,3; переход, только если другой быстрее
  больше чем на порог, по умолчанию 50 мс), «По кругу» (один счётчик на TCP и UDP), «Случайно»,
  «Закреплять сайт» (rendezvous-хэш «программа + сайт»: при уходе сервера двигаются только его
  ключи). Здоровый член = `usable` (как у сервера) и без штрафа: серия неудачных соединений к разным
  адресам (опция «после N ошибок», штраф 60 с, затем ровно одно пробное соединение, `TrialTimeout`
  15 с) или две неудачные пробы подряд, когда через другой член группы проба с тех пор прошла. Если
  здоровых нет, используются просто работающие (деградация), после того как вся цепочка проверена на
  здоровые. `ChooseUDP` пробных соединений не берёт и текущий сервер не двигает. `Pick.Failover`
  (для статистики) — выбор деградированный или член, которого выбор взял бы при здоровье всех,
  недоступен.
- **Сигналы здоровья.** Только от рабочих конечных точек: `tunnels.Manager.OnHealth` (статус) и
  `OnDial` (каждый Dial и UDP ASSOCIATE, кроме отменённых и помеченных `tunnels.Quiet` — ими ходит
  «Проверить» сервера). Временные конечные точки проверок ничего не сообщают. Заглушка SOCKS5 тоже
  сообщает статус через хуки. `ResetSession` при подключении обнуляет всё, что могло штрафовать
  (серии, пробы, время работы, отклонения), и текущий сервер групп «по порядку» с возвратом.
- **Проба задержки.** `Prober` раз в 5 с берёт членов используемых групп, которые работают сейчас, и
  тех, чья проба устарела (интервал по умолчанию 60 с) или кто только что подключился, до 8
  одновременно. `GET` на адрес пробы (по умолчанию `http://cp.cloudflare.com/generate_204`) только
  через SOCKS5 члена, время до первого байта, 5 с на всё, чтение ограничено строкой статуса (1 КиБ),
  редиректов нет, TLS проверяется. Проба, прерванная отключением или бюджетом, не считается отказом.
  После пробы текущий сервер групп «по порядку» и «самый быстрый» пересчитывается (только он: без
  пробного соединения и шага круга). «Проверить» у группы работает и без подключения: рабочие члены
  проверяются на месте, остальные через временный Hysteria (до 4 сразу, всего 60 с, не больше одной
  проверки на группу; при подключении — только если в исключениях есть место для 4 адресов).
- **Что работает.** Две разные «используемости»: ссылки (правила, в том числе выключенные, маршрут
  по умолчанию, запасные, прокси, основная) защищают группу от удаления и от опустошения подпиской
  (`groupUsedLocked`, `groupPinsLocked`); запуск серверов, пробы и проверки в статусе следуют
  включённой маршрутизации (`usedGroups` из `routingLocked`). Сервер, который используется только
  через группы, не переводит статус в «сервер недоступен», пока у группы есть рабочий член; группа,
  у которой не работает никто, — переводит («Группа «X»: все серверы недоступны»).
- **Блокировки.** Состояние групп в контроллере под `c.mu`, `probeStop` под `lifeMu`.
  `groups.Runtime.mu` — самая внутренняя блокировка: колбэк `usable` (блокировка менеджера туннелей)
  вызывается до неё, журнал и `OnSwitch` — после. Определения меняются атомарно (`SetGroups`),
  решение читает их без блокировки.
- **Отказ — закрыто.** Группа без рабочих членов, пустая, удалённая, неизвестная или битый
  `groups.json`: цель остаётся ID группы, `Core.tunnel` отдаёт `groupMiss` (недоступен, считает
  отклонение группы), TCP получает RST, UDP отбрасывается, relay отклоняет. Напрямую поток не уходит
  ни в одной ветке. Пока `groups.json` битый, все серверы защищены: удалить нельзя, подписка
  оставляет пропавшие. После отката на v1.0.0 цели-группы выглядят как удалённый сервер и тоже
  отклоняются.

## Локальные прокси

- Локальные прокси (`internal/localproxy`): у каждого прокси лимит одновременных клиентских
  соединений (`DefaultMaxConns` = 1024, для прокси с доступом из LAN 256). Соединение сверх лимита
  закрывается сразу, ещё до авторизации; предупреждение в журнал не чаще раза в минуту. Обрыв
  туннеля или клиента передаётся другой стороне RST, а не FIN, для SOCKS5, CONNECT и plain HTTP, в
  том числе при Close (Disconnect, переподключение, правка прокси). Если клиент plain HTTP бросил
  ответ, туннель сбрасывается сразу, и остаток тела с сервера не дочитывается. Ошибка Accept не
  останавливает порт: повтор через 50 мс → 1 с, в журнал не чаще раза в минуту (то же у relay).
  `Expect: 100-continue` прокси подтверждает сам (100 Continue клиенту, Expect к серверу не
  передаётся). `Connection` разбирается как список токенов. Клиент HTTP/1.0 получает тело без
  chunked, конец тела отмечается закрытием соединения.
- SOCKS5 UDP ASSOCIATE локального прокси (`localproxy/udp.go`, подробно — ниже): не больше 128
  одновременных UDP-сессий на прокси (32 для LAN-прокси), простой — 10 минут. Правила брандмауэра
  `HyRoute local proxies (TCP)` и `(UDP)` (второе — только для LAN-прокси с включённым UDP, те же
  порты, подсети и профили сетей) ставятся до открытия портов, чтобы Windows не спрашивал
  разрешения; «Удалить правило брандмауэра» убирает все три. Правила этой версии помечены в описании
  (`hyroute-proxy-rule-2`). Сервер без UDP — REP 2 и заметка на карточке, группа без члена с UDP —
  REP 1.
- **Локальные прокси: SOCKS5 UDP ASSOCIATE** (`localproxy/udp.go`, socks-udp). Переключатель `udp` в
  `proxies.json` (`store.UDPMode`: `""` — по умолчанию, `on`, `off`; любое другое значение читается
  как `""`, файл не ломается): по умолчанию включён для прокси на 127.0.0.1 и выключен для
  LAN-прокси; у прокси на 127.0.0.1 значение, равное умолчанию, не пишется (`NormalizeUDP`), у
  LAN-прокси `SaveProxy` пишет его всегда, `off` тоже (см. `KeepV12ProxyUDP` ниже). Прокси на
  127.0.0.1 даёт каждой ассоциации свой сокет `127.0.0.1:<порт от Windows>` (как SOCKS5 самой
  Hysteria), LAN-прокси — один общий сокет на том же номере порта, что и TCP (`SharedUDP`), чтобы
  правило брандмауэра оставалось точным. Все UDP-сокеты с `SO_EXCLUSIVEADDRUSE`. Каждая ассоциация
  клиента — своя ассоциация через туннель (сервер прокси или один член группы на всю её жизнь,
  `ChooseUDP`). Датаграмма сначала целиком проверяется (заголовок, FRAG, `socks5.MaxUDPPayload` —
  быстрый путь `UDPPayloadAlways` только для IP-назначений), и только потом может закрепить
  ассоциацию: мусор и фрагменты ничего не занимают. Принимается только IP управляющего соединения.
  Закрепление: порт из запроса — предпочтение (если с него ничего не пришло, а IP шлёт с другого
  порта и ассоциация у него одна, она перезакрепляется), иначе первая датаграмма, старейшая
  ожидающая ассоциация (FIFO). На общем сокете ассоциации одного IP, ждавшие одновременно,
  помечаются неоднозначными; когда одна из них закрывается, закрепления остальных по первой
  датаграмме возвращаются в ожидание, так что перепутанная пара не переживает закрывшуюся
  ассоциацию. Тот же адрес, названный новым запросом того же клиента, забирает закрепление у старой
  ассоциации (её управляющее соединение закрывается). **Проверка программы**: ассоциации с этого
  компьютера (прокси на 127.0.0.1 с паролем, LAN-прокси, к которому подключились с 127.0.0.1 или с
  адреса этого ПК) закрепляются только за UDP-сокетом того же процесса, что владеет управляющим
  TCP-соединением (`attrib.LookupTCPOwner`/`OwnerOf` при запросе; `attrib.LookupUDPOwnerStrict` по
  источнику: все строки таблицы с этим портом — точный адрес и wildcard, в том числе `::`
  двухстековых сокетов — должны принадлежать одному PID, иначе отказ). Названный порт такой
  ассоциации — предварительный, пока его владелец не проверен; чужой владелец возвращает ассоциацию
  в ожидание. На общем сокете закрепление, FIFO, неоднозначность и вытеснение действуют только
  внутри процесса. Кэш ответов (64 источника, 5 с, неудачное чтение таблицы — 250 мс) может только
  отбросить датаграмму, никогда не пропустить; не больше 50 чтений таблицы в секунду на сокет.
  Жизнь: пока открыто управляющее соединение (RFC 1928); конец ассоциации в туннеле (перезапуск
  Hysteria, смена сервера) закрывает управляющее соединение; 10 минут без датаграмм в обе стороны —
  ассоциация закрывается. Лимит одновременных ассоциаций резервируется до открытия туннеля: 128 на
  прокси, 32 на LAN-прокси. Общий UDP-порт LAN-прокси, занятый другой программой, не мешает TCP:
  `UDPError` на карточке, ASSOCIATE получает REP 1, повтор привязки раз в 30 с. Если правило
  брандмауэра не установилось (`ProxyFirewall` вернул ошибку), UDP у LAN-прокси не включается вовсе
  — сокет на всех интерфейсах без правила вызвал бы запрос Windows; на карточке `udpError`, прокси
  переоткрывается с UDP, когда правило установится. Отбросы считаются по видам, в журнал — не чаще
  раза в минуту на вид, без адресов. `Active`/`Total` в карточке и диагностике — только TCP (все
  управляющие соединения UDP ASSOCIATE, отклонённые тоже, вычитаются: `UDPCtlActive`/`UDPCtlTotal`).
  v1.2.0 обслуживал UDP у всех прокси без поля `udp`: если при запуске (`KeepV12ProxyUDP` из
  `cmd/hyroute/main_windows.go` сразу после `Load`, до окна и без подключения) находится его правило «HyRoute
  local proxies (UDP)» (без метки в описании, `fwrule.LegacyProxyUDP`), все LAN-прокси без `udp`,
  включённые и выключенные, получают `on`. Это происходит один раз: первое подключение переписывает
  правило, а до него файл уже помечен как файл этой версии — записанным `on` или явным значением,
  которое `SaveProxy` пишет у каждого LAN-прокси (иначе выключенный пользователем или добавленный до
  подключения LAN-прокси снова получал бы `on` при следующем запуске). Для IPv4-источника
  недоступная таблица IPv6 (стек IPv6 не установлен) считается пустой.
