# Маршрутизация: решение, NAT, relay, UDP

## Где принимается решение

```
новый flow (TCP SYN без NAT-записи / первый UDP-пакет 5-tuple)
 │
 ├─ исключение? ───────────────────────────────► pass (Direct, «system»)
 ├─ атрибуция (pending ≤100 мс)
 ├─ EvaluateSites(rules, proc, proto, dstIP, dstPort, dnsSites(dstIP))
 │     └─ результат: Final(action, rule, domainSrc)  |  NeedsDomain
 │
 ├─ Final:
 │    Direct ─► reinject как есть. Relay не участвует, в NAT только запись для UI
 │    Block  ─► RST (TCP), чтобы приложение быстро упало; UDP молча отбрасывается
 │              (ICMP unreachable не шлём: Windows отдаёт его как WSAECONNRESET всему
 │              UDP-сокету, и блок одного адреса ломал бы программе остальные направления)
 │    Tunnel ─► туннель недоступен (Hysteria не Connected или relay не работает)
 │                 → RST (TCP) / drop (UDP), счётчик «отклонено» (общий и профиля), напрямую НЕ идёт;
 │                   UDP-поток виден в «Соединениях» как «dropped: tunnel unavailable»,
 │                   а когда туннель поднимется, его исход станет «tunneled»
 │              IPv6 и «блокировать IPv6 в туннеле» → RST (приложение уйдёт на v4)
 │              TCP → relay в режиме NO-SNIFF (SOCKS5 CONNECT на IP сразу)
 │              UDP → UDP-сессия SOCKS5 ASSOCIATE (на пакетах, без listener'а)
 │                    сервер запретил UDP (udpEnabled=false) → drop
 │
 └─ NeedsDomain:
      TCP → IPv6, «блокировать IPv6 в туннеле» и хотя бы при одном домене соединение
            ушло бы в туннель → RST сразу, на SYN, без sniff: после рукопожатия RST уже
            не переводит приложение на IPv4 («IPv6 blocked for tunnel (domain unknown)»);
            если DNS-кэш знает для адреса только сайты, которые идут мимо туннеля, или у машины
            нет IPv4-маршрута в интернет (IPv6-only сеть, NAT64 без CLAT; `GetBestInterfaceEx`,
            не чаще раза в 5 с), SYN не сбрасывается
            иначе relay в режиме SNIFF ([«NAT и relay»](#nat-и-relay)); relay не работает → решение по DNS cache/default,
            и если оно Tunnel, то RST
      UDP → dst port 443 и «блокировать QUIC» → drop (браузер уйдёт на TCP, там будет SNI)
            иначе → решение без домена (доменные правила считаются несовпавшими)
```

**Evaluate с трёхзначной логикой домена.** Правила обходятся по порядку, первое совпадение
выигрывает. Приложение и протокол известны точно. Условие по домену даёт `Yes/No/Unknown`:
- в DNS cache для IP ровно один набор имён, и **все** имена дают одинаковый итог → `Final`
  (domainSrc = DNS). Исключение — настройка «Точное определение домена для веба» (`exactWebDomains`,
  по умолчанию включена): для TCP на 80/443/8080/8443 и для QUIC (UDP/443 при включённой блокировке
  QUIC) DNS cache на уровне пакетов не используется;
- имена дают разные итоги (CDN) или IP в cache нет → считаются обе ветви доменного условия. Если все
  ветви сходятся к одному действию, получаем `Final`, иначе `NeedsDomain`.

Отсюда гарантия: в relay попадают только соединения, итог которых зависит от ещё неизвестного
домена, и Tunnel. Tunnel в relay неизбежен, потому что SOCKS5 требует терминировать TCP. Direct и
Block не трогают relay никогда, и падение relay их не задевает.

**Смена правил.** Скомпилированный набор правил подменяется атомарно (`atomic.Pointer`). Решение
фиксируется в flow-записи при первом пакете. Соединения со своей записью после смены правил остаются
на прежнем маршруте, а новые получают новые правила. Hysteria при этом не перезапускается.
Исключения: UDP-поток, профиль которого больше не может его нести (остановлен или недоступен),
заново решается по текущим правилам (включая fallback), не чаще раза в секунду; чистый SYN на
4-tuple закрытого reflect-соединения получает новое решение.

Не-SYN пакет TCP-соединения, о котором у движка нет состояния (открыто до старта, в том числе через
туннель прежнего движка до крэша или отказа), решается по правилам как новое. Direct-поток, чья
запись в `tcp` истекла (через минуту после FIN или RST приложения, после 2 ч простоя), сюда не
попадает: `Maintain` переносит его ключ в `untracked` с прежним решением, так что хвост потока или
долго молчавшая SSH-сессия не решаются заново без домена или владельца. Владелец берётся из
SOCKET/FLOW-событий или из снимка таблицы TCP IP Helper ([interception.md, «Атрибуция
процесса»](interception.md#атрибуция-процесса)): `GetExtendedTcpTable` для обеих семей адресов, не
чаще раза в секунду, один снимок на все такие соединения. Соединение, которого нет в снимке (SYN
ушёл до старта, а в таблице оно появилось после чтения), ищется в новом снимке, если текущему больше
100 мс; только потом владелец считается неизвестным. Сначала обязательные исключения (HyRoute, его
hysteria, системный DNS). Домен берётся только из DNS cache: посреди потока снифать нечего, а при
«Точном определении домена для веба» веб-порты решаются без домена. DNS cache каждой сессии
начинается пустым. Если итог зависит от домена, решение принимается без него. С
`Options.ResetUnknownDomain` Direct без домена заменяется сбросом (правило «… (domain unknown,
reset)»): контроллер ставит опцию при автоматическом переподключении после отказа движка, при
переподключении пользователя после такого отказа (пока не было «Отключить») и при подключении поверх
блокировки kill switch (после крэша, обновления, `Reconnect`), когда соединение могло идти через
туннель и сброс прежнего движка мог не дойти. Серверная сторона входящего соединения (исходящий
SYN-ACK или сокет LISTEN на этом порту, на том же адресе или wildcard любой семьи, принадлежащий
владельцу соединения) не маршрутизируется и проходит. Слушатель другого процесса не в счёт: `[::]` с
IPV6_V6ONLY (по умолчанию в Windows) не занимает IPv4-порт, и клиент может получить его как
эфемерный. Direct проходит как есть. Tunnel и Block: приложению инжектится RST от имени удалённой
стороны (seq = ACK пакета), пакет дропается, дальнейшие сегменты получают RST без нового решения
(`gone`), собственный RST приложения глушится. Решения запоминаются по 4-tuple: Direct в `untracked`
(2 ч с последнего пакета, до 16384, при переполнении вытесняется произвольная запись), Tunnel/Block
в `gone` (2 ч, до 16384). FLOW_DELETED и новый SYN на том же 4-tuple их снимают. Входящие пакеты
неизвестных соединений не трогаются. Поэтому при подключении уже открытые соединения, которые
правила отправляют в туннель или блокируют, один раз сбрасываются и открываются заново через движок,
а Direct по правилам для программ и адресов продолжают работать. Direct по доменному правилу при
туннеле по умолчанию решается без домена и тоже один раз сбрасывается. В журнал пишутся первые 20
сбросов сессии, дальше каждый сотый (поле `count` — счётчик `UntrackedReset`).

## NAT и relay

### TCP reflect
```
Приложение:  L:lp → R:rp   (outbound, пойман H1)
  переписано: R:lp → L:RELAY  и инжектится как INBOUND на том же IfIdx
Relay accept видит peer = R:lp → по NAT[(R, lp)] получает оригинал {L:lp → R:rp, pid, решение}
Relay отвечает: L:RELAY → R:lp  (outbound, пойман H1 по tcp.SrcPort == RELAY)
  переписано: R:rp → L:lp  и инжектится как INBOUND
```
- NAT хранит два индекса: `app flow → entry` для прямого направления и `(R, lp) → entry` для accept
  и обратного направления. Запись закрывается по RST, по FIN в обе стороны, по закрытию
  relay-соединения и по FLOW_DELETED, и удаляется после грейса 30 с (хвостовые ACK/FIN). Записи без
  пакетов дольше 2 ч удаляются как потерянные.
- **Коллизия ключа** `(R, lp)`: одинаковые R и lp при разных rp. Windows умеет делить локальный порт
  между разными удалёнными endpoint'ами. Такой второй flow в relay не отражается и решается на
  уровне пакетов: NeedsDomain → DNS/default, Tunnel → RST (не Direct). Случай крайне редкий, пишется
  в лог.
- Checksum пересчитывается всегда (свой код в `internal/packet`), в адресе выставляются флаги
  «checksum valid», чтобы драйвер не считал их offload'ом.
- Relay слушает на `0.0.0.0:RELAY` и `[::]:RELAY` (IPV6_V6ONLY). Порт случайный из 49152–65535,
  свободный на обоих семействах. Внешние подключения отсекаются дважды: фильтр H1 дропает inbound на
  RELAY, который не был инжектнут нами (свои инжекты тот же хэндл не видит), а при accept
  проверяется наличие NAT-записи (нет записи → RST).
- **Windows Firewall:** инжектнутый inbound SYN проходит ALE_AUTH_RECV_ACCEPT, и без правила
  брандмауэр покажет запрос или заблокирует. Правило:
  - имя `HyRoute relay (TCP)`, входящее, разрешить, программа = наш exe, TCP, локальные порты
    49152–65535, все профили;
  - проверяется при **каждом** Connect: `netsh advfirewall firewall show rule name=…`. Нет правила —
    `add rule`. Есть — `set rule … new <параметры>`, что чинит правило, если exe переехал или
    пользователь его выключил или отредактировал. Вывод `netsh` локализован, поэтому смотрим только
    на коды возврата;
  - удаляется деинсталлятором и кнопкой «Удалить правило брандмауэра» в настройках;
  - если служба брандмауэра отключена, `netsh` вернёт ошибку. Это предупреждение, а не отказ: без
    брандмауэра правило не нужно.

### Relay: режимы
- **NO-SNIFF** (Tunnel решён по пакетам): если туннель недоступен → RST. Иначе `SOCKS5 CONNECT
  <IP>:rp`, затем двунаправленный copy с half-close. Ошибка CONNECT → RST. Ошибка (не EOF) в любом
  направлении сбрасывает обе стороны RST. Сторона приложения закрывается (FIN) только после того,
  как приложение подтвердило все отправленные ему байты и открыло окно (`SIO_TCP_INFO`). Пока этого
  нет, соединение остаётся в relay, и Abort (Disconnect, переподключение, отказ движка) сбрасывает
  его RST: FIN, поставленный через shutdown, Windows отправит и после `SO_LINGER 0`, уже к реальному
  R:lp. Приложение, которое остановило чтение (пейджер, пауза загрузки), ждём, пока соединение живо,
  как и простаивающее: после паузы оно получит хвост и конец потока. Ожидание прекращается, если
  приложение закрыло или сбросило сокет. Через 10 с без изменений оно прекращается, только когда
  счётчики несогласованы (окно открыто, в полёте ничего нет, а байты не подтверждены): тогда в
  журнал пишется предупреждение и ставится обычный FIN.
- **SNIFF**: соединение принимается, upstream не открыт. Первые данные читаются с дедлайном
  `sniffTimeout` (по умолчанию 800 мс, настраивается):
  - TLS: сборка записей handshake (ClientHello часто больше MSS, в Chrome с Kyber около 1.8 КБ) до
    полного ClientHello или 16 КБ, затем извлечение SNI (ext 0). SNI берётся и при расширении ECH
    (0xfe0d): Chrome и Firefox шлют GREASE ECH каждому сайту без ECH-конфига, и внешний SNI — это
    сам сайт. Исключение — известное публичное имя ECH (cloudflare-ech.com и `public_name` из
    ECH-конфигов HTTPS/SVCB-ответов, увиденных в DNS, не дольше 1 ч), если кэш DNS не держит это же
    имя как сайт для этого IP. Тогда сайт скрыт: решают имена из кэша DNS для этого IP, а если они
    не дают однозначного маршрута, домен неизвестен (правила по IP, приложению или «Всё остальное»).
    Правило на само публичное имя не срабатывает, туннель подключается по IP. Если SNI нет, имя
    неизвестно;
  - HTTP: строка запроса и `Host:` до `\r\n\r\n`, максимум 8 КБ;
  - по имени (источник SNI/Host) вызывается `Evaluate(domain=exact)`. Если имени нет, решение по DNS
    cache (если имена сходятся), иначе «без домена»: доменные правила считаются несовпавшими, и
    срабатывает первое подходящее правило без домена или default;
  - Tunnel → SOCKS5 CONNECT (туннель недоступен → RST). `ATYP=DOMAIN` только если имя пришло из
    SNI/Host и включён «Prefer remote DNS», иначе исходный IP. Запросы к forward-прокси (CONNECT или
    absolute-form) идут на IP прокси: Host там только выбирает маршрут. Direct → dial `R:rp` с
    исходного IP приложения (bind на `Flow.Src`, порт 0); адреса больше нет — RST. Block → RST
    (`SetLinger(0)`);
  - буфер пишется в upstream без изменений, дальше идёт splice.
  - Для server-first протоколов (SSH 22, SMTP 25/587, FTP 21, POP/IMAP 110/143, MySQL 3306…) по
    списку портов ожидание сокращается до 150 мс: там клиент молчит до баннера.

### UDP
- Сессия ключуется по `(L, lp)` (сокет приложения). В ней одна ассоциация SOCKS5 UDP ASSOCIATE.
  Hysteria привязывает ассоциацию к первому отправителю, а разные назначения мультиплексирует.
  Решение принимается по каждому 5-tuple: Tunnel-назначения идут в ассоциацию, остальные по своему
  решению.
- Ответ от Hysteria приходит с адресом `from`. Из него собирается пакет IPv4/IPv6+UDP `from → L:lp`
  и инжектится inbound на IfIdx исходного пакета.
- Таймаут простоя 60 с (DNS 10 с), затем ассоциация закрывается.
- Предел размера. Hysteria несёт датаграмму, только если она помещается в два буфера по 4096 байт:
  буфер SOCKS5 UDP (`app/internal/socks5` `udpBufferSize`, с заголовком SOCKS5) и сообщение QUIC
  (`core/internal/protocol` `MaxUDPSize`: 8 байт + varint + «host:port» + данные) — на клиенте и на
  сервере. Больше второго — молча теряется внутри Hysteria. Больше первого — хуже: `ReadFromUDP` в
  `udpServer` падает (WSAEMSGSIZE), и Hysteria закрывает всю ассоциацию сокета. Поэтому предел
  жёсткий: `socks5.MaxUDPPayload` считает его по тем же байтам адреса, что уходят в Hysteria
  (IPv4-mapped разворачивается, зона отбрасывается), и никогда не завышает: 4040–4078 байт (IPv4 не
  меньше 4066). Больше — отбрасывается в `udpSend` (`UDPTooBig`, у потока `tooBig`; если через поток
  не прошло ничего, «Соединения» показывают исход `dropped: larger than Hysteria carries`). Это не
  ошибка сервера: отказы профиля не считаются. Настройкой не меняется, другие режимы клиента
  (`udpForwarding`, `tun`) упираются в тот же буфер. Любой, кто шлёт SOCKS5 UDP в Hysteria, обязан
  проверять этот предел.
- Ответы собираются в один пакет и инжектятся inbound, даже если он больше MTU (так было и в 1.0.0:
  ответы до ~4,1 КБ): так WinDivert сам реинжектит собранные входящие пакеты (inbound-классификатор
  пропускает фрагменты и ловит собранный пакет), путь приёма MTU не проверяет. Поэтому входящие
  ответы на фрагменты не разбиваются: `packet.FragmentIP` написан и покрыт тестами, но не
  вызывается. Если проверка `tools/udpprobe` покажет, что Windows такие пакеты не принимает, его
  включают в `udpSession.read`.

### IP-фрагменты и нераспознанные пакеты

- Фильтр H1 ловит `(tcp or udp or fragment)`: фрагменты без транспортного заголовка не подходят ни
  под `tcp`, ни под `udp`, и раньше уходили мимо движка напрямую (проверено вычислителем фильтров
  WinDivert 2.2.2, `tools/wdfilter`). Фрагменты других протоколов (ICMP, ESP, GRE, AH) проходят без
  изменений.
- UDP-фрагменты IPv4 (с опциями тоже) и IPv6 с заголовком фрагмента сразу после основного собираются
  (`packet.Assembly`, ключ — адреса, протокол, ID). Фрагмент со смещением 0 всегда начинает новую
  датаграмму и заменяет прежнее решение по ключу (ID IPv4 16-битный и повторяется). Он смотрит на
  существующий поток: Direct — фрагменты проходят как есть (байты считаются по длине из
  UDP-заголовка, поток не истекает), решение живёт 2 с; Block — отбрасываются; Tunnel — датаграмма
  собирается, а если по длине из UDP-заголовка она больше предела Hysteria и туннель потока
  доступен, отбрасывается сразу (туннель недоступен — собирается и проходит `udpOut`, как целая:
  перевыбор сервера, затем проверки `udpSend`). Нового потока нет — датаграмма собирается целиком и
  решается обычным путём, как несфрагментированная (владелец, ожидание SOCKET-события, правила);
  если итог Direct, уходят исходные фрагменты с исходными адресами, без изменений (`Packet.Orig`,
  `injectDirect`; в очереди ожидания владельца — тоже, с лимитом 8 МБ). Фрагменты до первого ждут
  его до 5 с, после чего датаграмма собирается целиком и только потом маршрутизируется. Неполные
  через 5 с, перекрывающиеся, с длиной UDP не по размеру и ошибочные датаграммы отбрасываются
  целиком (`FragIncomplete`); память ограничена: 256 собираемых датаграмм, 4 МБ, 128 фрагментов на
  датаграмму; решения (до 16384) вытесняются от старых к новым, новые фрагменты из-за них не
  отбрасываются. Состояние меняется в одной функции под `Core.mu` с `defer`-разблокировкой: паника в
  сборке отбрасывает датаграмму, но не блокирует движок; счётчики занятой памяти меняются только
  после успешного шага и пересчитываются при каждой очистке. Ни один фрагмент Tunnel- или
  Block-датаграммы не уходит напрямую.
- DNS-запросы (UDP на порт 53) никогда не идут по быстрому пути: датаграмма собирается и проходит
  `udpOut` целиком, поэтому решение видит весь запрос; собранный запрос, ушедший напрямую,
  записывается в кэш DNS (иначе ответ отбросился бы как ответ без запроса). Без DNS-политики
  фрагменты запросов к частным адресам (домашний роутер) не перехватываются, как и в 1.0.0.
- TCP-фрагменты и фрагменты IPv6 с заголовками расширения перед заголовком фрагмента решаются по
  первому фрагменту, как раньше (существующий поток, иначе правила по владельцу; нет SOCKET-события
  — IP Helper; неизвестный домен — как у целой UDP-датаграммы): Direct проходит, Tunnel и Block
  отбрасываются (`FragLegacy`). Решение хранится 2 с. Первый фрагмент без портов (заголовок
  расширения после заголовка фрагмента) отбрасывается вместе с остальными.
- Исходящий TCP/UDP, который не разбирается парсером, отбрасывается (`Malformed`), а не отправляется
  без маршрутизации. Паника при обработке одного пакета или DNS-ответа отбрасывает этот пакет
  (`Panics`) и не снимает фильтры.
