# Отказоустойчивость и kill switch

## Два сценария отказа

Два разных сценария, и поведение в них разное:
- **Приложение живо, туннель недоступен** (Hysteria ещё не подключилась, упала, переподключается,
  relay не работает): Tunnel-трафик **отклоняется** (RST/drop). Отправлять его напрямую — худший
  вариант для обхода блокировок: будет утечка, а соединение, скорее всего, всё равно не пройдёт.
  Direct и Block работают как обычно, так что интернет в целом не ломается. Это мягкий kill switch,
  отдельный WFP для него не нужен.
- **Приложения нет** (выход, крэш, зависание, убито watchdog'ом): фильтры снимаются, весь трафик
  идёт напрямую (**fail-open**). С включённым kill switch ([«Kill switch (WFP)»](#kill-switch-wfp))
  после сбоя интернет закрывается.
- **DNS-политики** ([dns.md, «DNS-политики»](dns.md#dns-политики)): имя сайта через VPN при
  недоступном туннеле или неработающем DNS-сервере для VPN получает SERVFAIL и напрямую не
  спрашивается никогда (исключение — пауза портала, которую включает пользователь, только для
  недоступного туннеля). Сбой прямого DoH/DoT (в том числе его ответ SERVFAIL, REFUSED и другие коды
  ошибки, кроме NXDOMAIN; через VPN такой ответ даёт SERVFAIL этому запросу; в кэш он не попадает и
  к отказам сервера, после трёх подряд помечающим его неработающим, не засчитывается — SERVFAIL
  обычно касается одного имени, а Windows спрашивает A, AAAA и HTTPS одновременно), его NXDOMAIN или
  NODATA для A — запрос уходит DNS-серверу сети, как без настройки. При крэше и отказе движка
  фильтры снимаются, DNS идёт как без HyRoute; ответы через VPN Windows помнит не дольше 300 с,
  отказы — не дольше 60 с, а следующий запуск с включённой политикой чистит кэш.

## Kill switch (WFP)

Выключен по умолчанию (`settings.json`: `"killSwitch": true`). Пакет `internal/killswitch`, WFP
через `github.com/tailscale/wf`. Все объекты в своём подслое (вес 0xFFFF) с фиксированными GUID,
поэтому следующий запуск находит и снимает их без перечисления чужих фильтров. Слои:
`ALE_AUTH_CONNECT_V4/V6` и `ALE_AUTH_RECV_ACCEPT_V4/V6`.

| Фильтр | Вес | Сессия | Смысл |
|---|---|---|---|
| block | 1 | обычная (не dynamic, без PERSISTENT) | всё закрыто; живёт после смерти процесса, до `Release` или перезапуска BFE (перезагрузки) |
| исключения | 10 | обычная | loopback; LAN (10/8, 172.16/12, 192.168/16, 169.254/16, 224/4, 255.255.255.255, fe80::/10, fc00::/7, ff00::/8); DHCP — только `svchost.exe` (AppID), UDP с порта клиента на порт сервера (68→67, 546→547); DNS — только `svchost.exe` и только к DNS-серверам адаптеров своего семейства (`internal/sysdns`, список обновляется при каждом `Arm` и `RefreshApps`): UDP и TCP на порт 53, TCP на 443 и 853 (UDP на 443/853 — нет), так что BITS/WebDAV из svchost не выходят через порт 53 к другим хостам, а входящие с порта 53 не проходят; 443 и 853 нужны, чтобы при DoH/DoT-only Windows мог резолвить сервер Hysteria. Если DNS-серверы неизвестны (ни один адаптер ещё не поднят) — svchost.exe получает UDP и TCP на порт 53 любого хоста, но только исходящие (на слоях RECV_ACCEPT правила нет), DHCP остаётся узким. Если неизвестен AppID svchost — как раньше: удалённые порты 53, 67, 68, 546, 547 для всех программ; блок старой версии с портами для всех заменяется; AppID `HyRoute.exe` и `hysteria.exe` (выбранное, встроенное и предыдущее ядро; после установки или отката ядра список обновляется сразу, без нового `Arm`) |
| порт relay | 15 | обычная | block: `HyRoute.exe` (`Switch.Self`) с локального порта relay к не-loopback адресам. Выше исключения для HyRoute, ниже pass. Порт — текущей сессии, передаётся в `Arm(relayPort)`. После сбоя или крэша FIN, повторы и keepalive сокетов relay не уходят к реальным R:lp |
| pass | 20 | dynamic | разрешить всё: пока движок работает, маршрутизирует он |

Жизненный цикл (`app/killswitch.go`):
- движок поднялся → `Arm`: pass, затем block и исключения (идемпотентно, список программ
  обновляется);
- движок упал (panic, ошибка `Recv`, watchdog) → `Engine.fail` сначала инжектит RST в каждое
  отражённое соединение приложения, как `Engine.Stop`, пока pass ещё действует (блок мог бы
  отбросить входящие RST), затем вызывает `OnFail` (сбросить relay, закрыть pass) и только потом
  снимает хэндлы, так что между fail-open и блоком нет окна. Сброс ждёт не дольше 0,5 с: зависший
  packet loop может держать блокировку NAT или `swapMu`, и тогда фильтры снимаются без сброса, с
  записью в журнал; все шаги (`resetReflected` → `OnFail` → `closeMains`) делает только первый вызов
  `fail`, одновременный второй ничего не делает, так что окна между fail-open и блоком нет. Закрытый
  `divert.Handle` больше никогда не передаёт своё значение в WinDivert: зависший loop, проснувшись
  позже, не прочитает хэндл нового движка;
- через 5 с контроллер сам делает `Reconnect` (не больше 3 раз за 10 минут; попытка, которая не
  запустилась, тоже считается, и следующая планируется так же): pass уже закрыт, block держится всё
  время переподключения, новый `Arm` снова ставит pass. Когда попытки кончились, `OnGiveUp` (в
  отдельной горутине) показывает окно;
- крэш или kill процесса → Windows закрывает dynamic-сессию, pass исчезает, block остаётся;
- `Disconnect`, выключение настройки → `Release`;
- выход из приложения (`Shutdown`) block не снимает: Windows закрывает окно одинаково и по крестику,
  и по «Снять задачу» в диспетчере задач (WM_CLOSE), отличить их нельзя;
- завершение сеанса Windows (выключение, перезагрузка, выход; трей получает `WM_ENDSESSION`) →
  `Release`: при «Завершении работы» с быстрым запуском состояние WFP переживает выключение, и после
  включения интернета не было бы. Работает только у запущенного HyRoute, у которого systray создал
  своё окно (без него `WM_ENDSESSION` не приходит); block, оставшийся после закрытого HyRoute, при
  быстром запуске переживает выключение, его показывает проверка при входе (ниже). `WM_ENDSESSION`
  приходит и при отменённом завершении: `EndSession` до `SessionResumed` запрещает `Arm`, а трей
  через 30 с, если процесс жив и `SM_SHUTTINGDOWN` снят, вызывает `SessionResumed` и kill switch
  снова следует настройке. Если маршрутизация при этом не работает (движок отказал, сессии нет, блок
  остался от сбоя), `SessionResumed` снова ставит снятый блок без pass, если пользователь тем
  временем не нажал «Отключить» или «Открыть интернет» и не выключил настройку. systray сообщает
  `WM_ENDSESSION` один раз за запуск, поэтому после отменённого завершения трей сразу
  перезапускается (`renewTray`), до того как `SessionResumed` вернёт блокировку;
- GUID фильтров общие для всех HyRoute на машине: владеет ими копия, которая их поставила (`Arm`)
  или нашла блок при запуске (`Engaged`), пока фильтры стоят; `Release` отдаёт владение. Просто
  запущенная копия с выключенным kill switch владельцем не становится. Копия в другом сеансе Windows
  фильтры владельца не трогает. Владельца отмечает Global-мьютекс; объект с этим именем, чей
  владелец не Administrators/SYSTEM (его создала обычная программа), или объект другого типа не
  считается чужим HyRoute и не мешает kill switch.
- `Reconnect` и выход → сначала `Session.ResetConnections` (relay и отражённые соединения
  сбрасываются, пока pass пропускает RST к приложениям), затем pass закрывается до остановки движка,
  block остаётся до нового `Arm`;
- установка обновления и перенос в Program Files → `HoldKillSwitch`: block переживает выход, новая
  копия с `--reconnect` снова ставит pass;
- запуск → `InitKillSwitch` видит подслой от прошлого запуска: статус `blocking`, на главной
  «Подключиться» и «Открыть интернет». Он сразу обновляет исключение программ (`RefreshApps`): блок
  мог остаться от копии по другому пути (перенос в Program Files, обновление). Если состояние
  неизвестно (например, блоком владеет HyRoute другого пользователя), при включённом kill switch
  ошибка показывается в статусе. При старте с `--autostart` окно с оставшейся блокировкой
  открывается видимым (не в трее и не свёрнутым), как при `--killswitch-check`;
- «Открыть интернет» после того, как автопереподключение уже снова взвело kill switch, ничего не
  снимает: интернет открыт, защита подключения остаётся.
- проверка при входе: пока kill switch включён, HyRoute в Program Files (`protectedLocation`,
  [app.md, «Интерфейс и система»](app.md#интерфейс-и-система)) и нет задачи автозапуска, существует
  задача пользователя «HyRoute kill switch (<SID>)» (`autostart.EnableCheck`, та же XML-схема и COM
  `RegisterTask`, HighestAvailable, Priority 4, задержка 3 с). Она запускает `HyRoute.exe
  --killswitch-check`. Сразу после проверки прав, до `--wait-pid`, single-instance, восстановления
  обновления и прочего, `main` вызывает `killswitch.Leftover`: подслой установлен и нет
  Global-мьютекса владельца, созданного повышенным процессом, то есть ни один HyRoute его не ведёт.
  Без захвата владения, в отличие от `Engaged`. Если блокировки нет, процесс тихо выходит (код 0).
  Если есть или результат неизвестен, HyRoute стартует обычно с видимым окном. Синхронизация задачи
  (`GUI.syncKillSwitchCheck`, решение `planCheck`): при старте, при смене настройки kill switch, при
  `SetAutostart`. Пока `settings.json` не загружен, задача не меняется. Копия не в защищённой папке
  задачу не создаёт, а в настройках показывает предупреждение. Если права папки открыли уже после
  создания задачи, копия удаляет свою задачу при любых настройках: задача запускает exe с
  HighestAvailable, а его может подменить любая программа пользователя. Задачу другой копии она не
  трогает. Задачу автозапуска, которая запускает программу из папки, открытой на запись программам
  без прав администратора (`protectedLocationOf`), `syncKillSwitchCheck` удаляет при любых
  настройках и пишет об этом в журнал.

Блокируется весь трафик, а не только туннельный: без движка правила по программам и доменам
применить нечем. DNS разрешён, потому что Hysteria резолвит сервер через службу DNS-клиента
(svchost), а не от своего процесса. Флаг PERSISTENT не ставится намеренно: блок, переживший
перезагрузку, оставил бы без интернета пользователя, который не запускает HyRoute.

| Сценарий | Что происходит | Почему трафик не ломается |
|---|---|---|
| Штатный выход / Disconnect | `Session.Stop` сначала сбрасывает соединения relay RST, пока фильтры ещё стоят; движок инжектит RST (как от удалённой стороны) в каждое отражённое соединение приложения, ожидая этот сброс не дольше 0,5 с; затем `WinDivertShutdown(BOTH)` и `Close` у всех main-хэндлов (в том числе у второго, если шла горячая замена), H2–H4; Job убивает Hysteria. `Engine.Stop` ждёт горутины не дольше 5 с. Close relay отменяет ожидающие dial, а не ждёт `DialTimeout`. `Session.Stop` и `ResetConnections` ждут обработчики relay не дольше 0,5 с (`relayWait`): обработчик может ждать блокировку NAT, которую держит зависший packet loop. Если время вышло, в журнал пишется «relay: connection handlers still running after close», и остановка продолжается | Фильтров нет, новые соединения идут напрямую. Соединения, которые шли через relay или туннель, рвутся, приложения переподключатся, а не продолжают их напрямую |
| Panic в горутине | `recover` в каждой горутине. Ошибка в соединении закрывает только его. Паника или неожиданная ошибка `Recv` в packet loop закрывают все main-хэндлы и дают статус «Engine failed». Через 5 с — автоматическое переподключение с тем же лимитом (3 за 10 минут), см. «Зависание packet loop» | Хэндлы закрыты явно |
| Крэш процесса (fatal error, kill) | Ядро закрывает хэндлы процесса, WinDivert сразу снимает фильтры; `KILL_ON_JOB_CLOSE` убивает Hysteria | Фильтры в ядре живут только пока открыт хэндл |
| Зависание packet loop | **Опасно:** WinDivert дропает пакеты, пролежавшие в очереди дольше `QUEUE_TIME`, то есть получается чёрная дыра. **Watchdog в процессе:** зависание считается по тикам: 4 тика по 500 мс без завершения той же пачки (у каждого packet loop своё состояние), а не по настенным часам. Тогда все main-хэндлы закрываются принудительно (fail-open), отражённые соединения приложений сбрасываются RST, как при Stop, ещё до `OnFail` (пока pass действует), соединения relay — в `OnFail` (ожидание не дольше 0,5 с: зависший loop может держать блокировку NAT или `swapMu`, тогда фильтры снимаются без сброса, с записью в журнал). Перед закрытием хэндлов в журнал движка пишутся стеки всех горутин (до 64 КБ). Остановка ждёт обработчики relay не дольше 0,5 с (`relayWait`), как при Disconnect. Движок остаётся в failed до Stop, `SetServerIPs` больше не открывает H1. Контроллер через 5 с сам делает переподключение (новая сессия, новый движок; зависшая горутина старого не мешает). Не больше 3 автоматических переподключений за 10 минут, дальше статус «Движок перехвата снова отказал: 3 автоматических переподключения за 10 минут не помогли…», окно показывается (`OnGiveUp`), и HyRoute ждёт пользователя. Неудачный запуск при автоматическом переподключении тоже считается попыткой, в статусе к ошибке запуска добавляется, будет ли ещё попытка. Connect, Disconnect, Reconnect и выход отменяют ждущую попытку | Закрытие H1 снимает перехват |
| Зависание всего процесса | **Внешний watchdog** `HyRoute.exe --watchdog <pid>`: тот же exe, крошечный режим без UI, пинг через named pipe раз в 500 мс. Нет ответа 5 с → `TerminateProcess` главного процесса, дальше как при крэше | То же |
| NAT-запись отражённого соединения истекла | Внутри сессии не-SYN сегменты такого соединения получают RST, а не уходят напрямую | Приложение переподключится через движок |
| Соединения, открытые до старта (в том числе после крэша HyRoute) | Не-SYN пакеты без состояния решаются по правилам (владелец из IP Helper, домен только из DNS cache, [routing.md, «Где принимается решение»](routing.md#где-принимается-решение)): Direct проходит, Tunnel и Block — RST приложению, пакет в сеть не уходит | Приложение переподключится через движок. Ограничение: DNS cache каждой сессии начинается пустым (при любом Connect, после крэша и после автопереподключения), а при «Точном определении домена для веба» веб-порты решаются без домена вообще. Соединение, которое шло в туннель только по доменному правилу, решается без домена (обычно по «Всё остальное») и при обычном подключении может продолжиться напрямую. После отказа движка (автоматическое переподключение и переподключение пользователя до «Отключить») и поверх блокировки kill switch такое соединение сбрасывается (`ResetUnknownDomain`) |
| Relay-listener упал | Флаг `relayHealthy=false`: Tunnel → RST на уровне пакетов, NeedsDomain решается по DNS/default на пакетах (итог Tunnel → RST). Listener перезапускается | Direct/Block relay не используют |
| Hysteria упала или ещё не подключена | Tunnel → RST/drop, в UI «Туннель недоступен, N соединений отклонено». Автоперезапуск с backoff 1 → 2 → 4 … 60 с (сброс после 30 с стабильной работы); при ошибке авторизации или конфига сразу 60 с и красный статус | Direct не затронут |
| Сервер пропал после подключения | Hysteria сама переподключается при запросах и пишет warn «SOCKS5 TCP/UDP error» с `connect error` / `authentication error` / `invalid config`. Supervisor видит это как потерю сервера: перезапускает `hysteria.exe`, профиль уходит в Failed, новые соединения идут через запасной ([servers.md, «Запуск серверов: только нужные»](servers.md#запуск-серверов-только-нужные)). Возврат сервера — с обычным backoff (до 60 с) | Fallback работает, как при недоступности на старте |
| SOCKS CONNECT вернул ошибку | RST приложению, в логе причина | Обычная семантика прокси |
